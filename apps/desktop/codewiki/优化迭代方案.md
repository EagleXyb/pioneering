## 1. 六大维度现状综述

### 1.1 架构设计

项目采用标准的 Electron 三层架构（main / preload / renderer），主进程 `src/main/index.ts` 负责窗口创建与 CSP，`src/main/ipc-handlers.ts` 注册 26 个 `ipcMain.handle` + 3 个 `ipcMain.on`（拖拽），所有 `handle` 入口校验 `isTrustedSender`，路径相关操作额外做 `isValidFilePath` + `isPathAllowed` 校验。preload 通过 `contextBridge` 仅暴露 `window.api` 与 `window.electron`（不暴露整包 `electronAPI`，仅 `webUtils.getPathForFile`），`contextIsolation` 未启用时直接抛错终止，安全基线扎实。

架构上最核心的债务是**双轨分裂**（详见 [04-Agent 能力评估 §1](./04-agent-capability-assessment.md)）：mock 轨道（`useAgentStore` + `AgentPage` + `AgentStep`/`AgentExecution` 类型，`/agent` 路由入口）与生产轨道（`chatStore.agentMode` + `agentService` + `ToolCall`/`ContentBlock` 类型，主聊天界面 "Agent 模式" 开关入口）并行存在且互不相通。`AgentPage` 用 `setTimeout` + 硬编码 4 步模拟执行，`useAgentStore` 的方法从未被真实 API 调用，`/agent` 路由实际是死路。

### 1.2 核心业务逻辑

聊天业务核心在 `chatStore.ts` `sendMessage`（L193-478，约 285 行）中实现。发送流程：abort 旧流 → 建/复用 session → 生成单调递增 `streamSeq`（竞态守卫）→ 注入 userMessage + assistantPlaceholder → 根据 `agentMode` 选择 `agentService` / `chatService.sendMessageStream` → `buildSendText` 把 `@{path}` 转 `<select-file>` 标签 → 注册回调。

流式响应采用 rAF 批量更新（`scheduleUpdate`）：`pendingContent` / `pendingThinking` 累积增量，每帧最多 flush 一次到 `streamingContent` / `streamingThinking`。竞态守卫通过模块级 `streamSeq` 单调递增序号实现，每个回调入口检查 `if (mySeq !== streamSeq) return`，旧流回调发现自己不是最新流时立即丢弃。工具调用流程：`onToolCallStart` → `liveToolCalls.push`，`onToolCallArgs` 合并 arguments，`onToolCallResult` 回填状态。上下文注入单向：用户 `@{path}` → `buildSendText` → `<select-file>` 标签 → 后端解析；Agent 工具调用读文件的结果不会回注到前端上下文面板。

### 1.3 组件层级与依赖

`RootLayout` 实现三栏模式（`three-column`）与覆盖模式（`overlay`）双布局：三栏用 `ResizablePanelGroup` + 3 个 `ResizablePanel`（sidebar/center/context-panel），通过 `collapse/expand` 控显隐；覆盖模式中栏全宽 + 两个 `Drawer` 抽屉。`ResizablePanel` 的 `autoSaveId` 含 platform 后缀（`pioneering-main-layout-${platform}`），按平台区分记忆，避免各 OS 窗口尺寸差异导致布局错乱。

`ContextPanel` 三块（`CodePreview.tsx` 纯文本 `<pre>` 只读无高亮、`DiffViewer.tsx` 第 1 行硬编码 `bg-green-500/10` 演示无真实 diff 逻辑、`TerminalView.tsx` 100% 静态硬编码无输入输出流）均属历史遗留 mock，**与本项目工作协作向定位不符**，按"待清理的非核心遗留"处理（详见 §2.5 L1）。`ToolCallCard` 仅支持展开/收起结果文本，不支持批准/拒绝/重试/嵌套/分组/耗时。`ThinkingBlock` 纯文本流可折叠，不支持 Markdown/耗时/分阶段标记/与工具调用的关联。

### 1.4 数据流向与 API 交互

API 服务层使用双通道无 WebSocket：axios（`client.ts` 单例 `apiClient`，timeout 60s）负责常规 REST，fetch + ReadableStream（`client.ts` `stream()` 方法）负责 SSE 流式。认证采用 Bearer Token 双 Token 机制（accessToken + refreshToken，存储在 `ApiClient` 实例内存字段中不落 localStorage），401 自动刷新使用 single-flight 模式避免 refresh token 并发轮换。

`agui.ts` 是通用 AG-UI SSE 解析器，chat 与 agent 共用同一套事件类型（`RUN_STARTED`、`THINKING_*`、`TEXT_MESSAGE_*`、`TOOL_CALL_*`、`RUN_FINISHED`、`RUN_ERROR`），工具参数分片缓冲（`toolArgsBuffer`）累积后尝试 JSON 解析。IPC 调用通过 `ipc.ts` 封装 `window.api`，所有 API 通过 `getApi() => window.api` 获取，IPC 不可用时返回安全降级默认值（如 `isMaximized` → `Promise.resolve(false)`，`getVersion` → `'0.0.0'`，文件操作 → `{canceled:true}`）。

### 1.5 状态管理策略

状态管理采用 Zustand（业务）+ Jotai（UI）双库并存。Jotai `atoms.ts` 管理细粒度 UI 原子态：`platformAtom`、`isFullscreenAtom`、`sidebarVisibleAtom`、`contextPanelVisibleAtom`、`settingsOpenAtom`、`settingsCategoryAtom`（`atomWithStorage` 持久化）、`userAtom`（硬编码占位 `{ name: 'Demo User', email: 'demo@pioneering.ai' }`，未接入 `authService.getProfile()`）。Zustand 管理业务域：`useAppStore.ts`（主题模式，`persist` 中间件持久化）、`chatStore.ts`（聊天核心）、`useAgentStore.ts`（mock 专用，未被真实业务使用）、`useWorkspaceStore.ts`。

消息存储 `Record<sessionId, Message[]>` 全量内存缓存，无 LRU 淘汰、无上限（`chatStore.ts:27`）。`selectSession` 仅当 `messages[sessionId]` 不存在时才 `loadMessages`，且不 await（fire-and-forget）。持久化机制两套并存：`settingsCategoryAtom` 用 Jotai `atomWithStorage`，`theme` 用 Zustand `persist`，增加心智负担。主进程 `appStore` 注释承诺持久化但实际仅内存实现（`ipc-handlers.ts:30` `// 简单的内存 Store（可替换为 electron-store）`），重启即丢失。

### 1.6 页面布局与样式

布局系统采用 `ResizablePanel` 按平台记忆 + Tailwind v4。`platform/layout-tokens.css` 把所有平台差异下沉到 CSS 变量：`:root[data-platform='mac']` 定义 `--titlebar-h: 38px`、`--radius-control: 6px` 等，`:root[data-platform='windows']` 定义 `--titlebar-h: 40px`、`--titlebar-leading: 8px` 等，组件层只消费 `var(--titlebar-h)` 等语义变量，不再出现 `isMac ? '...' : '...'` 的平台硬编码。

菜单系统数据驱动，`shared/menu-template.ts` 为单一数据源（4 个顶级菜单：Pioneering / 编辑 / 窗口 / 帮助），macOS 由原生菜单处理，Windows/Linux 由渲染端 HTML 渲染下拉菜单，`formatAccelerator.ts` 把 Electron accelerator 转为平台符号。设置面板同样数据驱动，`settingsConfig.tsx` 为单一数据源，新增分类只需追加数组项零改动外壳。XSS 防护纵深：自定义 sanitize schema + SafeLink + 图片 mediaType 校验 + `rel="noreferrer noopener"`。

## 2. 问题分类详述

> 每个问题条目严格采用四段式：现状分析 / 对标差距 / 优化方案（重构方向 + 优先级 + 预期收益）。

### 第一类：架构缺陷（Architectural Flaws）

### 2.1 A1 双轨分裂：mock 轨道与生产轨道完全不互通 ✅ 已修复

**现状分析**：代码库存在两套并行且互不相通的 Agent 抽象（详见 [04-Agent 能力评估 §1](./04-agent-capability-assessment.md)）。mock 轨道：`src/renderer/src/stores/useAgentStore.ts` + `src/renderer/src/pages/AgentPage.tsx`（L20-33 硬编码 4 步 + setTimeout）+ `AgentStep`/`AgentExecution` 类型（`src/shared/types.ts:201-219`），`useAgentStore` 的 `startExecution`/`addStep`/`completeExecution` 从未被真实 API 调用。生产轨道：`src/renderer/src/stores/chatStore.ts`（`agentMode: boolean` L38，`setAgentMode` L537）+ `src/renderer/src/services/api/agent.ts` + `ToolCall`/`ContentBlock` 类型（`src/shared/types.ts:79-90,167-177`）。二者完全无互引用，`/agent` 路由是死路，真实 Agent 能力藏在主聊天界面的 agentMode 开关里，用户与维护者均易被误导。

**对标差距**：Workbuddy 等工作协作向产品采用统一的 Agent 运行时，任务/工具/记忆抽象单一来源，不存在 mock 与生产分裂。本项目双轨分裂导致 Agent 能力无法演进，与对标产品存在代际差距。

**优化方案**：
- 重构方向：删除 `useAgentStore.ts` 与 `AgentPage.tsx` mock 代码（或重写为 Agent 工作台），合并 agentMode 逻辑到统一 `chatStore`；补齐 `agentService` 会话管理接口（list/update/delete）；统一 Agent 会话与普通会话的 store 订阅模式。具体见 [05-Agent 重构方案 §4](./05-agent-refactor-plan.md)。
- 优先级：P0
- 预期收益：消除架构债务，统一 Agent 演进路径，避免维护者误判功能完成度，为后续任务规划/HITL/Diff 审查等能力扩展铺路。

**修复状态**（2026-07-18）：已删除 `useAgentStore.ts` 与 `AgentPage.tsx`；[App.tsx](../../src/renderer/src/App.tsx) 移除 `/agent` 路由；[HomePage.tsx](../../src/renderer/src/pages/HomePage.tsx) 移除指向 `/agent` 的导航卡片与 Hero 按钮，grid 从 3 列适配为 2 列。`agentService` 已具备完整会话管理接口（createSession/getSession/sendMessageStream/getExecutions/getExecutionResult/stopGeneration），Agent 功能统一由 `chatStore.agentMode` 承载。保留 `InputArea`/`SlashCommandPopover` 的 `/agent` 斜杠命令（与路由无关，属 L2 范围）。

### 2.2 A2 安全基线缺陷：信任源校验与 CSP 多处可绕过 ✅ 已修复

**现状分析**：三处高危/中危安全问题（详见 [02-问题诊断 §1](./02-issues-diagnosis.md)）。S1（高危）：`src/main/ipc-handlers.ts:73` `isTrustedSender` 正则 `/^https?:\/\/localhost(:\d+)?\b/i` 中 `\b` 对 `http://localhost.evil.com` 命中（`.` 是非单词字符），攻击者注册 `localhost.evil.com` 即可绕过信任源校验，所有依赖 `isTrustedSender` 的 IPC 通道均可被绕过。S2（高危）：`src/main/index.ts:23` CSP `connect-src 'self' http://localhost:6000 ws://localhost:* wss:` 中 `wss:` 无主机限定，渲染端被 XSS 后可通过 `wss://attacker.com` 外泄数据。S3（中危）：`src/main/index.ts:85-88` `setWindowOpenHandler` 直接 `shell.openExternal(details.url)` 未校验协议，与 `SHELL_OPEN_EXTERNAL`（仅允许 http(s)）不一致，`file://`/`javascript:`/`data:` 都会传给 `shell.openExternal`。S6（低危）：正则仅匹配 `localhost`，开发服务器若绑定 `127.0.0.1` 则所有 IPC 调用被判定不可信，功能大面积失效。

**对标差距**：Workbuddy 等工作协作向产品 均遵循最小信任源原则，CSP 严格限定主机与协议，外部链接打开均经协议白名单过滤。本项目 `wss:` 全开放与 localhost 正则可绕过属于基线级缺陷。

**优化方案**：
- 重构方向：`isTrustedSender` 改为 `^https?:\/\/(localhost|127\.0\.0\.1|\[::1\])(:\d+)?(?:\/|$)` 或字符串前缀匹配（顺带解决 S6）；CSP 移除 `wss:` 或限定为 `wss://具体主机`；`setWindowOpenHandler` 复用 `SHELL_OPEN_EXTERNAL` 的 http(s) 白名单，非白名单直接 `return { action: 'deny' }`。详见 [03-改进建议 §1](./03-improvement-suggestions.md)。
- 优先级：P0
- 预期收益：关闭信任源绕过与 CSP 数据外泄通道，恢复 IPC 与外部链接安全基线。

**修复状态**（2026-07-18）：全部修复。S1/S6：[ipc-handlers.ts:78-88](../../src/main/ipc-handlers.ts) `TRUSTED_HOST_PATTERN` 改为 `/^https?:\/\/(?:localhost|127\.0\.0\.1|\[::1\])(?::\d+)?(?:\/|$)/i`，补充 `127.0.0.1`/`[::1]` 并消除 `\b` 绕过。S2：[index.ts:26-38](../../src/main/index.ts) CSP `connect-src` 移除 `wss:`，改为 `http://localhost:* http://127.0.0.1:* ws://localhost:* ws://127.0.0.1:*`。S3：[index.ts:95-103](../../src/main/index.ts) `setWindowOpenHandler` 加 `^https?:\/\//i` 协议白名单，非白名单 `return { action: 'deny' }`。额外修复：S4 符号链接绕过（[ipc-handlers.ts:99-142](../../src/main/ipc-handlers.ts) `resolveWithParentRealpath` 逐级解析）、B6 STORE_SET sanitize 失败拒绝写入（[ipc-handlers.ts:432-444](../../src/main/ipc-handlers.ts)）、B13 拖拽状态窗口关闭清理（[ipc-handlers.ts:499-518](../../src/main/ipc-handlers.ts)）。

### 2.3 A3 类型层僵尸定义：定义但未消费的类型集合

**现状分析**：`src/shared/types.ts` 中多个类型已定义但未被真实链路消费（详见 [04-Agent 能力评估 §3](./04-agent-capability-assessment.md)）。`AgentExecuteRequest`（L138-143）：`agent.ts` 实际用 `SendMessageRequest`，此类型形同虚设；`AgentStep` / `AgentExecution`（L201-219）：仅 mock 使用；`AgentToolExecution`（L146-159）：`getExecutions`/`getExecutionResult` 接口前端从未调用；`ThinkingBlock.duration`（L162-165）：定义了但从未赋值；`ToolCall.startTime` / `endTime`（L167-177）：store 赋值但 UI 不渲染；`SSEChunk`（L107-115）：旧式定义，与 `agui.ts` 实际事件不一致。这些僵尸定义增加类型噪音、误导维护者，且阻塞类型层演进。

**对标差距**：Workbuddy 等工作协作向产品 的类型系统与运行时严格一致，类型即契约。本项目类型层与运行时脱节，类型不能作为可靠契约。

**优化方案**：
- 重构方向：删除 `AgentExecuteRequest`、`SSEChunk`、`AgentStep`/`AgentExecution` 等僵尸类型；`ThinkingBlock.duration`、`ToolCall.startTime/endTime` 要么在 UI 实现要么删除；按 [05-Agent 重构方案 §2](./05-agent-refactor-plan.md) 新增 `AgentPlan`/`AgentPlanStep`/`ContextWindowState`/`AgentCheckpoint` 等真实消费的类型。
- 优先级：P1
- 预期收益：消除类型噪音，使类型层成为可靠契约，为协议层扩展与 UI 渲染提供类型支撑。

### 2.4 A4 协议层无任务语义：agui.ts 通用 SSE 解析器无法表达 Agent 流程

**现状分析**：`agui.ts`（`src/renderer/src/services/api/agui.ts:134-228`）是通用 AG-UI SSE 解析器，chat 与 agent 共用同一套事件，协议层无任务语义。支持事件：`RUN_STARTED`、`THINKING_TEXT_MESSAGE_CONTENT`、`TEXT_MESSAGE_START`、`TEXT_MESSAGE_CONTENT`、`TOOL_CALL_START`、`TOOL_CALL_ARGS`、`TOOL_CALL_RESULT`、`RUN_FINISHED`、`RUN_ERROR`。**不支持**的事件（对标成熟 Agent 应用所需）：`PLAN_CREATED` / `STEP_STARTED` / `STEP_COMPLETED`（任务规划与拆解）、`TOOL_CALL_APPROVAL_REQUIRED`（人工确认）、`PARALLEL_TOOL_GROUP`（并行工具编排）、`CONTEXT_COMPACTED`（上下文压缩）、`MEMORY_UPDATED`（长期记忆）、`CHECKPOINT_CREATED`（断点恢复）。chat 与 agent 唯一差异是 URL 端点（`/chat/completions` vs `/agent/completions`），请求体完全一致，agentMode 不会附加 tools/plan/systemPrompt 等字段。

**对标差距**：Workbuddy 等工作协作向产品支持任务规划（Plan/Step）、关键操作人工确认（Approval）、任务编排与跨场景协作、上下文压缩与 checkpoint 恢复等事件语义。本项目协议层无法表达 Agent 的规划/审批/编排/压缩/恢复语义，是对标产品中能力最弱的一环。

**优化方案**：
- 重构方向：按 [05-Agent 重构方案 §3](./05-agent-refactor-plan.md) 扩展 `AguiEventType` 新增 PLAN/STEP/APPROVAL/PARALLEL/CONTEXT/CHECKPOINT 事件；扩展 `AguiStreamCallbacks` 新增 `onPlanCreated`/`onStepStarted`/`onApprovalRequired`/`onParallelGroup`/`onContextCompacted`/`onCheckpoint` 等回调；`agui.ts` switch 分支新增对应解析。后端在 `/agent/completions` 流里推送新事件。
- 优先级：P1
- 预期收益：协议层具备 Agent 任务语义，支撑任务规划 UI、HITL、工具编排、上下文压缩、中断恢复等核心能力落地。

### 第二类：逻辑冗余（Logic Redundancy）

### 2.5 L1 ContextPanel 三块遗留 mock：与工作协作定位不符的非核心代码

**现状分析**：`src/renderer/src/components/context-panel/` 三块均为 mock（详见 [02-问题诊断 §4 C3](./02-issues-diagnosis.md)）。`DiffViewer.tsx`（L24, L47）第 1 行硬编码 `bg-green-500/10` 当作「added」演示，无真实 diff 逻辑；`TerminalView.tsx` 是纯静态 UI，无输入/输出流；`CodePreview.tsx` 是纯文本 `<pre>` 只读无高亮无行号。三块均属历史遗留代码，**与本项目"工作协作向 AI Agent"定位不符**（非 AI Coding 产品，不涉及代码 Diff 审查、终端执行、代码编辑能力），但当前仍占据 `ContextPanel` 的 Tab 位置，既误导维护者对产品能力的判断，也占用 UI 空间。

- 重构方向：DevTools 生产构建时移除该 API，或 handler 内加 `is.dev` 守卫；`appStore` 接入 `electron-store` 或明确重命名为 `appMemoryStore`；`Cmd+K` 实现 `global-search` 监听器，或移除该快捷键绑定。
- 优先级：P2
- 预期收益：生产构建无调试后门，持久化语义与命名一致，无死快捷键误导用户。

## 5. 值得保留的架构亮点

> 重构过程中应保留以下已有优秀实践，勿在重构中丢失。

1. **安全基线扎实**：`sandbox: true` + `contextIsolation: true` + `nodeIntegration: false` + CSP + 信任源校验 + 路径白名单 + 原型链净化（`sanitizeValue`）+ 错误脱敏。`contextIsolation` 未启用时直接抛错终止。
2. **XSS 防护纵深**：`MessageBubble` 自定义 sanitize schema（基于 `hast-util-sanitize` 默认白名单扩展）+ 显式收紧 `href` 协议为 `http/https/mailto` + `SafeLink` 组件非 http(s) 链接降级为 `<span>` + 图片附件按 `mediaType` 区分（非 `image/*` 不作为 `<a href>` 打开，防 data: HTML 注入）+ `rel="noreferrer noopener"` 防 reverse tabnabbing。
3. **流式竞态处理**：`streamSeq` 模块级单调递增守卫，每个回调入口检查 `if (mySeq !== streamSeq) return`，旧流回调立即丢弃；rAF 批量更新每帧最多 flush 一次；single-flight token 刷新避免 refresh token 并发轮换。
4. **平台差异 CSS 变量化**：`platform/layout-tokens.css` 把所有平台硬编码下沉到语义变量（`--titlebar-h`、`--radius-control`、`--titlebar-leading` 等），组件层只消费 `var(--titlebar-h)`，不再出现 `isMac ? '...' : '...'`。
5. **菜单系统数据驱动**：`shared/menu-template.ts` 单一数据源（4 个顶级菜单），macOS 由原生菜单处理，Windows/Linux 由渲染端 HTML 渲染下拉菜单，`formatAccelerator.ts` 转平台符号。
6. **IME 正确处理**：`isComposing` 判断，避免输入法组合期间触发发送。
7. **ResizablePanel 按平台记忆**：`autoSaveId={`pioneering-main-layout-${platform}`}` 按平台区分记忆，避免各 OS 窗口尺寸差异导致布局错乱。
8. **TypeScript 严格模式**：`strict: true` + `noUncheckedIndexedAccess: true`，类型安全基线高。
9. **preload 不暴露整包 `electronAPI`**：仅暴露 `webUtils.getPathForFile`，最小暴露面。
10. **IPC 安全降级策略**：`ipc.ts` 封装 `window.api`，IPC 不可用时返回安全降级默认值（如 `isMaximized` → `false`，文件操作 → `{canceled:true}`），渲染端不崩溃。窗口拖拽 rAF 节流：`moveDrag` 由高频 `mousemove` 触发，通过模块级 `requestAnimationFrame` 合并，每帧最多发一次 IPC，只发最新坐标，`endDrag` 时 `flushDrag()` 冲洗最后一帧防止松手漂移。

## 6. 实施约束与风险提示

1. **双轨统一需谨慎**：删除 `useAgentStore` / `AgentPage` 前需确认无隐藏引用（如路由配置、测试用例），建议先标注 `@deprecated` 一个版本再删除。
2. **协议层扩展需后端协同**：`agui.ts` 新增事件解析需后端在 `/agent/completions` 流里推送对应事件，前后端需同步契约。
3. **遗留 mock 清理需确认引用**：移除 `DiffViewer` / `TerminalView` / `CodePreview` 前需排查 `ContextPanel` 的 Tab 注册、路由、类型引用，避免遗漏导致编译错误；清理后 `ContextPanel` 容器可保留为未来工作协作向面板的承载壳。
4. **消息虚拟化需处理动态高度**：`MessageBubble` 高度因 Markdown/工具调用而异，`@tanstack/react-virtual` 需用 `measureElement` 动态测量，避免滚动跳跃。
5. **安全基线修复需回归测试**：`isTrustedSender` 正则修改需覆盖 `localhost`/`127.0.0.1`/`[::1]`/`localhost.evil.com` 等场景；CSP 修改需验证开发服务器与生产环境 WebSocket 连接。
6. **保留亮点勿丢**：重构中需保留 §5 所列 10 项亮点，特别是 XSS 防护纵深与流式竞态处理，这些是已有安全与稳定性的基石。
7. **工作协作向能力扩展需先明确场景**：任务编排、文档预览、知识库等 P3 能力在实施前需先明确目标工作场景与用户流程，避免盲目对标导致功能堆砌。
