# 用户消息气泡交互优化方案

> 目标：用户消息发送后，鼠标悬停时在气泡下方显示「时间 + 编辑 + 复制」；点击编辑后，用户消息进入行内可编辑状态（气泡变为带边框的输入卡片 + 底部提示条 + 取消/发送），样式对齐参考图。
>
> 参考图仅作样式参考，图中文字内容不采纳；但图中提示语"编辑后将从此处重新开始对话，已有产物不会被删除"所隐含的**语义**（编辑 = 在该点重开分支）是本方案的改造目标之一，第 3 节会专门分析它与现有后端接口的冲突。
>
> 本方案基于对 `apps/web`（及 `apps/backend-ts` 契约侧）代码的逐文件比对，所有结论均标注了文件与行号。

与本文档的差异说明：

1. **§3.5 消息真实 id 的解法改为前端按内容对齐**（`resolveLocalMessageIds`），而非扩展 `RUN_STARTED` 事件。原因是该做法不需要改 SSE 协议，且对"本地存在未持久化占位消息"的错位场景更安全（严格按 (role, 文本) 单调回溯匹配，宁可解析失败也不允许错配）。
2. **`truncateAfter` 省略时按 true 处理**（仅在携带 `messageId` 的编辑重发请求中），避免前端漏传导致"改了正文却把后续消息全留下"。
3. **chat 模式在编辑重发成功或被中止后刷新历史**；失败时不刷新，以保留本地错误提示。
4. **pro / task 不在重发后强制刷新历史**：`loadHistory` 会重建右侧推理面板/任务流水线状态，代价高于收益；id 对齐在下次提交时按需完成。
5. **Python 后端（`apps/backend`）未同步改造**：Web 端经 vite 代理指向 `localhost:8088`（`apps/backend-ts`），Python 侧为迁移前的参考实现，如需保持镜像一致需另行按 `core/message-edit.ts` 的逻辑补齐。

### 1.4 消息 id 在实时会话中是"伪 id"（重大发现）

`useAguiChat.ts` 在流式发送时本地造 id：

```ts
// useAguiChat.ts L92-104
const ts = Date.now();
const userMsg = { id: `u_${ts}`, role: 'user', ... };
const assistantMsg = { id: `a_${ts}`, role: 'assistant', ... };
```

发送完成后**不会自动拉取历史**（`reloadHistory()` 仅在 `handleReplay` 成功后调用，见 `ChatMode.tsx` L234–262）。而 `TEXT_MESSAGE_START` 事件里虽然带着后端真实 `assistantMsgId`（`apps/backend-ts/src/core/llm.ts` L80），但 `useAguiChat` 并未消费 `onTextStart`，`RUN_STARTED` 也只带 `{threadId, runId}`，**不回传 user 消息的真实 id**。

推论（两条，均为本方案的前置依赖）：

1. 刚流式完成的用户消息，前端持有的是 `u_*`，**无法直接调用 `PUT /chat/sessions/:id/messages/:messageId`**（后端按真实 `msg_*` 主键查找，必然 404）。
2. 顺带暴露一个既有缺陷：`onReplay(message.id)` / `handleStop` 传入的也是 `a_*` 伪 id，对"本次刚生成、尚未刷新历史"的消息点击"重新生成"会 404（`apps/backend-ts/src/routes/chat.ts` L878–895 按 id 查库）。用户气泡编辑功能会继承同一个问题，必须一并解决。

## 3. 后端数据流向与接口冲突分析（核心章节）

### 3.1 现有相关接口清单

| 接口 | 前端封装 | 关键实现 | 语义 |
| --- | --- | --- | --- |
| `PUT /api/chat/sessions/:sessionId/messages/:messageId` | `api/message.ts#editMessage`（**当前无调用方**） | backend-ts `routes/chat.ts` L479–524；Python `app/api/v1/chat.py` L276–317 | 仅更新 user 消息 `content`；`regenerate=true` 时转 `doRegenerate` |
| `POST /api/chat/completions` | `useAguiChat` 内联 fetch（L164–179） | L530–827 | **每次必新建一条 user 消息**（L563–572），随后 SSE 流式，末尾持久化 assistant（L790–801） |
| `POST /api/chat/messages/:messageId/regenerate` | `api/message.ts#regenerateMessage` | L878–895 + `doRegenerate` L938–1039 | 复用既有 user 消息，**非流式**追加一条 assistant |
| `GET /api/chat/sessions/:sessionId/messages` | `getMessages` | L~420–476 | 游标分页，返回真实 id 与 `createdAt` |

### 3.2 编辑重发在现有实现下的真实数据流

以"编辑第 N 条用户消息并发送"为例，走现有 `editMessage(..., {regenerate:true})`：

```
前端 editMessage(sessionId, messageId, { content, regenerate: true })
  └─ PUT /chat/sessions/:id/messages/:messageId
       ├─ 校验会话归属 + 消息归属 + role === 'user'（否则 403）
       ├─ UPDATE chat_message SET content = ?            ← 只改这一条
       └─ doRegenerate(userId, messageId, sessionId, {})
            ├─ buildMessageContext(sessionId)
            │    └─ 取最近 20 条（createdAt desc, id desc）→ 反转为时序
            ├─ 按 id 找到编辑后的 user 消息下标，slice(0, idx+1)   ← 仅"喂给 LLM 的上下文"被截断
            ├─ llmService.chatCompletion(...)              ← 非流式，无思考流/无来源事件
            └─ INSERT 新的 assistant 消息（追加到末尾），messageCount += 1
  └─ 返回新 assistant 的 Message JSON（一次性，不支持 SSE）
```

### 3.3 与目标行为的四处冲突（必须显式决策）

| # | 冲突 | 现有实现 | 目标行为 | 影响 |
| --- | --- | --- | --- | --- |
| **C1** | **"从此处重新开始对话"未落地** | `doRegenerate` 只截断"送给 LLM 的上下文数组"，**不删除也不隐藏**被编辑点之后的旧消息 | 界面与历史中，编辑点之后的消息应消失（分支切换） | 只要用户刷新/切会话，旧回复会与新的回复**同时出现在时间轴上**（旧 assistant 创建时间更早，排在新的前面），界面与目标语义完全不符 |
| **C2** | **非流式 vs 流式体验断层** | 编辑重发走 `doRegenerate`，返回一次性 JSON | 日常发送走 `/chat/completions` SSE（思考流、`WEB_SEARCH_SOURCES`、token 用量） | 编辑重发时无"深度思考中…"、无"N 篇来源"、无逐字渲染，且 `useAguiChat` 的 `buildContent()`（reasoning/search/markdown 三块）与新回复结构不一致 |
| **C3** | **上下文窗口截断不彻底** | `buildMessageContext` 固定 `take: 20`，之后才按 id 截断 | 编辑点若在 20 条窗口之外，窗口内的历史仍会被带入 | 模型看到的上下文 ≠ 界面呈现的上下文，长会话下编辑早期消息会出现"答不对题" |
| **C4** | **`messageCount` / `lastMessageId` 只增不减** | L1006–1012 / Python L630–632 `messageCount + 1` | 若真截断，计数与实际消息数背离 | 侧边栏计数、`total` 分页终止条件（`conversationStore.fetchMoreSessions` L172 用去重长度对 total 比较）可能失真 |

### 3.4 两条落地路径

#### 方案 A：前端截断 + 复用现有 `PUT .../messages/:messageId`（最小改动，不推荐作终态）

前端在编辑发送时：

1. 本地把 `messages` 数组截断到 `index(editedId) + 1`，并把该条内容替换为新文本（乐观更新）；
2. 调 `editMessage(sessionId, messageId, { content, regenerate: true })`；
3. 收到返回的新 assistant 消息后追加到本地尾部；
4. 后续如需刷新历史，本地截断会被覆盖（§6 风险 R2）。

- 优点：不改后端、复用已存在的封装（`editMessage` 目前是死代码，正好启用）。
- 缺点：**C2 无法解决**（非流式）；**C1 只能在当前页面生命周期内"看起来对了"**，刷新即穿帮；C3、C4 仍在。
- 适用：仅作为 P0 的"可用版本"或降级兜底（后端不可改时的临时态）。

#### 方案 B（推荐）：让 `/chat/completions` 支持"编辑重发 + 截断"

后端 `ChatCompletionRequestSchema` **已经声明了 `messageId?` 与 `parentMessageId?`**（`schemas/chat.ts` L84、L87），但路由实现里 `dto.messageId` **从未被读取**（全仓仅 L570 消费 `dto.parentMessageId`）。这是一个"协议预留了、实现没做"的缺口，改动成本可控：

```
POST /chat/completions
{
  sessionId, message, stream: true,
  messageId: "msg_xxx",        // 【新增消费】编辑重发的目标 user 消息
  truncateAfter: true          // 【新增字段】删除该消息之后的所有消息
}
```

后端改动点（`apps/backend-ts/src/routes/chat.ts` `/completions` handler，L535–572 之间）：

1. `dto.messageId` 存在时，校验该消息 `role==='user' && userId===req.user.id && sessionId` 匹配；
2. `truncateAfter` 为真时，事务内 `chatMessage.deleteMany({ sessionId, createdAt: { gt: edited.createdAt } })`（或按 `parentMessageId` 链路递归），并重算 `messageCount`/`lastMessageId`；
3. `UPDATE` 该消息 `content = dto.message`（而非 `create` 新 user 消息）；
4. 后续 SSE 管线保持不变（`buildMessageContext` 天然只拿到截断后的历史，C3 顺带解决）；
5. 流式收尾时 `assistant.parentMessageId = editedUserMsg.id`（对齐 edit 语义）。

- 优点：**C1/C2/C3 全部解决**；编辑重发与普通发送共用同一条流式管线，前端 `useAguiChat` 只需增补"截断 + 就地替换"的乐观更新分支。
- 代价：后端需要一次破坏性较低的功能扩展；需与后端负责人确认"删除"是否要改为**软删除/分支标记**（`Message` 类型已有 `parentMessageId` / `childrenMessageIds`，见 `api/types.ts` L103–104，天然支持"分支"模型：截断 = 切到新分支，旧分支保留但不在主链上渲染）。若产品后续要"重新回到旧分支"，软删除是更好的选择。

> **"已有产物不会被删除"的对应实现**：产物（task 模式的 `artifactStore` / PlanPipeline 步骤）与消息是分离的存储，截断消息列表不触碰产物，天然满足。但需注意反向联动：`useScrollToMessage` 依赖 `[data-message-id="..."]`（`hooks/useScrollToMessage.ts` L38–40），被截断的消息节点消失后，产物面板点"跳转到源消息"会静默失效（该 hook 对找不到节点做了防御，不报错）。

### 3.5 尚未解决的前置问题：编辑需要真实消息 id

无论 A 还是 B，`messageId` 必须是后端真实 id。当前实时会话里是 `u_*`（§1.4）。三种解法：

| 解法 | 做法 | 评价 |
| --- | --- | --- |
| **B1** 协议增强 | `RUN_STARTED` 事件补 `userMessageId`（后端 L718 一行改动）；同时可选补 `assistantMessageId` | **推荐**：零额外请求，顺带修复"重新生成 404"的既有缺陷 |
| **B2** 发送后刷新 | `RUN_FINISHED` 后调一次 `reloadHistory()`，用真实 id 整包替换 | 实现最简单，但每次发送多一次 `GET`，且会打断 `ChatMessageList` 的自动滚动稳定性（§6 R3） |
| **B3** 编辑前按内容匹配 | 编辑时先 `GET` 历史并按 `content` 匹配 id | 脆弱（重复内容多轮对话必然误命中，后端 P2-8 修复注释里已明确否定了这种匹配方式） |

建议：**B1 为主 + B2 为兼容降级**（`useAguiChat` 兜底：若流结束后发现消息 id 仍为 `u_*`，在用户首次点击编辑时先触发一次 `reloadHistory` 再进入编辑态）。

## 5. 状态管理与交互流程设计

### 5.1 状态归属

编辑态是**会话内瞬时 UI 状态**，不应进全局 store（避免污染 `conversationStore`、避免持久化）：

| 状态 | 归属 | 说明 |
| --- | --- | --- |
| `editingId: string \| null` | `ChatSession`（chat）/ 各模式的会话壳组件 | 同一时刻只允许一条消息处于编辑态 |
| `editDraft: string` | 同上（或下放到 `UserMessageBubble` 内部 state） | 编辑中的文本；建议放组件内，取消时随卸载自动丢弃 |
| `submittingEdit: boolean` | 同上 | 请求中禁用"发送/取消"、显示 loading |
| `lastError` | 复用 `toast` | 失败提示 + 回滚，不引入新状态 |

> 选择放在 `ChatSession` 而非 `useAguiChat`：编辑重发需要同时操作"本地消息数组"与"会话历史/滚动"，`ChatSession` 已经同时持有 `messages`（来自 `useAguiChat`）与 `onReplay` 等会话级回调（`ChatMode.tsx` L24–148），是唯一能同时触达两端的层级。
> 会话切换时必须在 `activeId` 变化时清空 `editingId`（否则编辑态会残留在新会话）。

### 5.2 交互流程

```mermaid
flowchart TD
  A[悬停用户气泡] --> B[显示元信息行: 时间 | 编辑 | 复制]
  B --> C{点击编辑}
  C -->|是本地伪 id u_*| D[先 reloadHistory 对齐真实 id]
  C -->|真实 id 或对齐完成| E[进入编辑态: editingId=id, draft=原文, focus 且光标置尾]
  D --> E
  E --> F[气泡替换为编辑卡片 + 底部提示 + 取消/发送]
  F --> G{用户动作}
  G -->|Esc / 取消| H[还原只读气泡, 丢弃 draft]
  G -->|Enter 或 发送| I{内容非空?}
  I -->|空| J[发送按钮 disabled]
  I -->|非空| K[乐观更新: 本地截断到该条 + 就地替换文本 + 插入 assistant streaming 占位]
  K --> L[POST /chat/completions 携带 messageId + truncateAfter, SSE]
  L -->|RUN_FINISHED| M[reloadHistory 对齐顺序与真实 id]
  L -->|RUN_ERROR / 网络失败| N[回滚: 恢复原文本与原消息列表 + toast]
  E -.->|流式进行中| O[编辑入口禁用]
```

### 5.3 键盘与边界交互约定

| 场景 | 约定 |
| --- | --- |
| 发送快捷键 | 复用项目既有策略：Enter 发送 / Ctrl(⌘)+Enter 发送（由 `app:preferences.enterToSend` 决定），Shift+Enter 换行；**必须**做 IME composition 保护（`useTaskInput` 已有成熟实现，见 `modes/task/hooks/useTaskInput.ts`） |
| 取消 | Esc 优先取消编辑（且**不**触发 `ChatInput` 的全局 Esc 停止生成，需 `stopPropagation`） |
| 空内容 | trim 后为空 → 发送按钮 `disabled`，不发起请求 |
| 流式中 | 编辑与取消入口禁用（`status !== 'idle' && status !== 'complete'`） |
| 会话切换 | 清空 `editingId`；若有未保存 draft 直接丢弃（与主流产品一致，不弹确认） |
| 点击卡片外部 | 不自动提交（避免误触）；保持显式"发送/取消" |
| 焦点管理 | 进入编辑态 focus textarea 且光标置尾；取消后焦点回到编辑按钮（保持键盘可达） |

### 5.4 Hook 能力扩展（`useAguiChat`）

新增一个方法，与 `sendUserMessage` 并列：

```ts
export interface ResendOptions {
  messageId: string;      // 真实 user 消息 id
  prompt: string;         // 编辑后的正文
  prevText: string;       // 用于失败回滚
  deepThink?: boolean;
  netSearch?: boolean;
  model?: string;
}

// 语义：截断到 messageId 为止 → 就地替换正文 → 走与 sendUserMessage 相同的 SSE 管线
resendEditedMessage: (o: ResendOptions) => void;
```

实现要点：

1. `inflightRef` 复用（流式中直接 return）；
2. 乐观更新用**函数式** `setMessagesState`：`prev.slice(0, idx + 1)` 并替换该条 `content` 与 `datetime`；
3. 请求体在 `sendUserMessage` 的基础上追加 `messageId`（与 §3.4 方案 B 对齐）；若后端暂未支持，则退化为"截断 + `sendUserMessage`"（会被后端再写一条 user 消息，需靠 `reloadHistory` 收口 —— 这正是方案 A 的形态）；
4. `onTextStart` 回调中捕获后端真实 `assistantMsgId`（`parseAguiStream` L130–132 已分发该事件，目前 `useAguiChat` 未消费），用于就地替换 `a_*` 伪 id；
5. 失败时恢复 `prevText` 与截断前的数组快照。

## 8. 实现风险与边界情况

| # | 风险 / 边界 | 说明与对策 |
| --- | --- | --- |
| **R1** | **消息真实 id 缺失（阻塞级）** | 实时会话 user 消息为 `u_*`，`PUT` 必 404。对策：§3.5 的 B1（`RUN_STARTED` 补 `userMessageId`）为主，B2（发送后 `reloadHistory`）兜底 |
| **R2** | **历史整包替换覆盖乐观截断** | `ChatSession.tsx` L51–53 的 `useEffect` 在 `historyMessages` 变化时执行 `setMessages(historyMessages, 'replace')`。编辑后若触发任何刷新，本地截断结果会被覆盖。对策：截断后的刷新必须以"后端已真实截断"为前提（方案 B），否则会出现"刷新即复活旧回复" |
| **R3** | **自动滚动跳动** | `ChatMessageList.tsx` L100–104 的 effect 依赖 `messages.length` 与 `lastContentLen`；截断会让 `messages.length` **变小**，若用户当时不在底部则会触发意外 `scrollIntoView`。对策：截断时把 `isNearBottomRef.current` 显式置 `true`，或在编辑重发期间挂起该 effect |
| **R4** | **`useChatSync` 副作用** | `useChatSync.ts` L23–79 依赖 `messages` 更新预览与标题；截断后 `preview` 会变为新内容（可接受），`doneRef` 为 `true` 时不会重复生成标题（会话切换会重置 `doneRef`，此时可能重新生成标题 —— 需确认是否符合预期） |
| **R5** | **后端不删后续消息（方案 A 的固有缺陷）** | 刷新/重进会话后旧 assistant 回复复现，时间轴出现"编辑后的用户消息 → 旧回复 → 新回复"。必须在产品层明确：方案 A 只是过渡态 |
| **R6** | **并发与竞态** | ①流式中点击编辑：需禁用入口；②编辑提交中切换会话：请求返回后不得再写入 `messages`（用 `activeId` 快照比对，参照 `ChatMode.tsx` L185 的既有竞态保护写法）；③双击发送按钮：`submittingEdit` + `inflightRef` 双重守卫 |
| **R7** | **附件消息编辑** | 带附件的用户消息正文是"文本 + Markdown 图片/链接"（`useAttachments` 的 `takeMessageSuffix`）。编辑态以**原始 Markdown 文本**呈现（不做富文本），并需在提示中说明；若用户误删图片语法，属预期行为 |
| **R8** | **伪 id 的连带修复** | 修复 §1.4 后，"重新生成"（`onReplay`）与"停止生成"（`handleStop`，L103–117 传 `lastAssistant.id`）的 404 问题也会一并解决；否则编辑功能上线后这两个入口的既有缺陷会更加显眼 |
| **R9** | **Esc 冲突** | `useTaskInput` 用 Esc 停止生成，编辑态 Esc 取消编辑需 `stopPropagation`，否则会误停生成 |
| **R10** | **IME 中文输入** | 必须复用 composition 保护（`isComposingRef`），否则拼音候选阶段的 Enter 会误触发发送 |
| **R11** | **权限与角色** | 前端只对 `role === 'user'` 渲染编辑入口；后端对非 user 消息返回 403、非本人消息 404 —— 属预期，前端 `toast` 展示 `ApiError.message` |
| **R12** | **空/超长/纯空白** | 空 trim 禁用发送；超长走 textarea 内部滚动；粘贴超长内容时保持 `max-height` |
| **R13** | **无障碍** | 编辑按钮 `aria-label="编辑"`、`title` 提示；元信息行用 `role="toolbar"` + `aria-label="消息操作"`（对齐助手操作栏 L307–310）；编辑卡片 textarea 加 `aria-label="编辑消息"`；打开编辑后 focus 入 textarea |
| **R14** | **触屏** | `@media (hover:none)` 下元信息行常显（已覆盖） |
| **R15** | **pro/task 模式暂不可编辑** | `AgentCompletionBody`（`api/agent.ts` L46–51）没有 `messageId`/截断字段，agent 管线（Plan-Execute 步骤持久化、HITL 暂停、run 记录）截断语义复杂得多。建议**分阶段**：先在 chat 模式开放 `editable`，pro/task 仅显示"时间 + 复制"，待 agent 侧接口扩展后再打开 |
| **R16** | **测试影响面** | 用户分支 DOM 结构变化会影响 `modes/task/components/TaskMessageList.test.tsx`（示例中含 `datetime` 字段）；新增 `UserMessageBubble.test.tsx` 覆盖：悬停显示、编辑进入/取消、空内容禁用、提交回调、时间格式化 |
| **R17** | **产物反向联动失效** | 截断后消息节点消失，`useScrollToMessage` 的 `[data-message-id]` 查不到会静默 `clearHighlight`（该 hook L42–46 已有防御）。若产品要求产物仍可跳转，需要为被截断消息保留隐藏锚点或改为按 id 走"消息不存在"提示 |
