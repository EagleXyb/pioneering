## 二、问题清单与修复方案

### 🔴 F1：`/agent/completions` 返回 501，Pro 模式完全不可用
后端 `agent.ts:158-169` 显式 `return reply.code(501)...`，但前端 `useAgentChat.ts:114` 直接 `fetch('/api/agent/completions')` 并解析 SSE。结果 Pro 模式永远进入 `RUN_ERROR`/异常分支。

**修复（前端兜底）**——在 `useAgentChat.ts` 的 `!response.ok` 分支细化处理：
```ts
if (!response.ok) {
  const errData = await response.json().catch(() => null);
  if (response.status === 501) {
    setStatus('error');
    setMessages((prev) => [...prev, {
      id: `e_${Date.now()}`, role: 'assistant' as const,
      content: [{ type: 'text' as const, data: 'Agent 对话功能待上线（依赖 ModuAgent 框架）' }],
    }]);
    return;
  }
  throw new Error(errData?.message || `请求失败: ${response.status}`);
}
```
> 根因需后端接入 `packages/modu-agent` 并实现该端点（当前为有意未迁移），属前后端均未就绪。

### 🔴 F2：`api/chat.ts` 的 `streamChat` 用 OpenAI 格式解析 AG-UI 流
后端 SSE 发送 `TEXT_MESSAGE_CONTENT`/`THINKING_TEXT_MESSAGE_CONTENT`（字段 `delta`，`chat.ts:496-509`），而 `api/chat.ts:84-95` 却解析 `data.choices?.[0]?.delta?.content`，导致 `onChunk` 永远拿不到文本。该函数虽当前未被业务引用（搜索确认仅自包含），但属于真实格式错位。

**修复**——改为按事件解析（与 `useAgentChat` 对齐）：
```ts
const data: any = JSON.parse(dataStr);
if (data.type === 'TEXT_MESSAGE_CONTENT' || data.type === 'THINKING_TEXT_MESSAGE_CONTENT') {
  if (data.delta) callbacks.onChunk?.(data.delta);
} else if (data.type === 'RUN_FINISHED') {
  callbacks.onDone?.(finalResponse);
}
```
或若该助手仅作遗留代码，直接删除 `api/chat.ts` 及 `ChatCompletionResponse` 中 `choices[].delta` 相关误用，统一走 TDesign `useChat`。

### 🔴 F3：`/user/list` 无任何鉴权，公开泄露用户 PII
`user.ts:10-12` 在 `fastify.register(... { prefix: '/user' })` 内直接 `app.get('/list', ...)`，**未挂载 `authGuard`**，返回全部用户的 `username/email/phone/avatar/status` 及 token 用量。属安全漏洞。

**修复**——加 `preHandler`：
```ts
fastify.register(async (app) => {
  app.addHook('preHandler', authGuard)   // 新增
  app.get('/list', buildSchema({ ... }), async (req) => { /* ... */ })
}, { prefix: '/user' })
```
> 若该接口本意是管理员功能，还应追加角色校验（`user.status`/角色字段）。

### 🟠 F4：`QuotaInfo` 类型字段错位
前端 `api/types.ts:28-34` 定义 `remainingTokens`，后端 `/user/quota` 实际返回 `resetAt`（无 `remainingTokens`）。一旦前端接入配额接口，会读不到字段。

**修复**——以后端为准对齐（前端 `api/types.ts`）：
```ts
export interface QuotaInfo {
  totalTokens: number;
  usedTokens: number;
  dailyLimit: number;
  dailyUsed: number;
  resetAt?: string | null;   // 后端返回
  // remainingTokens 改为前端派生：totalTokens - usedTokens
}
```

### 🟠 F5：重复的 `User` 类型定义 + 可空性冲突
`api/types.ts:17-26` 的 `User` 把 `nickname/avatar` 定义为**必填非空**、`createdAt/updatedAt` 必填；而 `auth.d.ts` 的 `UserProfile` 全部可空。后端实际返回可空。若某处引用了 `api/types.ts` 的 `User`，运行时会因 `null` 崩溃。

**修复**——删除 `api/types.ts` 中的 `User`，统一使用 `UserProfile`（`auth.d.ts`），并将 `getProfileApi` 等用到的类型收敛到 `auth.d.ts`。

### 🟠 F6：`FeedbackRequest` 多了后端不需要的 `messageId`
前端 `api/types.ts:179-182` 定义 `FeedbackRequest { messageId; feedback }`，但后端 `FeedbackRequestSchema` 仅 `{ feedback }`（`messageId` 来自 URL path，非 body）。`message.ts:46` 发送 `{ messageId, feedback }` 虽因 Zod 默认剥离未知键而不报错，但契约不一致。

**修复**：
```ts
// api/types.ts
export interface FeedbackRequest { feedback: FeedbackType }

// api/message.ts feedbackMessage
return post<void>(`/chat/messages/${messageId}/feedback`, { feedback } as FeedbackRequest)
```

### 🟠 F7：`ChatCompletionRequest` 类型缺少 `deepThink/netSearch/messageId`
前端 `api/types.ts:123-132` 无这三个字段，但后端 schema 有，且 `ChatMode.tsx:55-56` 通过 `onRequest` 直接把 `deepThink/netSearch` 塞进原始 body（绕过类型）。`api/chat.ts` 的 `streamChat` 用 `ChatCompletionRequest` 则**不会**带上这两个开关。

**修复**——补全类型（保持单一事实来源）：
```ts
export interface ChatCompletionRequest {
  sessionId?: string;
  message: string;
  model?: string;
  systemPrompt?: string;
  temperature?: number;
  maxTokens?: number;
  stream?: boolean;
  parentMessageId?: string;
  deepThink?: boolean;   // 新增
  netSearch?: boolean;   // 新增
  messageId?: string;    // 新增
}
```

### 🔴 F8（缺失集成）：文件上传 `/upload` 无任何前端封装与入口
后端提供 `POST /upload`（multipart，返回 `{id,url,original_name,file_type,file_size}`）与 `DELETE /upload/:fileId`，但前端 `api/` 下无对应模块，头像/附件上传无法落地，`updateProfile`/`updateSession` 的 `avatar` 字符串无从产生。

**修复**——新增 `apps/web/src/api/upload.ts`：
```ts
import { getToken } from './client'
const BASE = '/api'
export interface UploadResult { id: string; url: string; original_name: string; file_type: string; file_size: number }

export async function uploadFile(file: File): Promise<UploadResult> {
  const form = new FormData()
  form.append('file', file)
  const token = getToken()
  const res = await fetch(`${BASE}/upload`, {
    method: 'POST',
    headers: token ? { Authorization: `Bearer ${token}` } : {},
    body: form,
  })
  const json = await res.json()
  if (!res.ok) throw json
  // 响应被包装为 { code, data, message }
  return (json.data ?? json) as UploadResult
}
export const deleteFile = (fileId: string) => del<void>(`/upload/${fileId}`)
```
随后在个人资料页用 `uploadFile` 取得 `url` 再调 `updateProfile({ avatar: url })`。

### 🟡 F9（缺失集成）：多个端点未消费
`/system/config`、`/user/quota`、`/user/quota/usage`、`/auth/wechat/*`、Agent 工具轨迹/反馈、Agent 消息列表均未消费。这些后端端点目前前端没有任何调用（含 Pro 模式对 `/agent/sessions/:id/messages`、`/agent/messages/:id/executions`、`/agent/messages/:id/feedback` 的依赖）。属于“后端已就绪、前端未接线”，建议按业务优先级补齐。

> 注意 Agent 反馈 body 字段为 `rating:number`+`feedbackText:string`，与 chat 反馈的 `feedback:enum` 命名不同，接线时需分别封装。

### 🟡 F10：`deleteSession` 默认 `archive=true` 实为“归档”而非“删除”
`session.ts:41` `deleteSession(id, archive=true)` → 后端 `chat.ts:209` `archive = query.archive === 'false' ? false : true`，即默认走归档。前端 `Conversation`（`conversationStore.ts:8-16`）**没有 `isArchived` 字段**，无法区分已归档会话，UI 上“删除”实为“隐藏”。

**修复**：
```ts
// conversationStore.ts sessionToConversation 增加
isArchived: s.isArchived ?? false,
// Conversation 接口增加 isArchived: boolean
```
并让删除入口明确区分“归档/彻底删除”（分别传 `archive=true/false`）。

### 🟡 F11：`/auth/profile` 与 `/user/profile` 端点重复
两者返回结构完全相同（`auth.ts:246` 与 `user.ts:80`）。前端只用 `/user/profile`。建议后端保留其一（或前端统一），避免维护双份。

### 🟡 F12：`registerApi` 注释过时
`auth-api.ts:13` 注释“后端待实现，当前为预留接口”，但后端 `auth.ts:73` 已实现 `/auth/register`。属误导性注释，应删除。

### 🟡 F13（待验证）：TDesign `useChat` `protocol:'agui'` 与后端 AG-UI 方言是否完全对齐
后端事件含 `RUN_STARTED`、`TEXT_MESSAGE_START/CONTENT/END`、`THINKING_START`、`THINKING_TEXT_MESSAGE_START/CONTENT/END`、`THINKING_END`、`RUN_FINISHED`、`RUN_ERROR`，增量字段统一为 `delta`。TDesign 的 `agui` 协议需消费同名字段。ChatMode/TaskMode 走该路径，请实机验证思考块（`THINKING_TEXT_MESSAGE_CONTENT`）能正确渲染；若 TDesign 期望 `reasoning_content` 或 `STEP_*` 事件，需在后端的 `streamAgui`（`core/llm.ts`）补充适配。

### 🟡 F14：非流式 `/chat/completions` 响应会被包装器包裹
`chat.ts:447-464` 非流式返回 OpenAI 结构，但 `responseWrapper` 会包成 `{code,data,message}`，而 TDesign `useChat`/自写 `streamChat` 都期望原始响应（且前端永远传 `stream:true`，故当前不触发）。若将来需要非流式，需在 `response-wrapper.ts` 的 `SKIP_PATHS` 增加 `/chat/completions` 或前端做分支解包。

### 低优先级
- **F15**：`getSession`(`GET /chat/sessions/:id`) 仅测试引用，业务未用 → 可删除或接入会话详情页。
- **F16**：后端 `ChatCompletionRequestSchema.messageId` 字段定义但路由未使用 → 清理。

## 四、归档功能实施方案

### 4.1 现状分析

后端已具备完整能力，前端只差 UI 层串联：

| 能力 | 后端状态 | 前端状态 |
|---|---|---|
| 归档会话 | ✅ `DELETE ?archive=true` → 设 `isArchived=true` | ✅ 已修复 |
| 查询归档列表 | ✅ `GET /sessions?archived=true` 过滤已归档 | ❌ 未接入 |
| 恢复归档 | ❌ PUT `/sessions/:id` 的 body 不含 `isArchived` | ❌ 无入口 |

### 4.2 后端：恢复归档能力

**`schemas/chat.ts`** — `UpdateSessionRequestSchema` 新增 `isArchived` 字段：
```ts
export const UpdateSessionRequestSchema = z.object({
  title: z.string().nullable().optional(),
  model: z.string().nullable().optional(),
  modelConfig: z.record(z.unknown()).nullable().optional(),
  isArchived: z.boolean().optional(),  // ← 新增
})
```

**`routes/chat.ts`** — PUT 处理器新增 `isArchived` 写入逻辑（与已有 `title`/`model` 一样处理）：
```ts
if (dto.isArchived != null) data.isArchived = dto.isArchived
```

恢复归档只需：`PUT /sessions/:id { isArchived: false }`，复用现有 PUT 端点。

### 4.3 前端：侧边栏"归档区"

在侧边栏底部（分组标签之后）新增一个 **"已归档"折叠区**：

```
┌─────────────────────────┐
│  今天                   │
│  ├ 会话A                │
│  └ 会话B                │
│                         │
│  ┌─────────────────────┐│
│  │ 📦 已归档 (3)      ▼ ││  ← 点击展开/折叠
│  └─────────────────────┘│
│  ├ 📋 会话C  [恢复][删] ││  ← 归档会话，视觉淡化
│  └ 📋 会话D  [恢复][删] ││
│                         │
│  [+ 新建会话]           │
└─────────────────────────┘
```

**交互逻辑**：

| 操作 | 行为 |
|---|---|
| 点击"已归档"头 | 展开/折叠归档列表 |
| 点击归档会话 | 恢复（unarchive）并跳转到该会话 |
| 点击"[恢复]" | `PUT /sessions/:id { isArchived: false }` → 刷新列表 |
| 点击"[删]" | 物理删除（复用 `remove(id, false)`） |
| 归档当前会话 | 归档后 toast "已归档 [撤销]" |
| 点击 toast "撤销" | 3 秒内调用恢复 API |
