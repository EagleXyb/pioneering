### 🔴 F1：`/agent/completions` 返回 501，Pro 模式完全不可用

后端 `agent.ts:158-169` 显式 `return reply.code(501)...`，但前端 `useAgentChat.ts:114` 直接 `fetch('/api/agent/completions')` 并解析 SSE。结果 Pro 模式永远进入 `RUN_ERROR`/异常分支。

**根因**：需后端接入 `packages/modu-agent` 并实现该端点（当前为有意未迁移），属前后端均未就绪。

**建议的前端兜底方案**——在 `useAgentChat.ts` 的 `!response.ok` 分支细化处理：
```ts
if (!response.ok) {
  const errData = await response.json().catch(() => null);
  if (response.status === 501) {
    setStatus('error');
    setMessages((prev) => [...prev, {
      id: `e_${Date.now()}`, role: 'assistant' as const,
      content: [{ type: 'text' as const, data: 'Agent 对话功能待上线（依赖 ModuAgent 框架）' }],
    }]);
    return;
  }
  throw new Error(errData?.message || `请求失败: ${response.status}`);
}
```

### 🔴 F8（缺失集成）：文件上传 `/upload` 无任何前端封装与入口

后端提供 `POST /upload`（multipart，返回 `{id,url,original_name,file_type,file_size}`）与 `DELETE /upload/:fileId`，但前端 `api/` 下无对应模块，头像/附件上传无法落地，`updateProfile`/`updateSession` 的 `avatar` 字符串无从产生。

**修复方案**——新增 `apps/web/src/api/upload.ts`：
```ts
import { getToken } from './client'
const BASE = '/api'
export interface UploadResult { id: string; url: string; original_name: string; file_type: string; file_size: number }

export async function uploadFile(file: File): Promise<UploadResult> {
  const form = new FormData()
  form.append('file', file)
  const token = getToken()
  const res = await fetch(`${BASE}/upload`, {
    method: 'POST',
    headers: token ? { Authorization: `Bearer ${token}` } : {},
    body: form,
  })
  const json = await res.json()
  if (!res.ok) throw json
  return (json.data ?? json) as UploadResult
}
export const deleteFile = (fileId: string) => del<void>(`/upload/${fileId}`)
```
随后在个人资料页用 `uploadFile` 取得 `url` 再调 `updateProfile({ avatar: url })`。

### 5.2 对标行业产品的缺陷与偏差

#### 严重级（P0）—— 影响数据正确性与核心体验

| # | 缺陷 | 行业做法 | 当前实现 |
|---|---|---|---|
| P0-1 | **停止生成不真正停止** | ChatGPT/千问/豆包：客户端+服务端同时中止，上游 LLM 立即停止计费 | 后端 no-op，上游持续消耗 |
| P0-2 | **重新生成重复写入用户消息** | 重用既有 user 消息，仅生成新 assistant 回复 | 前端走 completions 重发，DB 产生重复 user 消息 |
| P0-3 | **会话列表 total 翻页递减** | total 为绝对总数，翻页不变 | 第 2 页起 total=剩余条数，前端终止判断失真 |
| P0-4 | **流式空回复不持久化但 userMsg 已入库** | 要么回滚 userMsg，要么写入空/错误 assistant | 产生孤儿用户消息 + messageCount 多算 |
| P0-5 | **配额/限流完全缺失** | 千问/豆包：调用前校验配额，超限 429；调用后写 TokenUsage | completions 不校验、不记录用量 |

#### 重要级（P1）—— 影响功能完整性与一致性

| # | 缺陷 | 行业做法 | 当前实现 |
|---|---|---|---|
| P1-1 | **编辑消息无 UI 入口** | ChatGPT/千问/豆包：user 消息支持编辑（铅笔图标），编辑后分支重生成 | 后端已实现，前端完全未接入 |
| P1-2 | **无分支/版本管理** | 编辑/重生成产生分支，UI 可 `< 1/3 >` 切换 | DB 有 parentMessageId/childrenMessageIds 字段但无查询/切换逻辑；childrenMessageIds 从未填充 |
| P1-3 | **netSearch 联网查询为空壳** | 千问/豆包/元宝：联网搜索有引用来源、可点击跳转 | 前端有按钮，后端忽略参数 |
| P1-4 | **删除会话非事务** | 删除原子化 | 消息删除成功后会话删除失败→孤儿 |
| P1-5 | **消息游标无 tie-breaker** | 同会话列表用复合键 | 同毫秒消息跳过/重复 |
| P1-6 | **finishReason/usage 不准确** | 透传上游真实值 | 硬编码 stop、length/4 估算 |
| P1-7 | **详情接口 lastMessage 恒 null** | 与列表一致返回预览 | 硬编码 |

#### 一般级（P2）—— 体验与边界

| # | 缺陷 | 行业做法 | 当前实现 |
|---|---|---|---|
| P2-1 | 标题仅取首条用户消息前 30 字 | 千问/豆包：AI 摘要生成标题 | `useChatSync.ts:29` 截断 |
| P2-2 | 删除当前会话不自动切换 | 自动选中相邻会话 | `activeId=null` |
| P2-3 | 无置顶/搜索会话 | 千问/豆包支持置顶、搜索 | 无 |
| P2-4 | 反馈无理由文本 | DeepSeek 点踩弹理由框 | DB 有字段未用 |
| P2-5 | share 按钮无响应 | 分享链接/图片 | 死按钮 |
| P2-6 | 错误响应被 response-wrapper 二次处理 | 错误直出 | `error-handler` 无 `data` 字段→wrapper 重包，requestId 被覆盖 |
| P2-7 | 权限码与契约不符（404 vs 403） | 区分不存在/无权限 | 统一 404 |
| P2-8 | doRegenerate 按内容匹配父消息 | 按 id 匹配 | `chat.ts:683` |

### 5.3 具体差距与改进方向

#### A. 数据正确性修复（优先级最高）

1. **停止生成真正可中止**
   - 引入服务端 run 注册表（`Map<runId, AbortController>`），completions 创建时注册，`/stop` 通过 `sessionId`/`messageId` 查找并 `abort()`。
   - `streamAgui` 接收外部 `AbortSignal`，传入上游 `fetch`，客户端断开时联动取消上游。
   - 参考 `chat.ts:488` 已生成 `runId`，只需建立映射。

2. **重新生成走专用端点，不复用 completions**
   - 前端 `handleReplay` 改调 `regenerateMessage`（已存在），传被重生的 assistant messageId。
   - 后端 doRegenerate 改为流式（复用 streamAgui），并按 id（非内容）定位父消息：buildMessageContext 返回 `{role,content,id}`。
   - 重生不写新 user 消息，仅写新 assistant，`parentMessageId` 指向既有 user 消息。

3. **会话列表 total 修正**
   - `chat.ts:82`：count 的 `where` 去掉游标 `OR` 条件，仅保留 `userId`+`isArchived`，返回绝对总数。

4. **流式空回复回滚**
   - 流式结束时若 `!fullContent && !fullReasoning`，删除已写入的 userMsg 并回滚 messageCount，或写入 status=error 的 assistant 占位。

5. **配额校验与用量记录**
   - completions 入口查 `UserQuota`（dailyUsed/usedTokens），超限抛 429/403。
   - 完成后写 `TokenUsage`（用上游真实 usage，非 length/4），并 `increment` usedTokens/dailyUsed。

6. **删除走事务**
   - `prisma.$transaction([deleteMessages, deleteSession])`。

7. **消息游标加 tie-breaker**
   - 仿会话列表：`orderBy: [{createdAt:'desc'},{id:'desc'}]`，cursor 条件用 `(createdAt,id)` 复合比较。

#### B. 功能完整性补齐

8. **编辑消息 UI 接入 + 分支模型**
   - ChatMessageItem actionBar 增加 `edit`（仅 user 消息）。
   - 编辑后调 `editMessage(regenerate:true)`，后端用 `parentMessageId` 建立分支。
   - 消息列表查询补 `childrenMessageIds`（后端按 parentMessageId 反查填充），UI 渲染 `< 1/N >` 切换器，切换时按 `childrenMessageIds` 加载对应分支。

9. **联网搜索落地或移除按钮**
   - 短期：若未实现，移除前端"联网查询"按钮避免误导。
   - 中期：接入搜索 API，结果作为 tool 消息或 metadata 引用来源，UI 渲染可点击引用。

10. **finishReason/usage 透传**
    - 非流式：直接取 `resultData.choices[0].finish_reason` 与 `resultData.usage`。
    - 流式：聚合最后一个 chunk 的 usage（DeepSeek/OpenAI 流式末块带 usage）。

#### C. 体验对齐

11. **标题 AI 摘要**：首轮对话后异步调一次小模型生成标题，替换 `updateTitle` 截断逻辑。
12. **删除后自动选中相邻会话**：`remove` 成功后取 `conversations[0]` 或相邻项 activate。
13. **会话置顶/搜索**：DB 加 `pinnedAt` 字段，列表排序前置；前端加搜索框按 title 过滤。
14. **反馈理由**：点踩弹 textarea，写入 `userFeedback`；FeedbackRequest schema 扩展可选 `reason`。
15. **share 实现**：生成分享链接或导出图片，移除死按钮。
16. **错误响应直出**：error-handler 的错误体加 `data:null` 或让 wrapper 跳过已有 `code` 的对象，避免 requestId 丢失。

#### D. 契约对齐

17. **删除 archive 参数位置**：统一为 query 或 body，与契约一致。
18. **状态码**：创建 201、删除 204，对齐契约。
19. **权限码**：非 owner 返回 403，不存在返回 404，对齐契约。
20. **详情 lastMessage**：与列表一致返回真实预览。

### 5.4 总结矩阵

| 端点 | 前后端一致 | 主要问题 |
|---|---|---|
| 会话列表 | ⚠️ | total 翻页递减、N+1 |
| 创建会话 | ⚠️ | initialMessage 丢失、状态码 |
| 会话详情 | ❌ | lastMessage 恒 null、前端未用 |
| 更新会话 | ✅ | 无模型校验 |
| 删除/归档 | ⚠️ | 非事务、参数位置/状态码不符契约 |
| 消息列表 | ⚠️ | 游标缺 tie-breaker |
| 编辑消息 | ❌ | **前端无 UI、后端无分支** |
| 对话补全 | ⚠️ | netSearch 死参、空回复孤儿、无配额、停止不联动 |
| 停止生成 | ❌ | **后端纯 no-op** |
| 消息反馈 | ⚠️ | id 一致性风险、无理由 |
| 重新生成 | ❌ | **前端未调接口→重复 user 消息** |

**核心结论**：会话级 CRUD 与消息分页基础链路可用，但围绕"生成控制"的三件套（停止/编辑/重新生成）存在系统性缺陷——停止不停止、编辑无入口、重新生成重复写消息。这三项与千问/豆包/DeepSeek 的差距最大，应作为首要修复目标。配额/用量链路完全空转，是上线前的阻塞项。
