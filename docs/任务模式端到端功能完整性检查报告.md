## 六、工程层面不达标的详细说明

**判定口径**：本次任务产出确实达标（文档 15193 字 / 91 标题 / 严格四段式；正文 56156 字完整落库），但这是"LLM 恰好在第 1 步把整件事做完"的偶然结果，**不是机制保证的结果**。以下按证据展开六个维度。

### 6.1 计划-执行一致性（最严重）

**现象（实测）**：planner 拆出 7 步，但 LLM 在 step_1（职责="构建整体知识框架与输出结构"）内直接调 `doc_writer` 产出完整终稿并写盘；`step_2~6` 从未执行；DB 中 `step_1=running`、`step_2~6=pending`；`step_finalize` 全程未运行。

**设计缺口（三层）**

1. **步骤边界只是"一句建议"**：`context.ts:46-69` 注入的是一条 SystemMessage（`Current step 1/7: …` + 前序摘要 + "不要复述"）。没有任何机制判断"LLM 是否越权完成了后续步骤的活"，也没有任何机制把越权行为反馈回计划。
2. **验收标准被定义但从未使用**：planner 被强制要求为每步产出 `expected_output` 与 `verification_hint`（`prompt-templates.ts:58-59`、`types.ts:50-56`、`planner.ts:434-439` 解析透传），全仓搜索**无任何消费点**。"每步产出什么、怎么验证"的协议设计了一半——规划器认真填了，执行器完全不看。
3. **计划与执行的偏差没有闭环**：没有任何节点比对"本步实际产出 vs 本步职责"。

**后果**：步骤切得越细，浪费越大；对"必须分步产出、逐步校验"的任务形态（多来源调研、写代码并自测、长报告分章校验）会直接失效——第一次"顺手做完"就结束了整个计划。

### 6.2 收敛与终止语义

**现象（实测）**：最后一次 AIMessage 带 `datetime` 工具调用但无 `TOOL_CALL_RESULT`，正文结束即 `RUN_FINISHED`——说明走了 `force_finalize`（`nodes.ts:731-763`）→ `graph.ts:754` 直连 `finalize_response`，**绕过 step_finalize**。

**缺口 A：预算触顶被当作"整轮结束"而非"当前步结束"**。`force_finalize` 的设计语义是"禁用工具再答一次"，在 ReAct 模式合理；在 plan_execute 模式它把"这一步工具用多了"升级成"整个计划结束"。

**缺口 B：轮次计数器全 run 累加且无重置**。`state.ts:353-356` 是累加 reducer，`reasoning_round_count` 由 agentNode 累加（`nodes.ts:1350`），**全仓没有任何重置点**。修复 P0-2 时若不同时重置它，会出现"后续每一步一进 agent 就触顶"的新问题。

**后果**：长任务系统性丢掉后半段；即便"单步偶尔超轮次"的偶发场景，也会把整份 7 步计划一次性作废，且用户看不到任何原因（既不是错误，也没有警告文案）。

### 6.3 产物传递与汇总（"多步推理是否被正确合并"的失分点）

**现象（代码确认，本次侥幸未暴露）**

- 步骤产物在写入时即被截断：`dispatcher.ts:444-446` 取 `step_summary_max_chars`（`runtime-config.ts:121` 默认 500，`config.yaml` 未覆盖），`:621` `output: _truncate(lastAiContent, 500)`，`:670` 下发的 `step_update.result` 也是这份截断值 → 前端步骤面板（`PlanPipelineTree.tsx:193-195`）与 DB `plan_steps.result` 都只有 500 字。
- 后续步骤能看到的前序信息也只有这 500 字摘要（`context.ts:53-64`）。
- 最终答复取"最后一条无 `tool_calls` 的 AIMessage"（`nodes.ts:1782-1807`），**不读 `step_results`**；兜底合成 `_buildFallbackResponse:1725-1766` 也只读 `artifacts` / `tool_results`。
- 重规划时 `planner.ts:781` 返回 `step_results: []`，把已固化步骤的产物直接清空（只靠 `plan` 的 title/description 续命）。

**后果**：本次内容完整是因为 LLM 在 step_1 就把全文吐进了正文。一旦 LLM 老实按步骤执行，最终答复就是"最后一步的一句话"，中间 5 步产物全部消失——这与用户诉求（"整体结构清晰、层次分明、便于对照理解"）最直接冲突。

### 6.4 交互与审批（HITL）

**现象（实测）**：`doc_writer` 写操作恒需审批（`doc-writer.ts:141-156`，`create/append` 返回 true）→ 15:20:17 暂停①；批准后文档落盘、LLM 又调一次 `doc_writer`（不同标题）→ 15:25:15 暂停②；再批准才结束。全程用户需两次手动确认。

**缺口**

1. **doc-gen 防护在 plan_execute 下失效**：防重复写文档的守卫（`nodes.ts:686-725`）以 `state.task_type === 'document_generation'` 为前提，而 `task_type` 只由 perception 按**用户原文关键词**判定（`nodes.ts:161-176` 的"动作词 + 目标词 / 紧耦合短语"）。本次用户原文没有"文档/报告"等词 → `task_type=null` → 守卫完全不生效 → 计划内的写文档步骤被当成"任意写盘请求"反复审批。
2. **审批与"谁提出的写操作"解耦**：用户已批准整份计划，计划内的 `doc_writer` 本质是计划产物，却按敏感写操作逐次审批。
3. **超时即失败**：`config.yaml:35-39` 的 `approval_timeout_seconds: 300` + `auto_reject_on_timeout: true` 意味着**无人值守必然在 5 分钟后被拒**，且失败原因（"审批超时"）在任务面板上不可见。

**后果**：复杂文档类任务在第一步就"卡住等人"；用户离开或忘记处理 → 自动拒绝 → 步骤 failed → 触发 replan → 大概率连环失败。用户视角是"任务莫名其妙失败"。

### 6.5 状态与协议一致性

**现象（实测）**：后端落库 `metadata.plan_phase='done'`，而 `plan_steps` 是 `running + pending×5`；前端实时终态 `resolveTerminalPhase`（`usePlanExecuteChat.ts:61-69`）判定为 `incomplete` → badge「未完成」；刷新后 `hydrateFromHistory`（`planExecuteStore.ts:222`）无条件采用 `snapshot.phase='done'` → badge「已完成」而进度区显示「已完成 0/7 步」。

**缺口**：终态判定在前端（按 store 内步骤状态）与后端（`routes/agent.ts:175-181`，只看 `hasError/paused`，不看步骤）各实现一套、依据完全不同；历史恢复又无条件信任后端 metadata。此外 `routes/agent.ts:281-298` 落库从不写 `duration_ms`，而 `GET /plan`（`:1084`）却在读它。

**后果**：同一任务在"实时/刷新"两种视图下结论相反；进度数字与实际产出长期不符。这会持续训练用户不信任任务面板——而面板正是"复杂任务是否被正确拆解"的唯一可视证据。

### 6.6 健壮性与可观测性

- **硬崩溃**：`retrying` 状态（`dispatcher.ts:598` 经 `event-bridge.ts:461-465` 原样透传）使 `STATUS_CONFIG` 查表落空 → `PlanPipelineTree.tsx:135` `config.className` TypeError → 整个右栏面板崩溃。当前 `step_retry.default_max_attempts=0` 使其条件触发，但 planner schema 允许 `max_attempts` 1~5，一旦模型给出重试策略就会踩中。
- **定时炸弹**：`Send('step_dispatch', …)` 目标节点只收到 payload、拿不到 `plan`（`algo.cjs:398-401` `input: packet.args`）；最小复现图实测：路由被反复调用 4095 次直至 recursion limit。当前因"激活分支短路 + 游标线性推进"不可达，但任何让游标错位的改动都会引爆。同时 `depends_on` 的 DAG 校验在顺序模型下**从不生效**（`dispatcher.ts:219-242` 先于 `:245`），依赖数组形同虚设。
- **计量失效**：`agent-bridge.ts:58-59` 的 `promptTokens/completionTokens` 声明后无赋值点，run usage 恒 0；非流式分支不记账；429 发生在用户消息落库之后（`routes/agent.ts:453-468` vs `:477`），留下孤儿消息。
- **异常静默**：planner 解析/调用异常被 catch 后仅打日志（`planner.ts:718-732`）并降级为无计划直答，用户看不到"规划失败"；`stalled` 直接整单抛错（`dispatcher.ts:271`），没有"部分完成 + 说明卡点"的降级；落库/收尾/记账异常全部 `log.error` 吞掉。

**后果**：一旦线上出问题（内容缺失、步骤卡住、面板空白），**无法归因**——没有真实 usage、没有节点级耗时、没有"哪一步为什么被判失败"的可见原因，只有散落在 6.5MB 日志里的 warning。

### 8.7 如何手工复现端到端验证（无需脚本）

三个只在真实链路下暴露的缺陷（`duration_ms` 生成列、resume 清空步骤产物、孤儿 `tool_calls`）单测无法覆盖，故保留可复现步骤：

1. 启动后端：`cd apps/backend-ts && npm run dev`（需 `.env` 中 LLM Key 有效）
2. 提交复杂任务（本文档开头那段 Prompt 工程任务），`agentMode=plan_execute`
3. 观察 SSE 事件流应依次出现：`STATE_DELTA(phase=plan)` → 每步 `running`/`done` → `USER_QUESTION_REQUEST`（doc_writer 审批，**应仅 1 次**）→ 批准后 `RUN_FINISHED`
4. 校验落库：
   - `plan_steps` 各步 `result` 为**完整产物**（非 500 字符截断），`duration_ms` 有值
   - `chat_messages.metadata.plan_phase` 与步骤实际状态一致（有 running/pending 则为 `incomplete`）
5. 刷新页面：任务面板步骤数、状态、徽章与落库一致，无步骤长期停在 `running`

关键观察点：文档类任务只应触发 **1 次** 写文档审批；恢复后不应出现 `400 tool_calls` 报错。
