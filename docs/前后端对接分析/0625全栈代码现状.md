## 1. 模块功能与职责划分

### 1.1 全栈模块总览

| 层级 | 模块 | 技术栈 | 核心职责 |
|------|------|--------|----------|
| **前端** | `apps/web` | React 18 + TS + Vite 6 + react-router 7 + Zustand 5 + TDesign React + @tdesign-react/chat | 用户交互、SSE 流式对话、Agent 推理可视化、认证、会话管理 |
| **后端 API** | `apps/backend/app` | FastAPI + SQLAlchemy 2 async + asyncpg + httpx + sse-starlette | REST API、认证鉴权、会话/消息 CRUD、LLM 直连调用、Agent 桥接、响应包装 |
| **Agent 框架** | `apps/backend/ModuAgent` | 纯 Python（自研，非 LangGraph/LangChain） | 感知→记忆→推理→行动→反馈 编排、组件注册中心、AG-UI 事件适配、LangGraph 重构层 |

**关键职责矩阵**：

| 模块 | 核心职责 | 关键实现 |
|------|---------|----------|
| `main.py` ResponseInterceptor | 统一响应包装 | 对所有非 SSE 响应包装为 `{code, data, message}`，SSE 流式跳过，保留原始 CORS 头 |
| `api/v1/chat.py` | 普通对话补全 | `chat_completion` 支持流式（`llm_service.stream_agui`）和非流式，流式后异步持久化 assistant 消息 |
| `api/v1/agent.py` | Agent 对话补全 | `agent_completion` 通过 `agent_bridge.stream_agent_completion` 调用 ModuAgent Coordinator，StreamContext 收集元数据后持久化 |
| `core/agent_bridge.py` | Agent 桥接层 | `_init_moduagent()` 注册组件到 ComponentRegistry（单次），`stream_agent_completion` 通过 AGUIStreamAdapter 转换事件，`_collect_metadata_from_event` 提取元数据 |
| `core/llm.py` | LLM 直连服务 | `LlmService` 用 `httpx.AsyncClient`（异步）调用 OpenAI 兼容 API，`stream_agui` 产出 AG-UI 事件流（含 reasoning_content 支持） |

**数据模型（9 个表）**：

| 模型 | 关键字段 | 说明 |
|------|----------|------|
| `User` | username(唯一), password_hash, wechat_openid/unionid, status | 用户基础信息 |
| `RefreshToken` | token(唯一), expires_at, revoked, device_info | 刷新令牌（旋转机制） |
| `ChatSession` | user_id, title, model, **agent_mode**, message_count, last_message_id, is_archived | 会话（多 `agent_mode` 字段） |
| `ChatMessage` | session_id, parent_message_id(自引用), role, content, content_blocks(JSON), prompt_tokens/completion_tokens/latency_ms, user_rating/user_feedback | 消息（含可观测性 + 反馈字段） |
| `AgentToolExecution` | message_id, tool_name, input_params(JSON), output_result, status, duration_ms | **Python 独有**：工具执行轨迹 |
| `File` / `TokenUsage` / `UserQuota` / `AiConfig` | — | 文件/Token 用量/配额/AI 配置 |

### 1.4 ModuAgent 框架模块职责（`apps/backend/ModuAgent`）

采用**分层模块化**架构，8 个顶层包：

| 包名 | 职责 | 核心文件数 | 关键类/函数 |
|------|------|-----------|------------|
| `core/` | 核心架构层：抽象接口 + 组件注册中心 | 7 | `ComponentRegistry`, `BasePerception`, `BaseReasoningEngine`, `BaseMemory`, `BaseActionExecutor`, `BaseTool` |
| `components/` | 独立组件实现：感知/推理/记忆/行动 | 28 | `TextPreprocessor`(862行), `BaseLLMReasoner`, `ChromaLongTermMemory`, `InMemoryShortTermMemory`, `CalculatorTool`, `SearchTool` |
| `adapters/` | 标准化适配层：统一 LLM/工具/存储调用 | 3 | `LLMAdapter`, `ToolAdapter`, `StorageAdapter` |
| `orchestration/` | 编排层：主编排器 + 事件总线 + AG-UI 适配 | 9 | `Coordinator`(1048行), `EventBus`, `AGUIStreamAdapter`, `SSEEncoder`, `StreamPublisher` |
| `langgraph/` | LangGraph 重构层：图编排替代手写循环 | 11 | `build_modu_graph`, `create_agent`, `ModuAgentState`, `run_sync`, `stream_response` |
| `config/` | 配置管理：运行时配置 + 数据校验 schema | 2 | `RuntimeConfig`, `PerceptionInputSchema`, `ToolCallSchema` |
| `feedback/` | 反馈驱动：质量评估 + 进化信号收集 | 6 | `FeedbackLoop`, `QualityMonitor`, `EvolutionSignalCollector`, `AccuracyMetrics` |
| `evolution/` | 持续进化：参数调优 + 组件热替换 + 回滚 | 5 | `ParameterTuneStrategy`, `ComponentSwapStrategy`, `VersionedComponentStore`, `RollbackMechanism` |

**关键组件详解**：

- **`Coordinator`（`orchestration/coordinator.py`，1048 行）**：系统核心"上帝类"，承担请求全生命周期编排（感知→记忆→推理→工具→响应）、ReAct 循环（max 3 次迭代）、工具调用正则解析、事件发布、流式 SSE 输出、传感器管理。`process_request`（同步非流式）与 `stream_request`（流式 SSE）存在大量重复逻辑。
- **`BaseLLMReasoner`（`components/reasoning/llm/base_llm.py`）**：LLM 推理基类，封装 OpenAI 兼容 API 调用，`reason()` 非流式 + `stream()` 流式（同步 Generator），支持原生 function calling。
- **`TextPreprocessor`（`components/perception/text/rule_based.py`，862 行）**：最复杂单组件，实现文本解码/智能截断/清洗/语种检测/敏感词分级(0-5级)/安全检测/质量评估/加权置信度计算。
- **`AGUIStreamAdapter`（`orchestration/communication/agui_adapter.py`）**：将 Coordinator 内部事件（PERCEPTION/MEMORY/REASONING/TOOL/ACTION）映射为 AG-UI 标准事件（`RUN_STARTED` → `THINKING_*` → `TOOL_CALL_*` → `TEXT_MESSAGE_*` → `RUN_FINISHED`）。

### 2.4 ModuAgent 双轨引擎架构

系统支持 **legacy（Coordinator）** 和 **langgraph（重构版）** 两种引擎：

```
                    ┌─────────────────────────────────┐
                    │     get_runner(engine)           │
                    │     runner.py                    │
                    └────────┬───────────┬────────────┘
                             │           │
              engine=legacy  │           │  engine=langgraph
                    ┌────────▼────┐  ┌───▼──────────────────┐
                    │ Coordinator │  │ create_agent()        │
                    │ (手写循环)  │  │ → build_modu_graph()  │
                    │  1048 行    │  │ → CompiledGraph       │
                    └────────┬────┘  └───┬──────────────────┘
                             │           │
                    ┌────────▼───────────▼────────────────┐
                    │   process_request_compat()          │
                    │   stream_request_compat()           │
                    │   (统一接口，按 runner 类型分发)    │
                    └────────────────────────────────────┘
```

**当前状态**：`agent_bridge.py` 直接使用 `Coordinator`（legacy），未接入 langgraph 层。

### 2.5 AG-UI 事件流架构

```
Coordinator.stream_request()
    │
    ├── 发布内部事件 (5 域):
    │   PERCEPTION.ANALYZE / MEMORY.QUERY / REASONING.GENERATE
    │   TOOL.INVOKE / TOOL.EXECUTE / ACTION.EXECUTE
    │
    ▼
AGUIStreamAdapter.transform_streaming_events()
    │
    ├── 映射为 AG-UI 标准事件:
    │   RUN_STARTED
    │   ├── THINKING_START / THINKING_TEXT_MESSAGE_CONTENT / THINKING_END
    │   ├── TOOL_CALL_START / TOOL_CALL_ARGS / TOOL_CALL_END / TOOL_CALL_RESULT
    │   ├── TEXT_MESSAGE_START / TEXT_MESSAGE_CONTENT / TEXT_MESSAGE_END
    │   └── RUN_FINISHED / RUN_ERROR
    │
    ▼
sse-starlette EventSourceResponse
    │
    ▼
前端 useAgentChat SSE 状态机解析
    ├── stateMap[step_N] = {type, label, status, content}
    ├── messages[last].content 增量更新
    └── status: pending → streaming → complete | error
```

### 2.6 架构设计要点说明

1. **前后端通信**：Vite dev proxy 将 `/api` 转发至 `http://localhost:3000`（后端 FastAPI），生产环境需同源部署或 Nginx 反代。注意 proxy rewrite 会移除 `/api` 前缀。
2. **响应包装**：后端 `ResponseInterceptor` 中间件对所有非 SSE 响应统一包装为 `{code, data, message}`，前端 `client.ts` 自动解包。SSE 流式响应跳过包装。
3. **双对话路径**：`/chat/completions` 直连 LLM（`LlmService`，无 Agent 编排）；`/agent/completions` 经 ModuAgent Coordinator（ReAct 循环 + 工具调用）。两者均输出 AG-UI 事件。
4. **组件注册中心**：`ComponentRegistry` 全局单例，10 个分类字典存储组件，支持运行时热替换（`swap_component`），供进化机制使用。
5. **状态分层**：前端全局状态用 Zustand（会话/认证/应用），UI 局部状态用 React Context（主题/Toast）；后端无状态，依赖 DB 持久化。

## 4. 潜在问题排查与优化建议

### 4.1 并发问题

#### 4.1.1 【P0 高风险】Coordinator.process_request 同步阻塞事件循环

**位置**：`ModuAgent/orchestration/coordinator.py:233`

**问题**：`process_request` 是 `async` 方法，但 LLM 生成 `self._llm_adapter.generate()` 是**同步调用**（底层 `BaseLLMReasoner` 使用 `httpx.Client` 同步客户端），会阻塞整个事件循环。对比 `stream_request` 中第 542 行使用了 `await asyncio.to_thread()` 包装，`process_request` 未做此处理。

工具调用 `invoke_tool()`（第 298 行）同样是同步调用，在 async 上下文中阻塞。

**影响**：Agent 非流式请求期间，整个 FastAPI 服务无法处理其他请求。

**建议**：
```python
# 将同步调用包装为异步
response = await asyncio.to_thread(self._llm_adapter.generate, ...)
tool_result = await asyncio.to_thread(self._tool_adapter.invoke_tool, ...)
```

#### 4.1.2 【P0 高风险】ComponentRegistry 无线程安全保护

**位置**：`ModuAgent/core/registry.py` 全文

**问题**：`ComponentRegistry` 的所有注册/查询/替换操作（`register_*` / `get_*` / `swap_component`）均**无锁保护**。进化机制（`ComponentSwapStrategy` / `RollbackMechanism`）会触发 `swap_component`，若在高并发请求期间执行热替换，可能导致：
- 字典在迭代时被修改（`list_tools` 遍历 `_tools` 时 `swap_component` 修改字典）
- 读写竞争导致获取到半初始化的组件

**建议**：增加 `threading.RLock` 保护所有读写操作。

#### 4.1.3 【P1 中风险】InMemoryShortTermMemory 无并发保护

**位置**：`ModuAgent/components/memory/cache/redis_adapter.py`

**问题**：`_store: Dict[str, List]` 的 `query`/`update`/`_evict_expired` 操作无锁。在 `Coordinator` 中记忆更新通过 `asyncio.create_task(asyncio.to_thread(self._storage_adapter.update_all, ...))` 在**线程池**中执行，而查询在主协程中执行，存在真正的线程竞争。

**建议**：增加 `threading.Lock` 保护 `_store` 的读写。

#### 4.1.4 【P1 中风险】Chat 模式发送时序竞态

**位置**：`apps/web/src/modes/chat/ChatMode.tsx:74-80`

**问题**：`create('chat')` 是异步操作，`activeId` 在网络请求返回后才设置。`chatEngine.sendUserMessage` 在 `await` 后执行时，`onRequest` 回调读取的 `activeId` 可能为旧值或 null。

```typescript
const handleSend = async (text: string) => {
  if (!activeId) {
    await create('chat');   // 异步创建会话
  }
  chatEngine.sendUserMessage({ prompt: text });  // activeId 可能尚未更新
};
```

**建议**：`create` 返回 `session.id`，显式使用返回值。

#### 4.1.5 【P1 中风险】会话切换时旧 SSE 流未中止

**位置**：`ChatMode.tsx:26-42` + `ProMode.tsx`

**问题**：切换会话（`activeId` 变化）时，`useEffect` 重新加载历史消息，但未中止正在进行的 SSE 流。上一个会话的流式响应增量会写入新的 `messages` 状态，导致消息串台。

**建议**：在 `useEffect` 清理函数中调用 `chatEngine.abortChat()` 或 `abort()`。

#### 4.1.6 【P1 中风险】fire-and-forget 记忆更新任务无追踪

**位置**：`ModuAgent/orchestration/coordinator.py:387-392`

**问题**：记忆更新通过 `asyncio.create_task(asyncio.to_thread(...))` 异步执行，但**未保留 Task 引用**，可能导致：
- 任务被 GC 回收
- 任务异常静默丢失
- 应用关闭时任务被取消而无感知

**建议**：维护 `Set[asyncio.Task]` 集合，`add_done_callback` 自动清理。

#### 4.1.7 【P2 低风险】EventBus 订阅列表修改非线程安全

**位置**：`ModuAgent/orchestration/communication/message_bus.py:46-69`

**问题**：`subscribe()` / `unsubscribe()` 对订阅列表的修改无锁保护。asyncio 单线程模型下理论安全，但 `await handler(event)` 是切换点，若在 `await` 后调用 `unsubscribe` 有风险。

**建议**：使用 `asyncio.Lock` 或不可变列表替换模式。

### 4.2 异常处理问题

#### 4.2.1 【P0 高风险】SSE 流持久化不可靠——客户端断开时消息丢失

**位置**：`apps/backend/app/api/v1/agent.py:218-267` + `chat.py:426-473`

**问题**：SSE 流的 DB 持久化逻辑写在 `event_generator()` 的 yield 循环**之后**。客户端中途断开时，异步生成器被 GC 回收，后续持久化代码**可能不执行**，导致 assistant 回复丢失。

```python
async def event_generator():
    ctx = StreamContext()
    async for event_dict in stream_agent_completion(...):
        yield event_dict          # ← 客户端断开时此处抛异常
        _collect_metadata_from_event(event_dict, ctx)
    # ↓ 以下代码可能不执行
    assistant_msg = ChatMessage(content=ctx.answer_content, ...)
    db.add(assistant_msg)
    await db.commit()
```

**建议**：使用 `try/finally` 确保持久化执行，或引入后台任务队列异步持久化。

#### 4.2.2 【P0 高风险】Coordinator 异常处理不一致

**位置**：`ModuAgent/orchestration/coordinator.py` 多处

**问题**：
1. **硬编码错误码**：第 193 行 `"error_code": "INPUT_001"` 使用硬编码字符串，而其他地方使用 `ErrorCode` 常量，且无 `INPUT_001` 定义。
2. **LLM 异常泄露敏感信息**：第 244 行 `"message": str(e)`，可能泄露 API key、内部 URL。
3. **ReAct 循环中 LLM 失败静默 break**：第 368-370 行，迭代中 LLM 失败仅 log 后 break，不设置 error_code，最终返回空 response 但 status=success。

**建议**：统一使用 `ErrorCode` 常量；LLM 异常脱敏后返回；ReAct 循环失败时设置 error_code。

#### 4.2.3 【P0 高风险】SSE 流解析未处理连接中断

**位置**：`apps/web/src/api/chat.ts:66-100` + `modes/pro/hooks/useAgentChat.ts`

**问题**：网络中断导致 `reader.read()` 抛异常时，`streamChat` 的 `.catch` 调用 `onError`，但 `useAgentChat` 中只在 `try/catch` 处理。流传输中断开时用户可能看到不完整消息且无错误提示。

**建议**：统一错误处理策略，UI 层展示网络中断提示并提供重试按钮。

#### 4.2.4 【P1 中风险】ToolAdapter 错误码误用

**位置**：`ModuAgent/adapters/tool_adapter.py:54-60`

**问题**：工具调用的一般异常被映射为 `ErrorCode.TOOL_SERVICE_TIMEOUT`（超时错误码），但实际可能是参数错误、网络错误等，错误码语义不匹配。

**建议**：新增 `TOOL_EXECUTION_ERROR` 错误码区分超时与一般异常。

#### 4.2.5 【P1 中风险】401 Token 过期无自动刷新

**位置**：`apps/web/src/api/client.ts:62-66`

**问题**：Token 过期后直接清除并抛错，用户正在编辑的内容丢失。`refreshTokenApi` 已定义但从未被调用。后端 `/auth/refresh` 已实现刷新机制。

**建议**：实现 Token 刷新拦截器——401 时尝试用 `refreshToken` 调用 `/auth/refresh`，成功后重放原请求。

#### 4.2.6 【P1 中风险】useChatSync 标题更新竞态

**位置**：所有 `useChatSync.ts`

**问题**：`doneRef` 确保标题只更新一次，但切换会话时 `conversationId` 变化而 `doneRef` 不重置。会话 A 发消息后（doneRef=true），切到会话 B，B 的标题不会被更新。

**建议**：在 `useEffect` 中监听 `conversationId` 变化时重置 `doneRef.current = false`。

#### 4.2.7 【P2 低风险】EfficiencyMetrics 字段名不匹配

**位置**：`ModuAgent/feedback/metrics/efficiency.py:22-23`

**问题**：读取 `usage.get("input_tokens")` 和 `output_tokens`，但 `BaseLLMReasoner.reason()` 返回的 usage 键名是 `"prompt_tokens"` 和 `"completion_tokens"`，导致效率指标始终为 0。

**建议**：统一 usage 字段命名或兼容两种键名。

### 4.3 安全漏洞

#### 4.3.1 【P0 高风险】XSS 风险：Markdown 内容未消毒

**位置**：`apps/web/src/api/converter.ts:34-38` + `ChatMessageItem.tsx` + `AnalysisMessageList.tsx`

**问题**：assistant 消息内容以 `type: 'markdown'` 传递给 TDesign ChatMessage 渲染。若后端返回的 content 包含恶意 `<script>` 或 `javascript:` 链接，且 TDesign markdown 渲染未做严格消毒，存在 XSS 风险。

**建议**：
1. 确认 TDesign Chat 组件内部是否使用 DOMPurify。
2. 在 `converter.ts` 中对 content 做预过滤。
3. 后端做输出编码。

#### 4.3.2 【P0 高风险】API Key 可能通过异常信息泄露

**位置**：`ModuAgent/components/reasoning/llm/base_llm.py`、`apps/backend/app/core/llm.py`

**问题**：
- `BaseLLMReasoner` 的 HTTP 请求异常（`httpx.HTTPStatusError`）的 `str(e)` 可能包含请求头中的 `Authorization: Bearer <key>`。
- `llm.py:141` 的 `stream_agui` 异常处理 `yield str(e)` 直接输出到前端。
- `agent_bridge.py:164` 的 `ctx.error_info = {"message": str(e)}` 记录原始异常。

**建议**：异常处理中对 HTTP 错误信息脱敏（移除 headers 信息）。

#### 4.3.3 【P1 中风险】JWT Secret 硬编码默认值

**位置**：`apps/backend/app/config.py:7`

**问题**：`jwt_secret: str = "default-secret-change-in-production"`，若未通过环境变量覆盖，使用弱密钥签发 JWT，可被暴力破解或直接伪造。

**建议**：启动时检查 `jwt_secret` 是否为默认值，若是则拒绝启动或强制警告。

#### 4.3.4 【P1 中风险】CalculatorTool 使用 eval

**位置**：`ModuAgent/components/action/tools/calculator.py:84-86`

**问题**：虽做了字符白名单过滤（`0-9+-*/(). `），但 `eval(compiled, {"__builtins__": {}}, {})` 仍是风险点：
- 超长表达式导致栈溢出（如 `(((((((...))))))`）
- 特定 Python 版本的 eval 沙箱逃逸漏洞

**建议**：使用 `ast.literal_eval` 或自实现表达式解析器，彻底移除 `eval`。

#### 4.3.5 【P1 中风险】SecurityGuard 注入检测可被绕过

**位置**：`ModuAgent/components/perception/security/guard.py:25-42`

**问题**：Prompt Injection 检测基于正则模式匹配，存在绕过风险：
- Unicode 同形字攻击（全角字符替代 ASCII）
- 编码混淆（Base64 / HTML 实体）
- 多语言绕过（非中英文越狱指令）
- 间接注入（通过工具返回内容注入）

**建议**：增加 Unicode 同形字检测；考虑集成 LLM Guard 库；对工具返回内容也做注入检测。

#### 4.3.6 【P1 中风险】PII 脱敏不彻底

**位置**：`ModuAgent/components/perception/security/guard.py:107-118`

**问题**：`detect_pii` 返回的 `matches` 仅保留前 3 位 + `***`，但**原始文本中的 PII 未被脱敏**，仍会进入 LLM 上下文。检测是"标记"而非"清洗"。

**建议**：提供 `mask_pii(text)` 方法，检测到 PII 时对原文掩码替换后再传递给 LLM。

#### 4.3.7 【P1 中风险】Token 存储于 localStorage

**位置**：`apps/web/src/api/client.ts:9-25`

**问题**：JWT Token 存储在 `localStorage`，可被 XSS 攻击读取。

**建议**：考虑改为 `HttpOnly Cookie`（需后端配合 CORS + credentials）。

#### 4.3.8 【P1 中风险】路由守卫仅检查 Token 存在性

**位置**：`apps/web/src/stores/auth.ts:47-52` + `ProtectedRoute.tsx`

**问题**：`init()` 仅检查 `localStorage.getItem('token')` 是否存在，不验证 Token 有效性（过期时间、签名）。过期 Token 也会通过守卫，直到 API 返回 401 才清除。

**建议**：`init()` 中解码 JWT 检查 `exp` 字段，过期则主动清除。

#### 4.3.9 【P1 中风险】/agent/completions 未校验会话归属

**位置**：`apps/backend/app/api/v1/agent.py:176-211`

**问题**：`agent_completion` 在 `session_id` 已存在时，**未调用 `_verify_session_owner`** 校验会话归属。用户 A 可向用户 B 的会话发送消息并获取响应。

对比：`chat.py` 的 `_verify_session_owner` 在所有会话相关接口中均有调用。

**建议**：在 `agent_completion` 中增加会话归属校验。

### 4.4 性能问题

#### 4.4.1 【P0 高风险】ToolAdapter 每次调用创建新线程池

**位置**：`ModuAgent/adapters/tool_adapter.py:44-46`

**问题**：
```python
with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
    future = executor.submit(tool.invoke, params=params, context=context)
    result = future.result(timeout=timeout_ms / 1000.0)
```

每次工具调用都创建并销毁线程池，开销巨大。ReAct 循环中多次调用工具时严重影响性能。

**建议**：使用共享线程池（实例级），或用 `asyncio.wait_for(asyncio.to_thread(...))` 替代。

#### 4.4.2 【P1 中风险】ChromaDB 使用内存客户端，数据不持久化

**位置**：`ModuAgent/components/memory/vector/chroma.py:46`

**问题**：`chromadb.Client()` 创建纯内存客户端，进程重启后所有长期记忆丢失。文件名 `redis_adapter.py` 实为 `InMemoryShortTermMemory`（命名误导），并未真正使用 Redis。

**建议**：长期记忆使用 `chromadb.PersistentClient(path="./chroma_data")`；短期记忆考虑接入真正的 Redis。

#### 4.4.3 【P1 中风险】ChromaLongTermMemory 嵌入模型初始化线程不安全

**位置**：`ModuAgent/components/memory/vector/chroma.py:50-67`

**问题**：`_embed_texts` 中 SentenceTransformer 的延迟初始化是**线程不安全**的（多协程同时首次调用会重复初始化）。且异常处理逻辑有缺陷：`fn([__name__])` 抛异常时 `_use_sentence_transformer` 仍为 `None`，下次调用会重新尝试加载。

**建议**：初始化加锁；异常时设 `_use_sentence_transformer = False`；考虑构造时完成初始化。

#### 4.4.4 【P1 中风险】流式 scrollIntoView 高频调用

**位置**：`ChatMessageList.tsx:14-16` + `AnalysisMessageList.tsx:24-26` + `TaskMessageList.tsx:24-26`

**问题**：`useEffect` 依赖 `[messages]`，SSE 流式输出时每个 delta 都触发 `scrollIntoView({ behavior: 'smooth' })`，高频调用导致性能问题和滚动抖动。

**建议**：使用 `behavior: 'auto'`（流式期间）；或 `requestAnimationFrame` 节流；或仅当用户已滚动到底部时才自动滚动。

#### 4.4.5 【P1 中风险】useAgentChat stateMap 高频更新

**位置**：`apps/web/src/modes/pro/hooks/useAgentChat.ts:211-227`

**问题**：`THINKING_TEXT_MESSAGE_CONTENT` 每个 delta 都调用 `setStateMap`，触发组件重渲染。长文本思考过程产生大量渲染。

**建议**：对 `thinkingContent` 更新做节流（50ms），或用 `useRef` 暂存 + `requestAnimationFrame` 批量更新。

#### 4.4.6 【P2 中风险】工具描述每次请求重建

**位置**：`ModuAgent/orchestration/coordinator.py:199-206, 857-893`

**问题**：每次 `process_request` 都调用 `_build_native_tools()` 和 `_build_tool_descriptions()`，遍历注册表构建工具描述，但工具集运行时很少变化。

**建议**：缓存工具描述，仅在 `swap_component` 后失效缓存。

#### 4.4.7 【P2 低风险】EventBus 事件日志全量拷贝

**位置**：`ModuAgent/orchestration/communication/message_bus.py:74-75`

**问题**：每次超限都创建新列表（`[-n:]` 切片），高频事件时频繁列表拷贝。

**建议**：使用 `collections.deque(maxlen=1000)` 替代。

#### 4.4.8 【P2 低风险】会话列表查询 N+1 问题

**位置**：`apps/backend/app/api/v1/chat.py:79-104`

**问题**：`list_sessions` 对每个会话单独查询最后一条消息（第 81-88 行），产生 N+1 查询。会话数多时性能差。

**建议**：使用子查询或 JOIN 一次性获取。

### 4.5 架构设计问题

#### 4.5.1 【P1 高风险】Coordinator "上帝类"问题

**位置**：`ModuAgent/orchestration/coordinator.py`（1048 行）

**问题**：`Coordinator` 承担过多职责：请求编排、感知管线、ReAct 循环、工具调用解析、事件发布、流式输出、传感器管理、记忆更新、安全熔断。`process_request` 和 `stream_request` 存在大量重复代码。

**建议**：加速 LangGraph 重构迁移（`langgraph/` 目录已存在但未接入），或至少提取公共逻辑为内部方法。

#### 4.5.2 【P1 中风险】feedback 与 evolution 模块未集成到主流程

**位置**：`ModuAgent/feedback/` 和 `evolution/` 全模块

**问题**：`FeedbackLoop`、`ParameterTuneStrategy`、`ComponentSwapStrategy`、`RollbackMechanism` 均已实现，但**未被 `Coordinator` 或 `LangGraph` 节点调用**。`EvolutionSignalCollector` 虽初始化并订阅事件，但收集的信号**无人消费**。

存在两个 `EvolutionSignalCollector` 类（`feedback/evolution_signal.py` 和 `orchestration/communication/message_bus.py`），接口不兼容，导致信号收集与消费无法对接。

**建议**：合并为统一 `EvolutionSignalCollector`；在 `process_request` 完成后调用 `FeedbackLoop.evaluate`。

#### 4.5.3 【P1 中风险】双 SSE 解析实现重复

**位置**：`apps/web/src/api/chat.ts`（`streamChat`，死代码）+ `@tdesign-react/chat` 内部 + `useAgentChat.ts` 手写

**问题**：存在两套独立的 SSE 解析实现，`streamChat` 从未被 import（死代码），`useAgentChat` 手写解析与 TDesign 内部解析重复。Token 注入逻辑在 `client.ts` / `chat.ts` / `useAgentChat.ts` 三处重复。

**建议**：统一为单一 SSE 解析器，统一 Token 注入。

#### 4.5.4 【P1 中风险】三模式组件高度重复

**位置**：`modes/pro/` 与 `modes/task/`

**问题**：
- `AnalysisInput.tsx` 与 `TaskInput.tsx` 几乎逐行相同（仅 className 前缀不同）
- `AnalysisMessageList.tsx` 与 `TaskMessageList.tsx` 几乎逐行相同
- 三个 `useChatSync.ts`（chat/pro/task）完全相同

**建议**：提取到 `src/hooks/useChatSync.ts` 和公共组件共享。

#### 4.5.5 【P2 中风险】全局单例初始化顺序依赖

**位置**：`core/registry.py:173`、`config/runtime_config.py:156`、`orchestration/communication/message_bus.py:374`

**问题**：三个全局单例（`_registry`、`_config`、`_event_bus`）通过 `get_*()` 延迟初始化，存在隐式依赖。测试或多进程环境中未正确重置可能导致状态污染。

**建议**：引入依赖注入容器，显式管理依赖关系和生命周期。

#### 4.5.6 【P2 中风险】store 与 stores 目录分裂

**位置**：`apps/web/src/store/` 和 `apps/web/src/stores/`

**问题**：两个目录并存，`store/` 放 appStore/conversationStore/theme/toast，`stores/` 放 auth。命名混乱。

### 4.6 功能缺陷与边界条件

#### 4.6.1 【P0 高风险】Task 模式 onRequest 闭包过期

**位置**：`apps/web/src/modes/task/TaskMode.tsx:19-32`

#### 4.6.4 【P1 中风险】联网查询/附件功能未实现

#### 4.6.7 【P2 低风险】ProMainHeader 进度条计算可能为负
