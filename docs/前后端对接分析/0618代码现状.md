### 1.3 状态管理机制

项目使用 **Zustand** 作为全局状态管理方案，存在三个独立 Store + 两个 Context：

#### 1.3.1 `conversationStore.ts` — 会话列表状态（核心 Store）

```typescript
// store/conversationStore.ts:66-159
export const useConversationStore = create<ConversationStore>()(

    (set, get) => ({ ... }),
    {
      name: 'conversation-store',
      partialize: (state) => ({ sessionModes: state.sessionModes }),
```

**关键设计点：**

| 状态字段 | 说明 |
|----------|------|
| `conversations` | 会话列表数组（不持久化，每次 `fetchSessions` 从后端拉取） |

**数据流转：**

```
remove(id)      → DELETE /chat/sessions/:id → 从列表过滤 → 清理 sessionModes
updateTitle(id) → PUT /chat/sessions/:id → 更新本地列表
```

#### 1.3.5 状态管理问题

1. **Store 目录分裂**：`store/` 和 `stores/` 两个目录并存，`store/conversationStore.ts` 和 `stores/auth.ts` 分散在不同位置，缺乏统一的组织规范
2. **`sessionModes` 仅本地持久化**：会话模式（chat/pro/task）不存在于后端 `ChatSession` 表中，完全依赖前端 `localStorage` 维护。用户切换设备或清除缓存后，所有会话的 mode 归属丢失，默认回退到 `chat`
3. **会话列表与消息列表状态分离**：`conversationStore` 管理会话列表，但各模式组件内部用 `useState` 管理消息列表，无统一的消息状态层

### 1.4 接口调用与 HTTP 客户端

#### 1.4.1 通用 HTTP 封装（`api/client.ts`）

```typescript
// api/client.ts:36-85
async function request<T>(path: string, options: RequestInit = {}): Promise<T> {
  const token = getToken();              // 从 localStorage 读取
  headers['Authorization'] = `Bearer ${token}`;
  const response = await fetch(url, { ...options, headers });

  if (response.status === 401) {
    clearToken();                        // 直接清除 Token，无自动刷新
    throw { code: 401, message: '未认证或 Token 已过期' };
  }

  // 解包 ResponseInterceptor 的 { code, data, message } 格式
  if (data && 'data' in data && 'code' in data && 'message' in data) {
    return (data as any).data as T;      // 自动剥离外层包装
  }
}
```

提供 `get` / `post` / `put` / `del` 四个快捷方法，统一处理 Token 注入和响应解包。

#### 1.4.2 SSE 流式通信 — 两条独立链路

前端存在**两套完全独立的 SSE 消费实现**，分别服务于不同模式：

| 链路 | 模式 | 端点 | 实现 | 后端 |
|------|------|------|------|------|
| **链路 A** | chat 模式 | `/api/chat/completions` | TDesign `useChat` Hook（`protocol: 'agui'`） | NestJS |
| **链路 B** | pro 模式 | `/api/agent/completions` | 自定义 `useAgentChat` Hook（手动解析 SSE） | Python |

**链路 A — Chat 模式（`ChatMode.tsx:42-66`）：**

```typescript
const { chatEngine, messages, status } = useChat({
  chatServiceConfig: {
    endpoint: '/api/chat/completions',
    stream: true,
    protocol: 'agui',              // TDesign 内置 AG-UI 协议解析
    onRequest: (params) => ({
      ...params,
      body: JSON.stringify({
        sessionId: activeId,
        message: params.prompt,
        model: 'deepseek-v4-flash',
        stream: true,
        deepThink: deepThinking,   // 深度思考切换 deepseek-reasoner
      }),
    }),
  },
  defaultMessages: historyMessages,
});
```

- 由 TDesign Chat 引擎内部处理 SSE 解析、消息渲染、流式追加
- 历史消息通过 `defaultMessages` 注入（切换会话时从 `GET /chat/sessions/:id/messages` 加载）

**链路 B — Pro 模式（`useAgentChat.ts:113-445`）：**

手动实现完整的 SSE 解析与状态管理：

```
fetch('/api/agent/completions', { signal: controller.signal })
  → reader.read() 循环
    → buffer.split('\n')
      → 逐行匹配 'data: ' 前缀
        → JSON.parse → switch(event.type)
          ├─ THINKING_START         → 创建 stateMap 步骤，status='running'
          ├─ THINKING_TEXT_MESSAGE_CONTENT → 追加思考内容到 stateMap
          ├─ THINKING_END           → 标记步骤 done
          ├─ TOOL_CALL_START        → 创建工具调用步骤
          ├─ TOOL_CALL_RESULT       → 标记完成 + 创建 observation 步骤
          ├─ TEXT_MESSAGE_CONTENT   → 追加到 assistant 消息
          ├─ RUN_FINISHED           → 清理 currentStateKey
          ├─ RUN_ERROR              → 清理 running 状态，显示错误
          └─ default                → 忽略
```

#### 1.4.3 Token 管理问题

1. **无 401 自动刷新机制**：`client.ts:63-66` 中 401 响应直接清除 Token 并抛出异常，未利用 `refreshToken` 自动续期。用户 JWT 过期（2 小时）后必须重新登录
2. **Token 存储于 localStorage**：存在 XSS 攻击风险，恶意脚本可读取 Token
3. **SSE 请求绕过统一封装**：`useAgentChat.ts` 和 `api/chat.ts` 中的 SSE 请求直接使用 `fetch`，未复用 `client.ts` 的拦截逻辑

### 1.6 前端关键问题总结

| 问题 | 严重程度 | 位置 | 说明 |
|------|----------|------|------|
| 双 Store 目录并存 | 低 | `store/` vs `stores/` | 组织不规范，维护成本增加 |
| `sessionModes` 仅本地持久化 | 高 | `conversationStore.ts:24-25` | 后端无 mode 字段，跨设备丢失模式归属 |
| 无 401 Token 自动刷新 | 高 | `client.ts:63-66` | JWT 2h 过期后需重新登录，refreshToken 形同虚设 |
| 两套 SSE 解析逻辑 | 中 | `api/chat.ts` vs `useAgentChat.ts` | 重复实现，维护不一致风险 |
| `useAgentChat` 每次发送重置消息 | 中 | `useAgentChat.ts:103` | `setMessages([userMsg])` 覆盖而非追加，历史消息需重新加载 |
| SSE 请求绕过统一 client 封装 | 中 | `useAgentChat.ts:117` / `api/chat.ts:45` | 401 拦截、错误处理逻辑不统一 |
| Token 存 localStorage | 中 | `client.ts:9-11` | XSS 风险 |
| 历史消息无虚拟滚动 | 低 | `ChatMessageList.tsx` | 长会话性能下降 |

## 二、后端分析

### 2.1 双后端架构总览

项目存在**两个独立后端服务**，共享同一个 PostgreSQL 数据库：

| 后端 | 技术栈 | 端口 | ORM | 职责 |
|------|--------|------|-----|------|
| NestJS-backend | NestJS 10 + Express + Prisma 5 | **3000** | Prisma | 认证、用户管理、普通对话（Chat）、文件上传、系统配置 |
| Python-backend（已迁至 `apps/backend/`） | FastAPI + SQLAlchemy async | **8000** | SQLAlchemy | Agent ReAct 对话（Pro 模式）、工具执行轨迹、深度反馈 |

```
┌──────────────────────────────────────────────────────────┐
│ 前端 (Vite dev server :9000)                              │
│   proxy: /api → http://localhost:3000 (rewrite 去掉 /api) │
└────────────────────────┬──────────────────────────────────┘
                         │
          ┌──────────────┴──────────────┐
          ▼                             ▼
┌─────────────────────┐     ┌─────────────────────┐
│ NestJS (:3000)      │     │ Python (:3000)      │
│ /auth/*             │     │ /agent/*             │
│ /chat/*             │     │ /chat/* (旧兼容)     │
│ /user/*             │     │ /user/*              │
│ /system/*           │     │ /system/*            │
│ /upload/*           │     │ /upload/*            │
└────────┬────────────┘     └────────┬────────────┘
         │                           │
         └───────────┬───────────────┘
                     ▼
         ┌───────────────────────┐
         │ PostgreSQL (:5432)    │
         │ pioneering 数据库      │
         └───────────────────────┘
```

**核心矛盾**：两个后端均监听 **3000** 端口，无法同时运行。Vite 代理只能指向一个目标（`VITE_API_BASE_URL || http://localhost:3000`）。这意味着前端要么连接 NestJS（chat/task 模式可用），要么连接 Python（pro 模式可用），**无法同时支持全部三种模式**。

#### 2.2.3 认证服务链路

```
POST /auth/login { username, password }
  → AuthService.login()
    → prisma.user.findUnique({ username })
    → bcrypt.compare(password, user.passwordHash)
    → generateAuthResponse(user)
      → JwtService.signAsync({ sub: user.id, username })  // JWT 有效期 2h
      → prisma.refreshToken.create({ token: rt_xxx, expiresAt: now+30d })
      → 返回 { token, refreshToken, user, expiresIn: 7200 }

POST /auth/refresh { refreshToken }
  → AuthService.refreshToken()
    → prisma.refreshToken.findUnique({ token })
    → 检查 revoked + expiresAt
    → 撤销旧 token (revoked = true)
    → generateAuthResponse() 生成新 token 对
```

**认证守卫**（`jwt-auth.guard.ts`）：
- 全局 `APP_GUARD` 注册 `JwtAuthGuard`
- 通过 `@Public()` 装饰器标记公开路由（login、refresh、wechat 登录）
- 从 `Authorization: Bearer xxx` 提取 Token，`jwtService.verifyAsync()` 验证
- 验证通过后将 payload 挂载到 `request.user`，通过 `@CurrentUser('sub')` 装饰器注入 userId

```

  ├─ 获取 AiConfig 配置（provider, model, apiKey）
  ├─ deepThink? → model = 'deepseek-reasoner'
  ├─ prepareSession() → 确认/创建会话 + 保存用户消息

  ├─ ⚠️ Monkey-patch res.end 发送 RUN_FINISHED + 持久化 AI 消息
  ├─ this.activeStreams.set(assistantMsgId, { controller, sessionId })
  └─ llmService.streamChat(messages, res, assistantMsgId, provider, model)

              → TEXT_MESSAGE_START/CONTENT/END (content)
```

**`res.write` Monkey-patch 的脆弱性**（`chat.service.ts:390-452`）：

```typescript
// 包装 res.write 拦截 AG-UI 事件以收集数据
const originalWrite = res.write.bind(res);
res.write = (chunk: any) => {
  const str = typeof chunk === 'string' ? chunk : chunk.toString();
  const match = str.match(/data: (\{.*\})/);     // 正则匹配 SSE 数据
  if (match) {
    const parsed = JSON.parse(match[1]);
    if (parsed.type === 'TEXT_MESSAGE_CONTENT') collectedContent.push(parsed.delta);
    if (parsed.type === 'THINKING_TEXT_MESSAGE_CONTENT') collectedThinking.push(parsed.delta);
  }
  return originalWrite(chunk);
};

// 包装 res.end 先发 RUN_FINISHED 再保存消息
res.end = async (endChunk?: any) => {
  res.write(`data: ${JSON.stringify({ type: 'RUN_FINISHED', ...})}\n\n`);
  // 保存完整 AI 回复到数据库
  await this.prisma.chatMessage.create({ ... });
  await this.prisma.chatSession.update({ ... });
  this.activeStreams.delete(assistantMsgId);
  originalEnd();
};
```

这种通过覆盖 Express Response 方法来拦截流式数据的做法极其脆弱：
- 正则 `str.match(/data: (\{.*\})/)` 无法处理多行 JSON 或跨 chunk 的 SSE 事件
- `res.end` 被改为 `async` 但 Express 不保证等待异步完成
- `activeStreams` 中的 `AbortController` 实际从未传递给 `llmService.streamChat`，**停止生成功能无效**

#### 2.2.5 LLM 服务（`llm.service.ts`）

支持 5 个 LLM Provider，通过 `MODEL_TO_PROVIDER` 映射表路由：

| Provider | API 端点 | 流式实现 |
|----------|----------|----------|
| deepseek | `api.deepseek.com/v1/chat/completions` | `streamOpenAICompatible()` |

## 三、问题排查

### 3.1 架构设计问题

#### 3.1.1 双后端端口冲突 — 致命问题

```
NestJS main.ts:25  →  await app.listen(3000);
Python .env        →  PORT=3000
Vite vite.config   →  proxy /api → http://localhost:3000
```

三个服务争抢同一端口，实际只能启动一个。前端 Vite 代理只能指向一个后端，导致：

- **连接 NestJS 时**：`/api/chat/*`、`/api/auth/*` 可用，但 `/api/agent/*` 不存在 → Pro 模式不可用
- **连接 Python 时**：`/api/agent/*` 可用，但 NestJS 的 `/api/chat/*` 实现与 Python 不同 → 行为不一致

**根因**：项目演进过程中，Python 后端（ModuAgent Agent 能力）与 NestJS 后端（用户/认证/对话管理）未能合并为统一服务，也未通过网关或不同端口进行路由分流。

#### 3.1.2 双 ORM 共享数据库 — Schema 漂移风险

两个后端使用不同 ORM 定义同一数据库：

| 表 | Prisma（NestJS） | SQLAlchemy（Python） | 差异 |
|----|-------------------|----------------------|------|
| `chat_sessions` | 无 `agent_mode` | 有 `agent_mode` 列 | Prisma 迁移不感知此列 |
| `chat_messages` | 无 `prompt_tokens`/`completion_tokens`/`latency_ms`/`user_rating`/`user_feedback` | 有这些列 | Prisma 查询时会忽略，Python 写入的数据 Prisma 读不到扩展字段 |
| `agent_tool_executions` | **表不存在** | 完整定义 | Prisma 迁移不会创建此表，需 Python 侧手动建表 |

**实际影响**：
- Prisma 迁移可能 DROP Python 添加的列（取决于迁移策略）
- Python 写入的 `agent_mode`、可观测性字段对 NestJS 不可见
- `AgentToolExecution` 表的存在依赖于 Python 后端先运行

#### 3.1.3 前端 `sessionModes` 本地持久化 — 跨设备不一致

后端 `ChatSession` 表无 `mode` 字段（NestJS Prisma schema 确认）。前端通过 `conversationStore.sessionModes` 在 `localStorage` 中维护 `sessionId → mode` 映射。

```
用户在设备 A 创建 pro 模式会话 → sessionModes[sess_xxx] = 'pro'（仅存于设备 A）
用户在设备 B 登录 → fetchSessions() 拉到会话列表 → sessionModes 中无此映射 → 默认 'chat'
→ 设备 B 上该会话显示为 chat 模式，Pro 模式功能不可用
```

### 3.2 数据一致性问题

#### 3.2.1 流式消息持久化时序问题

**NestJS 侧**（`chat.service.ts:408-452`）：

```
res.end = async (endChunk?: any) => {
  // 1. 发送 RUN_FINISHED
  res.write(`data: ${JSON.stringify({ type: 'RUN_FINISHED', ...})}\n\n`);
  // 2. 保存 AI 消息到 DB
  await this.prisma.chatMessage.create({ ... });
  // 3. 更新 session
  await this.prisma.chatSession.update({ ... });
  // 4. 真正关闭响应
  originalEnd();
};
```

问题：
- `res.end` 被改为 `async`，但 Express 的 `res.end()` 调用者不 `await` 它，可能导致异步保存未完成时连接已关闭
- 如果 `prisma.chatMessage.create` 抛异常，`originalEnd()` 不会调用，连接挂起
- `llmService.streamChat` 内部也会调用 `res.end()`（`llm.service.ts:305,359`），与 ChatService 的 monkey-patched `res.end` 可能重复调用

**Python 侧**（`agent.py:219-267`）：

```
async def event_generator():
    async for event_dict in stream_agent_completion(...):
        yield event_dict          # 客户端断开 → 生成器被 GC → 以下代码不执行

    # 持久化逻辑（可能不执行）
    db.add(assistant_msg)
    await db.commit()
```

问题：客户端中途断开（网络故障、用户主动停止）时，Python 的异步生成器会被 GC 回收，后续 DB 持久化代码不执行，导致 assistant 回复丢失。

#### 3.2.2 会话消息计数不一致

NestJS 在 `prepareSession` 中 `messageCount: { increment: 1 }`（用户消息），又在 `res.end` 中再次 `increment: 1`（AI 消息），但如果 AI 消息保存失败，计数已增加。

Python 在 `agent.py:211` 先 `message_count += 1`（用户消息），在 `agent.py:265` 再 `+1`（AI 消息），同样存在中间失败导致计数不一致的风险。

#### 3.2.3 默认模型不一致

| 位置 | 默认模型 |
|------|----------|
| NestJS Prisma schema `ChatSession.model` | `deepseek-v4-flash` |

Python 后端代码默认值（`gpt-4o-mini`）与 `.env`（`glm-4-flash`）不一致，且与 NestJS（`deepseek-v4-flash`）不一致。

#### 3.3.1 历史消息加载无 Token 感知

两个后端均固定加载最近 20 条历史消息，不考虑 Token 总量：

## 四、结论与优化

### 4.1 项目整体结论

**项目定位**：这是一个企业级 AI 对话平台（IAC Incubator / 创路 Agent），支持普通对话（Chat）、智能分析（Pro / Agent ReAct）、任务模式（Task）三种交互形态，具备多 LLM 后端接入、流式 SSE 通信、AG-UI 协议、会话管理、用户认证等完整功能。

**架构优势**：
1. **AG-UI 协议标准化**：NestJS LLM 服务和 Python Agent 桥接层均已实现 AG-UI 标准事件输出，前后端协议统一
2. **多 LLM 适配**：NestJS 支持 5 个 Provider（deepseek/glm/kimi/qwen/minimax），Python 支持 4 个（GPT/DeepSeek/GLM/Qwen），覆盖主流国产大模型
3. **组件化 Agent 框架**：ModuAgent 的 `ComponentRegistry` + `Coordinator` 实现了 Perception-Memory-Reasoning-Action 四层解耦，支持运行时组件替换
4. **完善的数据库设计**：消息自引用（编辑/重新生成）、工具执行轨迹、Token 用量、用户配额等表结构设计合理
5. **前端体验**：TDesign Chat 组件 + 自定义推理过程可视化（ProcessPanel），交互体验完整

**核心矛盾**：项目最大的结构性问题是 **双后端端口冲突 + 双 ORM 共享数据库**，导致前端无法同时使用全部功能，且数据库 Schema 存在漂移风险。这是制约项目可部署性的首要障碍。

### 4.2 针对性优化方案

#### 4.2.1 【P0 · 致命】统一后端服务入口

**问题**：NestJS 和 Python 均监听 3000 端口，无法共存。

**方案 A（推荐）：NestJS 作为主服务，Python 作为内部 Agent 微服务**

```
前端 (:9000)
  → Vite proxy /api → NestJS (:3000)
                        ├─ /auth/*, /chat/*, /user/*, /upload/*, /system/*  → 本地处理
                        └─ /agent/* → HTTP 转发 → Python (:3001)
```

- Python 后端改为监听 **3001** 端口（修改 `.env PORT=3001`）
- NestJS 新增 `AgentProxyController`，将 `/agent/*` 请求转发到 `http://localhost:3001/agent/*`
- SSE 流式转发使用 `http-proxy` 或手动管道传递
- Python 后端可移除 auth/chat/user 等重复路由，仅保留 `/agent/*`

**方案 B：API 网关统一路由**

- 使用 Nginx / Traefik 作为反向代理
- `/api/auth/*`、`/api/chat/*` → NestJS (:3000)
- `/api/agent/*` → Python (:3001)
- 前端 Vite proxy 指向网关 (:8080)

1. 以 Prisma 为**唯一迁移源**，Python 后端不自动建表
2. 在 Prisma schema 中补充缺失字段：

#### 4.2.3 【P0 · 高】修复 NestJS 流式消息持久化

**问题**：`res.write`/`res.end` Monkey-patch 脆弱，停止生成无效。

**方案**：重构 `streamChatCompletion`，使用 RxJS Observable 或事件回调替代 Monkey-patch：

```typescript
// chat.service.ts 重构方案
async streamChatCompletion(userId, data, res) {
  const { sessionId, userMsgId } = await this.prepareSession(userId, data);
  const messages = await this.buildMessageContext(sessionId, data.systemPrompt);
  messages.push({ role: 'user', content: data.message });

  const assistantMsgId = `msg_${uuidv4().replace(/-/g, '').slice(0, 24)}`;
  const runId = `run_${uuidv4().replace(/-/g, '').slice(0, 24)}`;
  const controller = new AbortController();
  this.activeStreams.set(assistantMsgId, { controller, sessionId });

  const collectedContent: string[] = [];
  const collectedThinking: string[] = [];

  // 发送 RUN_STARTED
  res.write(`data: ${JSON.stringify({ type: 'RUN_STARTED', threadId: sessionId, runId })}\n\n`);

  try {
    // LlmService 改为返回 AsyncGenerator，由 ChatService 控制写入
    for await (const event of this.llmService.streamChat(
      messages, provider, model, { signal: controller.signal }
    )) {
      // 收集内容
      if (event.type === 'TEXT_MESSAGE_CONTENT') collectedContent.push(event.delta);
      if (event.type === 'THINKING_TEXT_MESSAGE_CONTENT') collectedThinking.push(event.delta);
      // 写入 SSE
      res.write(`data: ${JSON.stringify(event)}\n\n`);
    }
    // 发送 RUN_FINISHED
    res.write(`data: ${JSON.stringify({ type: 'RUN_FINISHED', threadId: sessionId, runId })}\n\n`);
  } catch (err) {
    res.write(`data: ${JSON.stringify({ type: 'RUN_ERROR', message: err.message, code: 'STREAM_ERROR' })}\n\n`);
  } finally {
    // 持久化（无论成功失败，只要有内容就保存）
    const fullContent = collectedContent.join('');
    if (fullContent) {
      await this.prisma.chatMessage.create({ ... });
      await this.prisma.chatSession.update({ ... });
    }
    this.activeStreams.delete(assistantMsgId);
    res.end();
  }
}
```

对应 `LlmService.streamChat` 改为返回 `AsyncGenerator`，内部使用 `controller.signal` 支持中止。

#### 4.2.5 【P1 · 中】前端 401 Token 自动刷新

**问题**：JWT 2h 过期后需重新登录。

**方案**：在 `client.ts` 中实现自动刷新拦截器：

```typescript
let isRefreshing = false;
let refreshPromise: Promise<string> | null = null;

async function refreshToken(): Promise<string> {
  if (isRefreshing && refreshPromise) return refreshPromise;
  isRefreshing = true;
  refreshPromise = (async () => {
    const refreshToken = localStorage.getItem('refreshToken');
    if (!refreshToken) throw new Error('No refresh token');
    const resp = await fetch('/api/auth/refresh', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ refreshToken }),
    });
    if (!resp.ok) throw new Error('Refresh failed');
    const data = await resp.json();
    const newToken = data.data?.token || data.token;
    setToken(newToken, data.data?.refreshToken || data.refreshToken);
    return newToken;
  })();
  try {
    return await refreshPromise;
  } finally {
    isRefreshing = false;
    refreshPromise = null;
  }
}

// request 函数中 401 处理改为：
if (response.status === 401) {
  try {
    const newToken = await refreshToken();
    headers['Authorization'] = `Bearer ${newToken}`;
    return request<T>(path, options);  // 重试一次
  } catch {
    clearToken();
    window.location.href = '/auth/login';
    throw { code: 401, message: 'Token 已过期，请重新登录' };
  }
}
```

#### 4.2.7 【P1 · 中】历史消息 Token 感知截断

**问题**：固定 20 条可能超上下文窗口。

**方案**：实现基于 Token 估算的历史截断：

```typescript
private async buildMessageContext(sessionId: string, systemPrompt?: string) {
  const MAX_CONTEXT_TOKENS = 6000;  // 预留 2K 给系统提示+新消息+回复
  let usedTokens = 0;
  const context: Message[] = [];

  // 系统提示
  if (systemPrompt) {
    usedTokens += Math.ceil(systemPrompt.length / 4);
    context.push({ role: 'system', content: systemPrompt });
  }

  // 从最新往前加载，直到 Token 预算用完
  const batchSize = 50;
  let offset = 0;
  while (usedTokens < MAX_CONTEXT_TOKENS) {
    const batch = await this.prisma.chatMessage.findMany({
      where: { sessionId, role: { not: 'system' } },
      orderBy: { createdAt: 'desc' },
      skip: offset,
      take: batchSize,
      select: { role: true, content: true },
    });
    if (batch.length === 0) break;
    for (const m of batch) {
      const tokens = Math.ceil(m.content.length / 4);
      if (usedTokens + tokens > MAX_CONTEXT_TOKENS) break;
      usedTokens += tokens;
      context.push({ role: m.role, content: m.content });
    }
    offset += batchSize;
  }

  // 反转为时间正序
  return [...context.slice(0, 1), ...context.slice(1).reverse()];
}
```

### 2.5 Agent 模块 — 前端完全缺失调用层

Python 后端 `/agent/*` 路由共 **7 个接口**（会话管理 3 个 + 对话执行 1 个 + 工具轨迹 2 个 + 反馈 1 个），但前端仅在 `useAgentChat.ts:117` 直接 `fetch('/api/agent/completions')`，**其余 6 个接口前端无任何调用**。

## 三、业务流程与数据流转合理性评估

### 3.1 会话生命周期流程

```
前端创建会话
  → POST /chat/sessions { title, model: 'deepseek-v4-flash' }
    → 后端创建 ChatSession（无 agent_mode 字段）
      → 返回 SessionResponse

前端切换到 Pro 模式
  → useAgentChat.sendMessage({ prompt })
    → POST /agent/completions { sessionId, message, stream: true }
      → Python agent.py: agent_completion()
        → _verify_session_owner? ❌ 未调用！直接使用 sessionId
        → 创建用户消息 + 加载历史 + Agent ReAct 执行
```

**流程缺陷**：
1. `/agent/completions` 未校验会话是否属于当前用户（`agent.py:177-182` 直接使用 `dto.sessionId`，无 `_verify_session_owner` 调用）
2. 会话创建走 `/chat/sessions`，但 Agent 对话走 `/agent/completions`，两套接口操作同一 `ChatSession` 表，但 `/chat/sessions` 创建时无 `agent_mode`，Agent 无法区分会话类型
3. 前端 `useAgentChat.ts:103` 每次发送消息 `setMessages([userMsg])` 覆盖整个消息列表，**历史消息不会被展示**，需重新加载

### 3.2 消息持久化时序

```
POST /chat/completions (stream=true)
  → 后端 chat.py:427-484 event_generator()
    1. yield RUN_STARTED
    2. yield AG-UI 事件流（TEXT_MESSAGE_CONTENT 等）
       → 同时收集 collected_content
    3. yield RUN_FINISHED
    4. 持久化：db.add(assistant_msg) + db.commit()
```

**问题**：如果客户端在步骤 2-3 之间断开连接，`event_generator()` 的后续 yield 不会执行，步骤 4 的持久化代码**不会运行**，AI 回复丢失。Python 异步生成器在客户端断开时会被 GC 回收，`finally` 块可能不执行。

### 3.3 认证与 Token 流转

```
前端登录
  → POST /auth/login { username, password }
    → 后端返回 { token, refreshToken, user }
      → 前端 setToken(token, refreshToken) 存入 localStorage

Token 过期（2h）
  → 前端请求返回 401
    → client.ts:63-66 → clearToken() + throw 401
      → ❌ 未调用 /auth/refresh 自动刷新
      → 用户需重新登录
```

**问题**：
1. 后端 `RefreshTokenRequest` 的 `refresh_token` 字段名与前端发送的 `refreshToken` 不匹配，即使前端调用刷新也会 422 错误
2. 后端 `TokenResponse` 未返回 `expiresIn`，前端无法预判 Token 过期时间
3. 前端 `client.ts` 无自动刷新机制

### 3.4 响应格式包装链路

Python 后端 `main.py:70-118` 的 `response_wrapper` 中间件将所有非 SSE 响应包装为 `{ code, data, message }` 格式。

前端 `client.ts:80-82` 自动解包：
```typescript
if (data && 'data' in data && 'code' in data && 'message' in data) {
  return (data as any).data as T;
}
```

**问题**：
- 后端 `response_wrapper` 会将 `UserProfile` 的 `created_at`/`updated_at`（snake_case）原样放入 `data` 字段，前端解包后得到 snake_case 字段，与前端类型定义的 camelCase 不匹配
- `response_wrapper` 在异常情况下（如 422 校验错误）返回的 `detail` 字段格式与前端 `ApiError` 期望的 `{ code, message }` 格式不一致

#### 5.3.3 统一前端 API 调用层

```typescript
// api/sse.ts — 统一 SSE 请求封装
import { getToken } from './client';

export interface SSEEvent {
  type: string;
  [key: string]: any;
}

export interface SSEOptions {
  url: string;
  body: any;
  signal?: AbortSignal;
  onEvent: (event: SSEEvent) => void;
  onError?: (err: Error) => void;
  onComplete?: () => void;
}

export async function connectSSE(options: SSEOptions): Promise<void> {
  const token = getToken();
  const headers: Record<string, string> = {
    'Content-Type': 'application/json',
    ...(token ? { Authorization: `Bearer ${token}` } : {}),
  };

  try {
    const response = await fetch(options.url, {
      method: 'POST',
      headers,
      body: JSON.stringify(options.body),
      signal: options.signal,
    });

    if (!response.ok) {
      const errData = await response.json().catch(() => null);
      throw new Error(errData?.message || `请求失败: ${response.status}`);
    }

    const reader = response.body?.getReader();
    if (!reader) throw new Error('无法读取响应流');

    const decoder = new TextDecoder();
    let buffer = '';

    while (true) {
      const { done, value } = await reader.read();
      if (done) break;

      buffer += decoder.decode(value, { stream: true });
      // 按 SSE 标准的 \n\n 分隔事件
      const events = buffer.split('\n\n');
      buffer = events.pop() || '';

      for (const event of events) {
        for (const line of event.split('\n')) {
          if (!line.startsWith('data: ')) continue;
          const dataStr = line.slice(6);
          try {
            const parsed = JSON.parse(dataStr);
            options.onEvent(parsed);
          } catch { /* 忽略解析失败 */ }
        }
      }
    }
    options.onComplete?.();
  } catch (err: any) {
    if (err.name === 'AbortError') {
      options.onComplete?.();
    } else {
      options.onError?.(err);
    }
  }
}
```

Pro 模式 `useAgentChat` 和 Chat 模式的 `streamChat` 均复用此封装。

#### 5.3.4 优化会话列表 N+1 查询

```python
# chat.py — list_sessions 使用 JOIN 替代 N+1
from sqlalchemy.orm import aliased
from sqlalchemy import func

@router.get("/sessions")
async def list_sessions(
    current_user: User = Depends(get_current_user),
    db: AsyncSession = Depends(get_db),
    page: int = Query(1, ge=1),
    pageSize: int = Query(20, ge=1, le=100, alias="pageSize"),
    archived: bool | None = None,
):
    where = [ChatSession.user_id == current_user.id]
    if archived is not None:
        where.append(ChatSession.is_archived == archived)

    # 使用子查询获取每个 session 的最后一条消息
    LastMsg = aliased(ChatMessage)
    subq = (
        select(
            ChatMessage.session_id,
            func.max(ChatMessage.created_at).label("max_created")
        )
        .group_by(ChatMessage.session_id)
        .subquery()
    )

    q = (
        select(ChatSession, LastMsg)
        .outerjoin(
            LastMsg,
            (LastMsg.session_id == ChatSession.id) &
            (LastMsg.created_at == subq.c.max_created)
        )
        .where(*where)
        .order_by(ChatSession.updated_at.desc())
        .offset((page - 1) * pageSize)
        .limit(pageSize)
    )
    result = await db.execute(q)
    rows = result.all()

    # 一次查询获取总数
    total = (await db.execute(
        select(func.count()).select_from(ChatSession).where(*where)
    )).scalar() or 0

    session_list = []
    for session, last_msg in rows:
        session_list.append(SessionResponse(
            id=session.id,
            title=session.title,
            # ...
            lastMessage={
                "content": last_msg.content[:150] if last_msg else None,
                "role": last_msg.role.value if last_msg else None,
                "createdAt": last_msg.created_at.isoformat() if last_msg else None,
            } if last_msg else None,
        ))

    return SessionListResponse(sessions=session_list, total=total, page=page, pageSize=pageSize)
```

### 5.5 终态接口契约建议

统一后的接口契约应遵循以下原则：

1. **命名规范**：全链路 camelCase（后端 Pydantic `alias_generator=to_camel`）
2. **响应格式**：统一 `{ code: number, data: T, message: string }`，SSE 流除外
3. **认证**：所有非 `/auth/*` 接口需 Bearer Token，401 时返回标准化错误
4. **分页**：统一 `{ page, pageSize, total, list/sessions/messages }` 结构
5. **SSE 协议**：统一 AG-UI 标准事件，`\n\n` 分隔，前端统一解析
6. **接口去重**：`/auth/profile` 与 `/user/profile` 合并，`/agent/sessions/*` 与 `/chat/sessions/*` 合并
7. **Schema 约束**：所有嵌套结构（`contentBlocks`、`lastMessage`）必须有 Pydantic 模型定义，禁止裸 `dict`/`list`
