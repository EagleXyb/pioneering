## 2. AG-UI 协议规范验证

### 2.1 AG-UI 协议实现概览

ModuAgent 在 `orchestration/communication/agui_adapter.py` 下实现了完整的 AG-UI 事件系统。

**第一层：AG-UI 事件类型定义**

```python
class AGUIEventType(str, Enum):
    RUN_STARTED              # 运行开始
    RUN_FINISHED             # 运行结束
    RUN_ERROR                # 运行错误
    TEXT_MESSAGE_START       # 文本消息开始
    TEXT_MESSAGE_CONTENT     # 文本消息内容
    TEXT_MESSAGE_END         # 文本消息结束
    TEXT_MESSAGE_CHUNK       # 文本消息块
    THINKING_START           # 思考开始
    THINKING_END             # 思考结束
    THINKING_TEXT_MESSAGE_START   # 思考文本开始
    THINKING_TEXT_MESSAGE_CONTENT # 思考文本内容
    THINKING_TEXT_MESSAGE_END     # 思考文本结束
    TOOL_CALL_START          # 工具调用开始
    TOOL_CALL_ARGS           # 工具调用参数
    TOOL_CALL_END            # 工具调用结束
    TOOL_CALL_CHUNK          # 工具调用块
    TOOL_CALL_RESULT         # 工具调用结果
    STATE_SNAPSHOT           # 状态快照
    STATE_DELTA              # 状态增量
    MESSAGES_SNAPSHOT        # 消息快照
```

**第二层：AGUIStreamAdapter** — 提供 `transform()`（收集后一次性输出）和 `transform_streaming()`（实时流式输出）两种模式。

### 2.2 协议兼容性矩阵

| AG-UI 规范事件 形式 | 已实现 | 说明 |
|--------------------|--------|------|
| `RUN_STARTED` | 是 | 携带 threadId + runId |
| `RUN_FINISHED` | 是 | 携带 threadId + runId |
| `RUN_ERROR` | 是 | 携带 code + message |
| `TEXT_MESSAGE_START/CONTENT/END` | 是 | 完整的文本消息生命周期 |
| `THINKING_START/END` | 是 | 思考过程可见 |
| `THINKING_TEXT_MESSAGE_CONTENT` | 是 | 思考内容流式输出 |
| `TOOL_CALL_START/ARGS/END` | 是 | 完整的工具调用生命周期 |
| `TOOL_CALL_RESULT` | 是 | 工具执行结果返回 |
| `STATE_SNAPSHOT` | 否 | 未实现 |
| `STATE_DELTA` | 是 | 用于阶段状态变更 |
| `MESSAGES_SNAPSHOT` | 否 | 未实现 |

### 2.3 关键问题：AG-UI 适配器未被主流程使用

这是最严重的问题。AG-UI 适配器（`AGUIStreamAdapter`）虽然代码完整，但**未被集成到实际 API 流程中**。

实际的数据流为：

```
前端 useAgentChat → Fetch POST /api/agent/completions
  → agent.py: agent_completion()
    → agent_bridge.py: stream_agent_completion()
      → Coordinator.stream_request()
        → SSEEncoder.encode_token/thinking/tool_call_start/...  (自定义格式)
      → agent_bridge 将 Coordinator 帧转为自定义事件
        → {type: "thinking"|"tool_call"|"tool_result"|"text"|"done"|"error"}
      → 前端 useAgentChat 解析这些自定义事件
```

**AG-UI 标准事件格式**（`data: {"type": "RUN_STARTED", ...}\n\n`）从未被发送给前端。前端接收的是 `data: {"type": "thinking", ...}\n\n` 这种自定义格式。

### 2.4 三套并行的事件编码体系

系统中存在**三套不同的事件编码体系**：

| 编码层 | 所在文件 | SSE 格式 | 是否被使用 |
|--------|----------|----------|-----------|
| `SSEEncoder` | `ModuAgent/orchestration/communication/streaming.py` | `{"event": "token", "data": "..."}` 字典帧 | 是（Coordinator 内部） |
| `AGUIEncoder` | `ModuAgent/orchestration/communication/agui_adapter.py` | `data: {"type": "RUN_STARTED", ...}\n\n` 标准 SSE | **否**（未集成） |
| `agent_bridge` 自定义 | `app/core/agent_bridge.py` | `{"data": "{\"type\": \"thinking\", ...}"}` 封装格式 | 是（API 层） |

#### 3.2.3 关键发现：`__agent_metadata__` 死代码

在 `agent.py` 中，`__agent_metadata__` 事件被拦截用于数据库持久化，不发送给前端。但前端 `useAgentChat.ts` 中仍然保留了对 `__agent_metadata__` 的处理逻辑（`case '__agent_metadata__'`），**这段代码永远不会被触发**。

### 3.3 前端 SSE 解析逻辑

前端在 `useAgentChat.ts`（约第 85-145 行）中手动解析 SSE 流：

```
逐行解析 SSE 格式：
  buffer.split('\n') → 过滤 data: 前缀 → JSON.parse
    ├─ case 'thinking'     → 添加到 stateMap（推理步骤可视化）
    ├─ case 'tool_call'    → 标记 running，更新 currentStateKey
    ├─ case 'tool_result'  → 标记 done，更新内容
    ├─ case 'text'         → 流式追加到 messages
    ├─ case 'done'         → 清除 currentStateKey
    ├─ case 'error'        → 设置 error 状态，return 退出循环
    └─ default             → 忽略
```

### 3.5 错误处理流程

**后端错误处理链路：**

1. `Coordinator.stream_request()` 中通过 `SSEEncoder.encode_error()` 发送错误帧（LLM 生成失败、敏感内容拦截等）
2. `agent_bridge.py` 的 `stream_agent_completion()` 最外层 `try/except` 捕获异常并包装为 `error` 事件
3. `agent.py` 的 `event_generator()` 透传错误事件给前端

**前端错误处理：**

1. HTTP 层面：`response.ok` 检查，非 200 抛出异常
2. SSE 流内：解析 `error` 事件类型，设置 `status: 'error'`
3. 网络中断：`AbortError` 静默处理（设置为 `complete` 状态），其他异常显示错误消息
4. 用户中止：通过 `AbortController` 取消请求

**错误处理问题：**

- `useAgentChat.ts` 中 `error` 事件处理使用了 `return` 直接退出循环，但缺少 `finally` 清理逻辑
- 后端 `agent_bridge.py` 中的 `try/except` 只捕获了最外层异常，Coordinator 内部的 `try/except` 在各处独立处理，可能导致部分错误帧丢失
- 前端 `error` 事件处理后没有清理 `stateMap` 中的 `running` 状态，可能导致 ProcessPanel 显示"永远运行中"的步骤

### 4.1 架构优势

1. **插件化设计**：通过 `ComponentRegistry` 实现了 Perception / Reasoning / Memory / Action 四大组件的运行时注册与替换
2. **接口标准化**：`core/interfaces/` 下定义了清晰的抽象基类（`BaseReasoningEngine`、`BaseMemory`、`BaseTool` 等），支持多 LLM 后端（GPT / DeepSeek / GLM / Qwen）
3. **ReAct 循环**：Coordinator 实现了完整的 Reasoning-Action-Observation 循环，支持多轮工具调用和格式错误重试
4. **事件总线**：`EventBus` 提供了发布/订阅模式，支持组件间解耦通信
5. **进化机制预留**：`evolution/` 目录预留了组件替换和参数调优策略

### 4.2 架构问题总结

| 问题 | 严重程度 | 位置 | 说明 |
|------|----------|------|------|
| AG-UI 适配器未集成 | 高 | `agui_adapter.py` | 代码完整但未被任何 API 路径调用 |
| 三套事件编码体系并存 | 高 | `streaming.py` / `agui_adapter.py` / `agent_bridge.py` | Coordinator 用 SSEEncoder，AG-UI 用 AGUIEncoder，API 层自定义格式 |

| `stateMap` 在 `error` 后残留 running 状态 | 低 | 前端 `useAgentChat.ts` | Error 分支缺少对 stateMap 的清理 |

## 5. 改进建议

### 5.1 统一 AG-UI 协议（高优先级）

将 `AGUIStreamAdapter` 集成到主流程中，替代当前的自定义事件格式：

```python
# agent.py 中应改为：
from orchestration.communication.agui_adapter import AGUIStreamAdapter

adapter = AGUIStreamAdapter(trace_id=trace_id)
async for agui_event in adapter.transform_streaming(
    coordinator.stream_request(...)
):
    yield agui_event  # 直接产出 AG-UI 标准 SSE
```

前端 `useAgentChat.ts` 需要相应调整为解析 AG-UI 标准事件类型（`RUN_STARTED`、`TEXT_MESSAGE_CONTENT` 等）。

### 5.2 修复 metadata 死代码

**方案 A**：删除 `useAgentChat.ts` 中对 `__agent_metadata__` 的处理逻辑。  
**方案 B**：后端同时发送 `__agent_metadata__` 给前端，让前端可以利用其中的 token 用量、延迟等数据做展示。

### 5.3 增强 SSE 安全性

在 `AGUIEncoder.to_sse()` 中增加换行符转义：

```python
@staticmethod
def to_sse(event_type: AGUIEventType, data: Dict[str, Any]) -> str:
    payload = json.dumps({"type": event_type.value, **data}, ensure_ascii=False)
    # 转义 payload 中的换行符，防止 SSE 注入
    payload = payload.replace('\n', '\\n').replace('\r', '\\r')
    return f"data: {payload}\n\n"
```

### 5.4 添加日志持久化

配置 `logging.FileHandler` 将日志写入文件，按日期轮转：

```python
import logging.handlers
handler = logging.handlers.TimedRotatingFileHandler(
    filename='logs/agent.log', when='midnight', backupCount=30
)
logging.getLogger().addHandler(handler)
```

### 5.5 注入会话历史

在 `stream_agent_completion()` 中将历史消息注入到 LLM 上下文，实现真正的多轮对话：

```python
# 从 DB 加载历史消息
messages = await load_history(session_id)
context["history"] = [
    {"role": m.role.value, "content": m.content}
    for m in messages
]
```

### 5.6 异步化 LLM 调用

将 `BaseLLMReasoner.reason()` 改为 `async` 方法，避免阻塞事件循环：

```python
class BaseLLMReasoner(BaseReasoningEngine):
    async def reason(self, prompt, context, **kwargs) -> Tuple[str, Dict[str, int]]:
        async with httpx.AsyncClient(timeout=30) as client:
            resp = await client.post(self.base_url, json={...})
            ...
```

### 5.7 清理安全敏感配置

1. 确保 `.env` 在 `.gitignore` 中
2. 替换 JWT Secret 为安全随机值
3. 限制 CORS 为具体域名
4. 考虑使用密钥管理服务（如 Vault、AWS Secrets Manager）管理 API Key

#### 1.3.5 状态管理问题

1. **Store 目录分裂**：`store/` 和 `stores/` 两个目录并存，`store/conversationStore.ts` 和 `stores/auth.ts` 分散在不同位置，缺乏统一的组织规范
2. **`sessionModes` 仅本地持久化**：会话模式（chat/pro/task）不存在于后端 `ChatSession` 表中，完全依赖前端 `localStorage` 维护。用户切换设备或清除缓存后，所有会话的 mode 归属丢失，默认回退到 `chat`
3. **会话列表与消息列表状态分离**：`conversationStore` 管理会话列表，但各模式组件内部用 `useState` 管理消息列表，无统一的消息状态层

### 1.4 接口调用与 HTTP 客户端

#### 1.4.1 通用 HTTP 封装（`api/client.ts`）

```typescript
// api/client.ts:36-85
async function request<T>(path: string, options: RequestInit = {}): Promise<T> {
  const token = getToken();              // 从 localStorage 读取
  headers['Authorization'] = `Bearer ${token}`;
  const response = await fetch(url, { ...options, headers });

  if (response.status === 401) {
    clearToken();                        // 直接清除 Token，无自动刷新
    throw { code: 401, message: '未认证或 Token 已过期' };
  }

  // 解包 ResponseInterceptor 的 { code, data, message } 格式
  if (data && 'data' in data && 'code' in data && 'message' in data) {
    return (data as any).data as T;      // 自动剥离外层包装
  }
}
```

提供 `get` / `post` / `put` / `del` 四个快捷方法，统一处理 Token 注入和响应解包。

#### 1.4.2 SSE 流式通信 — 两条独立链路

前端存在**两套完全独立的 SSE 消费实现**，分别服务于不同模式：

| 链路 | 模式 | 端点 | 实现 | 后端 |
|------|------|------|------|------|
| **链路 A** | chat 模式 | `/api/chat/completions` | TDesign `useChat` Hook（`protocol: 'agui'`） | NestJS |
| **链路 B** | pro 模式 | `/api/agent/completions` | 自定义 `useAgentChat` Hook（手动解析 SSE） | Python |

**链路 A — Chat 模式（`ChatMode.tsx:42-66`）：**

```typescript
const { chatEngine, messages, status } = useChat({
  chatServiceConfig: {
    endpoint: '/api/chat/completions',
    stream: true,
    protocol: 'agui',              // TDesign 内置 AG-UI 协议解析
    onRequest: (params) => ({
      ...params,
      body: JSON.stringify({
        sessionId: activeId,
        message: params.prompt,
        model: 'deepseek-v4-flash',
        stream: true,
        deepThink: deepThinking,   // 深度思考切换 deepseek-reasoner
      }),
    }),
  },
  defaultMessages: historyMessages,
});
```

- 由 TDesign Chat 引擎内部处理 SSE 解析、消息渲染、流式追加
- 历史消息通过 `defaultMessages` 注入（切换会话时从 `GET /chat/sessions/:id/messages` 加载）

**链路 B — Pro 模式（`useAgentChat.ts:113-445`）：**

手动实现完整的 SSE 解析与状态管理：

```
fetch('/api/agent/completions', { signal: controller.signal })
  → reader.read() 循环
    → buffer.split('\n')
      → 逐行匹配 'data: ' 前缀
        → JSON.parse → switch(event.type)
          ├─ THINKING_START         → 创建 stateMap 步骤，status='running'
          ├─ THINKING_TEXT_MESSAGE_CONTENT → 追加思考内容到 stateMap
          ├─ THINKING_END           → 标记步骤 done
          ├─ TOOL_CALL_START        → 创建工具调用步骤
          ├─ TOOL_CALL_RESULT       → 标记完成 + 创建 observation 步骤
          ├─ TEXT_MESSAGE_CONTENT   → 追加到 assistant 消息
          ├─ RUN_FINISHED           → 清理 currentStateKey
          ├─ RUN_ERROR              → 清理 running 状态，显示错误
          └─ default                → 忽略
```

#### 1.4.3 Token 管理问题

1. **无 401 自动刷新机制**：`client.ts:63-66` 中 401 响应直接清除 Token 并抛出异常，未利用 `refreshToken` 自动续期。用户 JWT 过期（2 小时）后必须重新登录
2. **Token 存储于 localStorage**：存在 XSS 攻击风险，恶意脚本可读取 Token
3. **SSE 请求绕过统一封装**：`useAgentChat.ts` 和 `api/chat.ts` 中的 SSE 请求直接使用 `fetch`，未复用 `client.ts` 的拦截逻辑

### 2.1 双后端架构总览

**`res.write` Monkey-patch 的脆弱性**（`chat.service.ts:390-452`）：

```typescript
// 包装 res.write 拦截 AG-UI 事件以收集数据
const originalWrite = res.write.bind(res);
res.write = (chunk: any) => {
  const str = typeof chunk === 'string' ? chunk : chunk.toString();
  const match = str.match(/data: (\{.*\})/);     // 正则匹配 SSE 数据
  if (match) {
    const parsed = JSON.parse(match[1]);
    if (parsed.type === 'TEXT_MESSAGE_CONTENT') collectedContent.push(parsed.delta);
    if (parsed.type === 'THINKING_TEXT_MESSAGE_CONTENT') collectedThinking.push(parsed.delta);
  }
  return originalWrite(chunk);
};

// 包装 res.end 先发 RUN_FINISHED 再保存消息
res.end = async (endChunk?: any) => {
  res.write(`data: ${JSON.stringify({ type: 'RUN_FINISHED', ...})}\n\n`);
  // 保存完整 AI 回复到数据库
  await this.prisma.chatMessage.create({ ... });
  await this.prisma.chatSession.update({ ... });
  this.activeStreams.delete(assistantMsgId);
  originalEnd();
};
```

这种通过覆盖 Express Response 方法来拦截流式数据的做法极其脆弱：
- 正则 `str.match(/data: (\{.*\})/)` 无法处理多行 JSON 或跨 chunk 的 SSE 事件
- `res.end` 被改为 `async` 但 Express 不保证等待异步完成
- `activeStreams` 中的 `AbortController` 实际从未传递给 `llmService.streamChat`，**停止生成功能无效**

## 三、问题排查

### 3.1 架构设计问题

#### 3.1.1 双后端端口冲突 — 致命问题

```
NestJS main.ts:25  →  await app.listen(3000);
Python .env        →  PORT=3000
Vite vite.config   →  proxy /api → http://localhost:3000
```

三个服务争抢同一端口，实际只能启动一个。前端 Vite 代理只能指向一个后端，导致：

- **连接 NestJS 时**：`/api/chat/*`、`/api/auth/*` 可用，但 `/api/agent/*` 不存在 → Pro 模式不可用
- **连接 Python 时**：`/api/agent/*` 可用，但 NestJS 的 `/api/chat/*` 实现与 Python 不同 → 行为不一致

**根因**：项目演进过程中，Python 后端（ModuAgent Agent 能力）与 NestJS 后端（用户/认证/对话管理）未能合并为统一服务，也未通过网关或不同端口进行路由分流。

#### 3.1.2 双 ORM 共享数据库 — Schema 漂移风险

两个后端使用不同 ORM 定义同一数据库：

| 表 | Prisma（NestJS） | SQLAlchemy（Python） | 差异 |
|----|-------------------|----------------------|------|
| `chat_sessions` | 无 `agent_mode` | 有 `agent_mode` 列 | Prisma 迁移不感知此列 |
| `chat_messages` | 无 `prompt_tokens`/`completion_tokens`/`latency_ms`/`user_rating`/`user_feedback` | 有这些列 | Prisma 查询时会忽略，Python 写入的数据 Prisma 读不到扩展字段 |
| `agent_tool_executions` | **表不存在** | 完整定义 | Prisma 迁移不会创建此表，需 Python 侧手动建表 |

**实际影响**：
- Prisma 迁移可能 DROP Python 添加的列（取决于迁移策略）
- Python 写入的 `agent_mode`、可观测性字段对 NestJS 不可见
- `AgentToolExecution` 表的存在依赖于 Python 后端先运行

#### 3.1.3 前端 `sessionModes` 本地持久化 — 跨设备不一致

后端 `ChatSession` 表无 `mode` 字段（NestJS Prisma schema 确认）。前端通过 `conversationStore.sessionModes` 在 `localStorage` 中维护 `sessionId → mode` 映射。

```
用户在设备 A 创建 pro 模式会话 → sessionModes[sess_xxx] = 'pro'（仅存于设备 A）
用户在设备 B 登录 → fetchSessions() 拉到会话列表 → sessionModes 中无此映射 → 默认 'chat'
→ 设备 B 上该会话显示为 chat 模式，Pro 模式功能不可用
```

### 3.2 数据一致性问题

#### 3.2.1 流式消息持久化时序问题

**NestJS 侧**（`chat.service.ts:408-452`）：

```
res.end = async (endChunk?: any) => {
  // 1. 发送 RUN_FINISHED
  res.write(`data: ${JSON.stringify({ type: 'RUN_FINISHED', ...})}\n\n`);
  // 2. 保存 AI 消息到 DB
  await this.prisma.chatMessage.create({ ... });
  // 3. 更新 session
  await this.prisma.chatSession.update({ ... });
  // 4. 真正关闭响应
  originalEnd();
};
```

问题：
- `res.end` 被改为 `async`，但 Express 的 `res.end()` 调用者不 `await` 它，可能导致异步保存未完成时连接已关闭
- 如果 `prisma.chatMessage.create` 抛异常，`originalEnd()` 不会调用，连接挂起
- `llmService.streamChat` 内部也会调用 `res.end()`（`llm.service.ts:305,359`），与 ChatService 的 monkey-patched `res.end` 可能重复调用

**Python 侧**（`agent.py:219-267`）：

```
async def event_generator():
    async for event_dict in stream_agent_completion(...):
        yield event_dict          # 客户端断开 → 生成器被 GC → 以下代码不执行

    # 持久化逻辑（可能不执行）
    db.add(assistant_msg)
    await db.commit()
```

问题：客户端中途断开（网络故障、用户主动停止）时，Python 的异步生成器会被 GC 回收，后续 DB 持久化代码不执行，导致 assistant 回复丢失。

#### 3.2.2 会话消息计数不一致

NestJS 在 `prepareSession` 中 `messageCount: { increment: 1 }`（用户消息），又在 `res.end` 中再次 `increment: 1`（AI 消息），但如果 AI 消息保存失败，计数已增加。

Python 在 `agent.py:211` 先 `message_count += 1`（用户消息），在 `agent.py:265` 再 `+1`（AI 消息），同样存在中间失败导致计数不一致的风险。

## 四、结论与优化

### 4.1 项目整体结论

**项目定位**：这是一个企业级 AI 对话平台（IAC Incubator / 创路 Agent），支持普通对话（Chat）、智能分析（Pro / Agent ReAct）、任务模式（Task）三种交互形态，具备多 LLM 后端接入、流式 SSE 通信、AG-UI 协议、会话管理、用户认证等完整功能。

**架构优势**：
1. **AG-UI 协议标准化**：NestJS LLM 服务和 Python Agent 桥接层均已实现 AG-UI 标准事件输出，前后端协议统一
2. **多 LLM 适配**：NestJS 支持 5 个 Provider（deepseek/glm/kimi/qwen/minimax），Python 支持 4 个（GPT/DeepSeek/GLM/Qwen），覆盖主流国产大模型
3. **组件化 Agent 框架**：ModuAgent 的 `ComponentRegistry` + `Coordinator` 实现了 Perception-Memory-Reasoning-Action 四层解耦，支持运行时组件替换
4. **完善的数据库设计**：消息自引用（编辑/重新生成）、工具执行轨迹、Token 用量、用户配额等表结构设计合理
5. **前端体验**：TDesign Chat 组件 + 自定义推理过程可视化（ProcessPanel），交互体验完整

**核心矛盾**：项目最大的结构性问题是 **双后端端口冲突 + 双 ORM 共享数据库**，导致前端无法同时使用全部功能，且数据库 Schema 存在漂移风险。这是制约项目可部署性的首要障碍。

### 4.2 针对性优化方案

#### 4.2.1 【P0 · 致命】统一后端服务入口

**问题**：NestJS 和 Python 均监听 3000 端口，无法共存。

**方案 A（推荐）：NestJS 作为主服务，Python 作为内部 Agent 微服务**

#### 4.2.3 【P0 · 高】修复 NestJS 流式消息持久化

**问题**：`res.write`/`res.end` Monkey-patch 脆弱，停止生成无效。

**方案**：重构 `streamChatCompletion`，使用 RxJS Observable 或事件回调替代 Monkey-patch：

```typescript
// chat.service.ts 重构方案
async streamChatCompletion(userId, data, res) {
  const { sessionId, userMsgId } = await this.prepareSession(userId, data);
  const messages = await this.buildMessageContext(sessionId, data.systemPrompt);
  messages.push({ role: 'user', content: data.message });

  const assistantMsgId = `msg_${uuidv4().replace(/-/g, '').slice(0, 24)}`;
  const runId = `run_${uuidv4().replace(/-/g, '').slice(0, 24)}`;
  const controller = new AbortController();
  this.activeStreams.set(assistantMsgId, { controller, sessionId });

  const collectedContent: string[] = [];
  const collectedThinking: string[] = [];

  // 发送 RUN_STARTED
  res.write(`data: ${JSON.stringify({ type: 'RUN_STARTED', threadId: sessionId, runId })}\n\n`);

  try {
    // LlmService 改为返回 AsyncGenerator，由 ChatService 控制写入
    for await (const event of this.llmService.streamChat(
      messages, provider, model, { signal: controller.signal }
    )) {
      // 收集内容
      if (event.type === 'TEXT_MESSAGE_CONTENT') collectedContent.push(event.delta);
      if (event.type === 'THINKING_TEXT_MESSAGE_CONTENT') collectedThinking.push(event.delta);
      // 写入 SSE
      res.write(`data: ${JSON.stringify(event)}\n\n`);
    }
    // 发送 RUN_FINISHED
    res.write(`data: ${JSON.stringify({ type: 'RUN_FINISHED', threadId: sessionId, runId })}\n\n`);
  } catch (err) {
    res.write(`data: ${JSON.stringify({ type: 'RUN_ERROR', message: err.message, code: 'STREAM_ERROR' })}\n\n`);
  } finally {
    // 持久化（无论成功失败，只要有内容就保存）
    const fullContent = collectedContent.join('');
    if (fullContent) {
      await this.prisma.chatMessage.create({ ... });
      await this.prisma.chatSession.update({ ... });
    }
    this.activeStreams.delete(assistantMsgId);
    res.end();
  }
}
```

对应 `LlmService.streamChat` 改为返回 `AsyncGenerator`，内部使用 `controller.signal` 支持中止。

#### 4.2.4 【P0 · 高】修复 Python SSE 流中断持久化丢失

**问题**：客户端断开时 `event_generator()` 后续 DB 代码不执行。

**方案**：使用 `try/finally` 确保持久化：

```python
# agent.py event_generator 重构
async def event_generator():
    ctx = StreamContext()
    try:
        async for event_dict in stream_agent_completion(..., ctx=ctx):
            yield event_dict
    except asyncio.CancelledError:
        logger.warning("Agent stream cancelled by client, partial save")
    finally:
        # 无论正常结束还是中断，都尝试保存已收集的内容
        if ctx.answer_content:
            assistant_msg = ChatMessage(
                content=ctx.answer_content,
                content_blocks=ctx.content_blocks or None,
                # ...
            )
            db.add(assistant_msg)
            await db.commit()
```

#### 4.2.5 【P1 · 中】前端 401 Token 自动刷新

**问题**：JWT 2h 过期后需重新登录。

**方案**：在 `client.ts` 中实现自动刷新拦截器：

```typescript
let isRefreshing = false;
let refreshPromise: Promise<string> | null = null;

async function refreshToken(): Promise<string> {
  if (isRefreshing && refreshPromise) return refreshPromise;
  isRefreshing = true;
  refreshPromise = (async () => {
    const refreshToken = localStorage.getItem('refreshToken');
    if (!refreshToken) throw new Error('No refresh token');
    const resp = await fetch('/api/auth/refresh', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ refreshToken }),
    });
    if (!resp.ok) throw new Error('Refresh failed');
    const data = await resp.json();
    const newToken = data.data?.token || data.token;
    setToken(newToken, data.data?.refreshToken || data.refreshToken);
    return newToken;
  })();
  try {
    return await refreshPromise;
  } finally {
    isRefreshing = false;
    refreshPromise = null;
  }
}

// request 函数中 401 处理改为：
if (response.status === 401) {
  try {
    const newToken = await refreshToken();
    headers['Authorization'] = `Bearer ${newToken}`;
    return request<T>(path, options);  // 重试一次
  } catch {
    clearToken();
    window.location.href = '/auth/login';
    throw { code: 401, message: 'Token 已过期，请重新登录' };
  }
}
```

#### 4.2.7 【P1 · 中】历史消息 Token 感知截断

**问题**：固定 20 条可能超上下文窗口。

**方案**：实现基于 Token 估算的历史截断：

```typescript
private async buildMessageContext(sessionId: string, systemPrompt?: string) {
  const MAX_CONTEXT_TOKENS = 6000;  // 预留 2K 给系统提示+新消息+回复
  let usedTokens = 0;
  const context: Message[] = [];

  // 系统提示
  if (systemPrompt) {
    usedTokens += Math.ceil(systemPrompt.length / 4);
    context.push({ role: 'system', content: systemPrompt });
  }

  // 从最新往前加载，直到 Token 预算用完
  const batchSize = 50;
  let offset = 0;
  while (usedTokens < MAX_CONTEXT_TOKENS) {
    const batch = await this.prisma.chatMessage.findMany({
      where: { sessionId, role: { not: 'system' } },
      orderBy: { createdAt: 'desc' },
      skip: offset,
      take: batchSize,
      select: { role: true, content: true },
    });
    if (batch.length === 0) break;
    for (const m of batch) {
      const tokens = Math.ceil(m.content.length / 4);
      if (usedTokens + tokens > MAX_CONTEXT_TOKENS) break;
      usedTokens += tokens;
      context.push({ role: m.role, content: m.content });
    }
    offset += batchSize;
  }

  // 反转为时间正序
  return [...context.slice(0, 1), ...context.slice(1).reverse()];
}
```
