# 感知层优化方案

> 基于 ModuAgent `components/perception/` 模块深度代码分析，针对《0623Agent现状分析》中识别的 11 个问题，逐一给出根因分析与优化方案。

---

## 一、代码现状总览

### 1.1 架构概览

ModuAgent 采用五层可插拔架构（Perception → Reasoning → Memory → Action → Feedback），由 `Coordinator` 统一编排，`ComponentRegistry` 管理组件生命周期，`EventBus` 传递事件。感知层在整体数据流中的位置：

```
用户输入 → Coordinator.process_request()
  ├─ [1] 感知层: TextPreprocessor.perceive() → 清洗/检测/截断
  ├─ [2] 敏感词熔断: sensitivity_level >= threshold → 直接拒绝
  ├─ [3] 构建感知事件: AgentEvent(domain=PERCEPTION) → EventBus
  ├─ [4] 记忆层: StorageAdapter.query_all()
  ├─ [5] 推理层: LLMAdapter.generate()
  └─ [6] 行动层: ToolAdapter / ActionExecutor
```

### 1.2 感知层当前实现文件清单

| 文件 | 状态 | 说明 |
|------|------|------|
| `core/interfaces/perception.py` | 已实现 | 定义 `BasePerception`（被动感知）和 `BaseSensor`（主动感知）两个抽象接口 |
| `components/perception/text/rule_based.py` | 已实现 | `TextPreprocessor`：解码、截断、语言检测、敏感词匹配，共 95 行 |
| `components/perception/text/llm_parser.py` | **空文件** | 预留的 LLM 深度解析器，未实现 |
| `components/perception/vision/camera.py` | **空文件** | 预留的摄像头采集器，未实现 |
| `components/perception/vision/image_processor.py` | **空文件** | 预留的图像处理器，未实现 |
| `config/schemas.py` | 已实现 | `PerceptionInputSchema` / `PerceptionOutputSchema`，声明支持 text/image/audio |
| `config/runtime_config.py` | 已实现 | `default_processor = "text_preprocessor"`，`sensitivity_threshold = 5` |
| `core/registry.py` | 已实现 | 支持 `register_perception()` / `register_sensor()`，但 `sensor` 仅在 `list_all()` 中暴露 |
| `orchestration/coordinator.py` | 已实现 | 感知层调用入口（L38-L80），仅使用 `parsed_content.text` 和 `sensitivity_level` |

## 二、11 个问题逐项分析与优化方案

### 问题 1：多模态感知基本未实现

**根因分析：**

- `llm_parser.py`、`camera.py`、`image_processor.py` 均为空文件，属于架构预留但未开发的占位模块。
- `TextPreprocessor.perceive()` 在 `input_type != "text"` 时直接返回错误，没有任何降级或路由逻辑。
- `PerceptionInputSchema` 虽声明支持 `text/image/audio` 三种类型，但 `Coordinator` 只调用 `text_preprocessor`，且无 fallback 机制。

**优化方案：**

| 阶段 | 措施 | 涉及文件 |
|------|------|----------|
| **短期（P0）** | 实现 `llm_parser.py`：基于 LLM 的多模态解析器，将 image/audio 输入转为文本描述后再走文本处理管线 | `llm_parser.py`（新建实现） |
| **短期（P0）** | 实现 `image_processor.py`：集成 OCR（如 Tesseract/EasyOCR）+ 场景描述（如 BLIP/CLIP），返回结构化感知结果 | `image_processor.py`（新建实现） |
| **中期（P1）** | 实现 `camera.py`：基于 OpenCV 的实时帧捕获，对接 `image_processor` | `camera.py`（新建实现） |
| **中期（P1）** | 新增 `audio/` 子模块：集成 Whisper/ASR 进行语音转文字，再走文本管线 | `components/perception/audio/`（新建） |
| **架构层面** | 在 `Coordinator` 中增加输入类型路由：根据 `input_type` 动态选择感知器，非 text 类型先经对应模态解析器转为文本，再走 `TextPreprocessor` | `coordinator.py` |

**关键代码变更示意（Coordinator 路由逻辑）：**

```python
# coordinator.py 中 process_request 的感知阶段改造
PERCEPTION_ROUTER = {
    "text": "text_preprocessor",
    "image": "image_processor",
    "audio": "audio_processor",
}

perception_name = config.get(
    f"perception.{PERCEPTION_ROUTER.get(input_type, 'text_preprocessor')}",
    "text_preprocessor"
)
perception = self._registry.get_perception(perception_name)
```

### 问题 2：感知深度不足，停留在"清洗"而非"理解"

**根因分析：**

当前 `perceive()` 方法仅做 4 件事：字节解码 → Unicode 归一化 → 截断 → 敏感词匹配。输出结构虽定义了 `confidence` 字段，但恒为 `1.0`，无真实置信度计算。`TextPreprocessor` 本质是一个"输入清洗器"而非"语义理解器"，缺少所有 NLU 能力。

**优化方案：**

| 能力 | 实现方式 | 优先级 |
|------|----------|--------|
| **意图识别** | 轻量级方案：基于 Sentence-BERT 的 embedding + 余弦相似度与预定义意图库匹配；重量级方案：调用小模型（如 Qwen2.5-0.5B）做 zero-shot/few-shot 分类 | P0 |
| **命名实体抽取（NER）** | 集成 spaCy / HanLP 做实体识别，支持人名、地名、组织、日期、金额等通用实体 | P1 |
| **情感/情绪检测** | 基于 SnowNLP / TextBlob 或蒸馏模型（如 DistilBERT fine-tuned on sentiment） | P1 |
| **输入质量评估** | 定义质量分（模糊度、信息量、参数完整度），基于启发式规则（如疑问词密度、有效词占比、语句长度）计算 | P1 |
| **语种混淆处理** | 检测中英混用比例，标记 `mixed_language` 标志，当混用比例 >30% 时降低 confidence | P1 |
| **真实置信度** | 综合语言检测置信度、敏感词匹配置信度、输入质量分的加权平均，替代恒为 1.0 的硬编码 | P0 |

**新增 `PerceptionOutputSchema` 扩展字段：**

```python
@dataclass
class PerceptionOutputSchema:
    parsed_content: Dict[str, Any] = field(default_factory=dict)
    detected_language: Optional[str] = None
    confidence: float = 0.0  # 改为真实计算值
    metadata: Dict[str, str] = field(default_factory=dict)

    # 新增字段
    intent: Optional[Dict[str, float]] = None        # {"意图名": 置信度}
    entities: List[Dict[str, str]] = field(default_factory=list)  # [{"text":..., "label":...}]
    sentiment: Optional[Dict[str, float]] = None     # {"positive": 0.8, "negative": 0.1, "neutral": 0.1}
    quality_score: float = 0.0                        # 0~1，输入质量
    language_mixed: bool = False                      # 是否存在语种混淆
```

### 问题 3：语言检测算法粗糙

**根因分析：**

当前 `_detect_language()` 仅统计 CJK 统一汉字区间（U+4E00-U+9FFF, U+3400-U+4DBF, U+3000-U+303F）和拉丁字母区间（U+0041-U+007A, U+00C0-U+024F）的字符数，以数量比较决定返回 `"zh"` 还是 `"en"`。缺陷：

1. 日文平假名/片假名（U+3040-U+309F, U+30A0-U+30FF）不在 CJK 统计范围，会被 fallback 到默认语言
2. 韩文（U+AC00-U+D7AF）完全未被覆盖
3. 阿拉伯文（U+0600-U+06FF）、西里尔文（U+0400-U+04FF）等未被覆盖
4. Emoji 密集文本（如社交媒体内容）会干扰统计，因为 emoji 不属于任何语言区间
5. 中英混合文本（如"这个 feature 很 nice"）可能误判，因为没有语种混合度指标

**优化方案：**

| 阶段 | 方案 | 说明 |
|------|------|------|
| **短期（P0）** | 扩展 Unicode 区间覆盖 | 增加日文（平假名、片假名、CJK扩展）、韩文（谚文音节）、阿拉伯文、西里尔文、泰文、天城文的区间 |
| **短期（P0）** | 增加 Emoji 过滤 | 在统计前先用 `emoji` 库或正则去掉 emoji 字符，避免干扰 |
| **中期（P1）** | 集成轻量语种检测库 | 使用 `langdetect`（Google 语种检测的 Python 移植）或 `fasttext`（Facebook 的 176 语种模型），它们基于 n-gram 统计，准确率远高于 Unicode 计数 |
| **中期（P1）** | 返回置信度 | 不返回单一语种，而是返回 `{"zh": 0.65, "en": 0.30, "mixed": 0.05}` 式的分布，让下游自行决策 |
| **长期（P2）** | 语种感知的后续处理 | 根据检测到的语种自动选择对应的 NER 模型、情感分析模型 |

**推荐实现（langdetect 集成）：**

```python
# 在 TextPreprocessor 中新增方法
def _detect_language_robust(self, text: str) -> Dict[str, float]:
    """
    使用 langdetect 做语种检测，返回各语种概率分布。
    当 top-1 概率 < 0.7 时标记为 mixed。
    """
    from langdetect import DetectorFactory, detect_langs
    DetectorFactory.seed = 0  # 保证可复现
    try:
        langs = detect_langs(text)
        result = {lang.lang: lang.prob for lang in langs}
        return result
    except Exception:
        return {self._language: 1.0}
```

### 问题 4：敏感词检测简单粗暴，误伤率高

**根因分析：**

当前 `_detect_sensitivity()` 的逻辑：遍历固定正则列表，命中任一模式即返回 `5`（最高敏感度），否则返回 `0`。问题：

1. 正则 `password` 使用 `re.search` 会匹配 `passwordless`、`password_reset` 等无害词
2. 正则 `银行卡` 无法区分"忘记银行卡密码"（正常求助）和"帮我查银行卡余额"（敏感操作）
3. 敏感度只有二值（0/5），无法区分"需要确认"和"直接拒绝"
4. 无上下文语义，容易被"银 行 卡"、"yin hang ka"、"yhk" 等变体绕过

**优化方案：**

| 措施 | 实现方式 | 优先级 |
|------|----------|--------|
| **词边界匹配** | 对中文关键词使用 `(?<!\w)` 和 `(?!\w)` 边界，对英文关键词使用 `\b` 边界 | P0 |
| **细粒度分级** | 将敏感度从 `{0, 5}` 扩展为 `{0: 安全, 1: 注意, 2: 敏感, 3: 高风险, 4: 需人工审核, 5: 直接拒绝}` | P0 |
| **上下文语义判断** | 将敏感词检测从纯正则升级为"正则初筛 + LLM 二次判断"：正则命中后，用轻量 prompt 让 LLM 判断上下文是否真的存在敏感操作意图 | P1 |
| **变体检测** | 增加拼音/谐音/拆字归一化预处理：将常见变体还原为原文后再检测 | P1 |
| **白名单机制** | 支持配置白名单（如特定用户、特定场景、特定短语），命中白名单直接跳过敏感检测 | P1 |
| **分级响应策略** | 不同敏感度对应不同处理：0-1 正常放行，2-3 标记 metadata 但继续，4 触发二次确认，5 直接拒绝 | P0 |

**关键代码变更示意（细粒度分级）：**

```python
# 敏感度分级定义
SENSITIVITY_LEVELS = {
    0: "safe",           # 无敏感内容
    1: "notice",         # 含可能敏感词，但上下文安全
    2: "sensitive",      # 含敏感词，需标记
    3: "high_risk",      # 高风险，需降级处理
    4: "review",         # 需人工审核
    5: "block",          # 直接拒绝
}

# 多层正则分类
SENSITIVITY_PATTERNS = {
    5: [  # 直接拒绝级
        r'\b(?:password|passwd)\s*[=:]\s*\S+',  # 密码明文泄露
    ],
    3: [  # 高风险级
        r'(?<!\w)(?:银行卡|身份证|passport)(?!\w)',
    ],
    1: [  # 注意级
        r'(?<!\w)(?:密码|password)(?!\w)',
    ],
}
```

### 问题 5：安全防护面窄

**根因分析：**

当前安全防护仅有关键词级别的敏感检测，且判断逻辑完全在 `_detect_sensitivity()` 中。整个 ModuAgent 框架缺少系统性的安全防护层，包括但不限于：

- 无 Prompt Injection 检测
- 无越狱攻击（Jailbreak）检测
- 无 XSS/SQL/命令注入清洗
- 无 PII（个人隐私信息）结构化识别

**优化方案：**

| 安全能力 | 实现方式 | 优先级 |
|----------|----------|--------|
| **Prompt Injection 检测** | 集成 `llm-guard` 或自建检测器：检测"忽略之前的指令"、"你现在是 DAN"、"system prompt 泄露"等模式 | P0 |
| **越狱攻击检测** | 维护越狱攻击模式库（如角色扮演绕过、编码绕过、多语言绕过），正则 + embedding 相似度匹配 | P0 |
| **注入攻击清洗** | 对输入中的 HTML 标签、SQL 关键字、Shell 命令模式做转义或标记，不直接拒绝而是标记 `metadata.injection_risk` | P1 |
| **PII 识别** | 集成 `presidio`（Microsoft 开源）或正则模式库：识别手机号、身份证号、银行卡号、邮箱、IP 地址等，标记 `metadata.pii_detected` | P1 |
| **安全评分** | 综合敏感词、注入风险、PII 检测结果，计算 `security_score`（0~1），作为 `confidence` 的重要因子 | P0 |

**新增安全检测器模块（建议新建 `components/perception/security/`）：**

```python
class SecurityGuard:
    """统一安全检测器，在 TextPreprocessor 之前/内部调用"""
    
    def detect_injection(self, text: str) -> Dict[str, Any]:
        """检测 Prompt Injection / Jailbreak 尝试"""
        ...
    
    def detect_pii(self, text: str) -> Dict[str, Any]:
        """检测 PII 信息"""
        ...
    
    def sanitize(self, text: str) -> Tuple[str, Dict[str, Any]]:
        """清洗 XSS/SQL/命令注入"""
        ...
```

### 问题 6：截断策略生硬

**根因分析：**

当前 `_decode_and_truncate()` 在 `len(text) > max_length` 时直接执行 `text[:max_length]`，存在以下风险：

1. **语义断裂**：在中文字符边界截断可能产生不完整的词语
2. **JSON 结构破坏**：如果输入是 JSON 格式，截断后可能缺少闭合括号，导致下游解析失败
3. **HTML 结构破坏**：可能在标签中间截断
4. **实体被切开**：如"中华人民共和国"可能在"中华人"处截断
5. **无截断位置标记**：下游无法知道截断发生的位置

**优化方案：**

| 措施 | 实现方式 | 优先级 |
|------|----------|--------|
| **智能截断** | 在 `max_length` 附近寻找最近的句子边界（。！？.!?\n）或词边界进行截断 | P0 |
| **JSON 感知截断** | 检测输入是否为 JSON，若是则按 JSON 结构截断（保留完整 key-value 对），并在最后补 `}` 标记 | P1 |
| **截断摘要** | 当截断发生时，用 LLM 对被截断部分生成简短摘要，附加到截断后的文本末尾 | P2 |
| **截断元数据** | 记录截断位置、截断比例、截断原因（按句子/按词/按字符），存入 `metadata.truncation_info` | P0 |

**关键代码变更示意：**

```python
def _truncate_smart(self, text: str, max_length: int) -> tuple[str, bool, Dict]:
    """智能截断：在句子边界截断，避免语义断裂"""
    if len(text) <= max_length:
        return text, False, {}
    
    # 在 max_length 附近寻找最近的句子边界
    truncated = text[:max_length]
    sentence_boundaries = ['. ', '。', '！', '？', '! ', '? ', '\n', '\r\n']
    
    best_pos = max_length
    for boundary in sentence_boundaries:
        pos = truncated.rfind(boundary)
        if pos > max_length * 0.8:  # 至少保留 80%
            best_pos = min(best_pos, pos + len(boundary))
    
    if best_pos < max_length:
        truncated = text[:best_pos]
    
    info = {
        "truncated": True,
        "original_length": len(text),
        "truncated_length": len(truncated),
        "truncation_ratio": round(len(truncated) / len(text), 2),
        "method": "sentence_boundary",
    }
    return truncated, True, info
```

### 问题 7：感知结果未被下游充分利用

**根因分析：**

在 `coordinator.py` L38-L80 中，感知结果的使用非常有限：

```python
# 仅使用了 parsed_content.text 和 sensitivity_level
cleaned_text = perception_result["parsed_content"].get("text")
detected_level = perception_result.get("metadata", {}).get("sensitivity_level", 0)
```

而 `detected_language`、`confidence`、`metadata` 中的其他字段完全没有被消费。`PerceptionEvent` 的 metadata 也只记录了 `input_type`、`sensitivity_level`、`truncated` 三个字段。

**优化方案：**

| 措施 | 实现方式 | 优先级 |
|------|----------|--------|
| **感知结果注入 LLM Context** | 将 `detected_language`、`confidence`、`intent`、`entities`、`sentiment`、`quality_score` 注入到 LLM 的 system prompt 或 context 中，让推理层感知输入质量 | P0 |
| **感知结果影响推理策略** | 低 confidence 时启用保守模式（降低 temperature、增加验证步骤）；高 sensitivity 时切换为安全模型；语种混合时启用多语言 prompt | P1 |
| **感知结果写入事件** | `PerceptionEvent` 的 metadata 扩充为包含所有感知输出字段 | P0 |
| **感知结果影响记忆存储** | 将 `intent`、`entities`、`sentiment` 作为记忆的索引标签，提升后续检索精度 | P1 |

**关键代码变更示意（Coordinator 感知结果消费）：**

```python
# coordinator.py 中 process_request 改造
if perception_result:
    cleaned_text = perception_result["parsed_content"].get("text")
    detected_level = perception_result.get("metadata", {}).get("sensitivity_level", 0)
    
    # 将感知结果注入 LLM context
    perception_context = {
        "detected_language": perception_result.get("detected_language"),
        "confidence": perception_result.get("confidence"),
        "intent": perception_result.get("intent"),
        "entities": perception_result.get("entities"),
        "sentiment": perception_result.get("sentiment"),
        "quality_score": perception_result.get("quality_score"),
    }
    context["perception"] = perception_context
    
    # 低置信度 → 降低 temperature
    if perception_result.get("confidence", 1.0) < 0.5:
        config.set("llm.temperature", 0.3)  # 保守模式

# PerceptionEvent 扩展
perception_event = AgentEvent(
    domain=EventDomain.PERCEPTION,
    action=EventAction.ANALYZE,
    metadata={
        "input_type": input_data.get("input_type", "text"),
        "sensitivity_level": str(detected_level),
        "truncated": str(truncated),
        "detected_language": str(perception_result.get("detected_language", "")),
        "confidence": str(perception_result.get("confidence", 1.0)),
        "original_length": str(perception_result.get("metadata", {}).get("original_length", 0)),
        "intent": json.dumps(perception_result.get("intent", {})),
        "quality_score": str(perception_result.get("quality_score", 0.0)),
    },
)
```

### 问题 8：`BaseSensor` 接口闲置

**根因分析：**

`core/interfaces/perception.py` 中定义了 `BaseSensor`（主动感知）和 `BasePerception`（被动感知）两个接口：

- `BasePerception`：被动响应输入，`perceive(input_type, raw_content, ...)` → 已被 `TextPreprocessor` 实现
- `BaseSensor`：主动采集数据，`capture(context)` → 无任何实现，`Coordinator` 和 registry 中均未集成

`ComponentRegistry` 有 `register_sensor()` 和 `get_sensor()` 方法，但 `Coordinator` 从未调用。`BaseSensor` 的设计意图是支持定时抓取、摄像头、麦克风等主动感知场景，但当前完全被架空。

**优化方案：**

| 措施 | 实现方式 | 优先级 |
|------|----------|--------|

```python
# coordinator.py 新增 Sensor 管理
class Coordinator:
    def __init__(self):
        ...
        self._sensor_tasks: Dict[str, asyncio.Task] = {}
    
    async def start_sensors(self, sensor_names: List[str]) -> None:

                action=EventAction.ANALYZE_SCENE,
                payload=raw_data,
                metadata={"sensor_type": sensor.sensor_type()},
            )
            await self._event_bus.publish(event)
            await asyncio.sleep(1.0)  # 采集间隔
```

### 问题 9：缺乏输入路由与多感知融合

**根因分析：**

当前有两个层面的路由缺失：

1. **输入类型路由缺失**：`config.runtime_config.py` 中 `default_processor = "text_preprocessor"` 是写死的，`Coordinator` 直接取这个名字，不根据 `input_type` 动态选择
2. **多路感知融合缺失**：当同一输入有多个感知器处理（如同时有文本 + 图像 + 音频），没有融合机制将多路结果合并

**优化方案：**

| 措施 | 实现方式 | 优先级 |
|------|----------|--------|
| **输入类型路由** | 在配置中增加 `perception.routing` 映射表，`Coordinator` 根据 `input_type` 查表选择感知器 | P0 |
| **感知器链（Pipeline）** | 支持多个感知器串行/并行处理：如先 `ImageProcessor` 提取文字，再 `TextPreprocessor` 清洗 | P1 |
| **多路融合器（Fusion）** | 实现 `PerceptionFusion` 组件，将多路感知结果按权重融合，输出统一的 `PerceptionOutputSchema` | P1 |
| **配置化路由规则** | 支持在配置中定义路由规则，如 `{"input_type": "image", "pipeline": ["image_processor", "text_preprocessor"]}` | P1 |

**关键代码变更示意（路由配置）：**

```python
# runtime_config.py 中 DEFAULT_CONFIG 扩展
"perception": {
    "default_processor": "text_preprocessor",
    "max_length": 2048,
    "sensitivity_threshold": 5,
    "routing": {
        "text": {
            "pipeline": ["text_preprocessor"],
        },
        "image": {
            "pipeline": ["image_processor", "text_preprocessor"],

        "audio": {
            "pipeline": ["audio_processor", "text_preprocessor"],

    "fusion": {
        "strategy": "weighted_average",  # weighted_average | max_confidence | voting
        "weights": {"text": 0.4, "image": 0.35, "audio": 0.25},

},

# coordinator.py 中路由逻辑
routing = config.get("perception.routing", {})
pipeline = routing.get(input_type, {}).get("pipeline", ["text_preprocessor"])

    perception = self._registry.get_perception(processor_name)

        result = perception.perceive(...)
```

### 问题 10：编码与清洗细节问题

**根因分析：**

当前 `_decode_and_truncate()` 方法存在以下细节问题：

1. **UnicodeDecodeError 处理粗糙**：`errors="replace"` 会将无法解码的字节替换为 U+FFFD（），但没有任何标记或告警，可能把乱码送入 LLM
2. **缺少控制字符清洗**：如 `\x00`（NULL）、`\x08`（退格）、`\x1B`（ESC）等控制字符未被过滤
3. **缺少零宽字符清洗**：如 U+200B（零宽空格）、U+200C（零宽非连接符）、U+FEFF（BOM）等可能干扰 LLM 的 tokenization
4. **缺少重复字符检测**：如"好好好好好好好" 或 "AAAAAAA" 这种可能触发 LLM 异常行为的输入
5. **缺少过度大写检测**：全大写英文可能表示强调或攻击意图
6. **缺少不可见字符清洗**：如 U+202E（RTL Override）等方向控制字符可能被用于 prompt injection 攻击

**优化方案：**

| 措施 | 实现方式 | 优先级 |
|------|----------|--------|
| **解码异常标记** | 当使用 `errors="replace"` 时，在 `metadata.decoding_errors` 中记录，并记录替换次数 | P0 |
| **控制字符过滤** | 新增 `_sanitize_text()` 方法，过滤 ASCII 控制字符（0x00-0x1F，保留 \t\n\r） | P0 |
| **零宽字符过滤** | 过滤 Unicode 零宽字符类别（`unicodedata.category(char) == 'Cf'`） | P0 |
| **重复字符压缩** | 当同一字符连续出现 >5 次时，压缩为最多 3 次重复 | P1 |
| **过度大写归一化** | 当大写字母占比 >70% 时，标记 `metadata.excessive_uppercase`，可选择性地转为小写 | P1 |
| **方向控制字符过滤** | 过滤 Unicode 双向控制字符（U+202A-U+202E, U+2066-U+2069） | P0 |

**关键代码变更示意：**

```python
import unicodedata

# 需过滤的字符类别
_STRIP_CATEGORIES = {'Cc', 'Cf', 'Co', 'Cs'}  # 控制字符、格式字符、私有区、代理区
_KEEP_CHARS = {'\t', '\n', '\r'}  # 保留的空白控制字符

def _sanitize_text(self, text: str) -> tuple[str, Dict[str, Any]]:
    """清洗文本中的控制字符、零宽字符、方向控制字符"""
    sanitized = []
    warnings = {
        "stripped_control_chars": 0,
        "stripped_zero_width": 0,
        "stripped_bidi_chars": 0,
        "decoding_replacements": 0,
    }
    
    for char in text:
        cp = ord(char)
        cat = unicodedata.category(char)
        
        # 保留的空白控制字符
        if char in _KEEP_CHARS:
            sanitized.append(char)
            continue
        
        # 过滤其他控制字符/格式字符
        if cat in _STRIP_CATEGORIES:
            if cat == 'Cf':
                warnings["stripped_zero_width"] += 1
            else:
                warnings["stripped_control_chars"] += 1
            continue
        
        # 过滤双向控制字符
        if 0x202A <= cp <= 0x202E or 0x2066 <= cp <= 0x2069:
            warnings["stripped_bidi_chars"] += 1
            continue
        
        sanitized.append(char)
    
    return "".join(sanitized), warnings
```

### 问题 11：事件追踪信息不完整

**根因分析：**

当前在 `coordinator.py` L91-L101 构建的 `PerceptionEvent` 只记录了 3 个字段：

```python
perception_event = AgentEvent(

```

缺失的关键字段：`detected_language`、`confidence`、`original_length`、`intent`、`entities`、`quality_score`、`security_score`、`decoding_errors`、`truncation_info` 等。

这些字段的缺失导致：
1. **可观测性不足**：无法从事件日志中追溯某次请求的输入质量、语种、安全状态

**优化方案：**

| 措施 | 实现方式 | 优先级 |
|------|----------|--------|
| **事件字段标准化** | 定义 `PerceptionEventMetadata` 标准结构，包含所有感知输出字段 | P0 |
| **EventBus 日志持久化** | 将 `EventBus._event_log` 定期写入 `StorageAdapter`，支持历史查询和统计分析 | P1 |
| **感知层 Dashboard** | 基于事件日志构建感知层监控面板，展示置信度分布、语种分布、敏感词命中率、截断率等 | P2 |
| **进化信号联动** | `evolution/` 模块订阅 `PERCEPTION` 域事件，当质量指标持续低于阈值时自动触发组件替换或参数调优 | P1 |

```python
# 在 perception/__init__.py 中定义标准事件构建函数
def build_perception_event_metadata(
```

## 四、关键风险与注意事项

1. **性能影响**：新增 NER、情感分析、PII 检测等会增加感知层延迟。建议：
   - 所有 NLU 模块默认异步执行，结果通过 `asyncio.gather` 并行获取
   - 提供开关配置，允许按场景选择性启用
   - 为每个模块设置超时（如 500ms），超时则降级跳过

2. **兼容性**：`PerceptionOutputSchema` 扩展字段需保持向后兼容，下游代码（如 `Coordinator`）应对新字段做 `get()` 安全取值

3. **依赖管理**：新增 `langdetect`、`spaCy`、`presidio` 等依赖需在 `pyproject.toml` 中声明为可选依赖（`extras`），避免强制安装

4. **敏感词误伤**：分级方案实施后，需建立敏感词测试用例库，验证各类边界场景（正常提及 vs 敏感操作）

5. **LLM 成本**：当引入 LLM 做敏感词二次判断或输入质量评估时，需注意成本控制 —— 建议使用轻量模型（如 0.5B-1.5B 参数），或仅在正则初筛命中后才调用 LLM
