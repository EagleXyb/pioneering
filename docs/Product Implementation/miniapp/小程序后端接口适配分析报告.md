## 三、关键适配问题详解

### 问题 1：SSE 流式数据类型不匹配 【致命】

后端 SSE 输出的类型字段与小程序解析期望不匹配：

| 来源 | Thinking 类型 | Answer 类型 | Done 类型 |
|------|:---:|:---:|:---:|
| **后端输出** | `"thinking"` | `"answer"` | `"done"` |
| **小程序期望** | `"thinking"` | `"content"` | `"done"` |

**代码位置**：

- 后端：[llm.service.ts](file:///c:/Users/HS/Desktop/pioneering/backend/src/api-v1/common/llm.service.ts#L261-L280) — `res.write({ type: 'answer', content })`
- 小程序：[sse.ts](file:///c:/Users/HS/Desktop/pioneering/miniprogram/src/services/sse.ts#L24-L30) — `parsed.type || 'content'`
- 小程序类型：[chat.ts](file:///c:/Users/HS/Desktop/pioneering/miniprogram/src/types/chat.ts#L58-L62) — `type: 'thinking' | 'content' | 'error' | 'done'`

**影响**：小程序 `SSEChunk` 类型定义中没有 `"answer"` 类型。后端发出的 `{ type: "answer", content: "..." }` 会被 `parseSSELine` 解析为 `type: "answer"`，在 TS 层面类型不匹配，运行时虽不报错（`parsed.type || 'content'` 会返回 `"answer"`），但后续 `useSSE` 中只处理 `thinking` 和 `content` 分支，`"answer"` 类型会被忽略。

```typescript
// useSSE.ts 中的分支处理——缺少 "answer" 分支
if (data.type === 'thinking') {
  setThinkingContent((prev) => prev + data.data);
} else {
  setStreamingContent((prev) => prev + data.data);
}
// 运行时这里 data.type 是 "answer"，会走到 else 分支 → 勉强能用但不正确
```

**同时也存在兜底解析覆盖**：`parseSSELine` 有 `<thinking>...</thinking>` 兜底正则，但后端如果走路径 A（`reasoning_content`），不会输出 `<thinking>` 标签，而是分别输出 `type: "thinking"` 和 `type: "answer"`。

**修复建议**：
1. 统一类型：将小程序 `SSEChunk.type` 从 `'content'` 改为 `'answer'`，或后端改为输出 `type: 'content'`
2. 推荐方案：`shared/types/` 中统一定义 SSE 事件类型，两端引用同一份类型

### 问题 2：认证机制缺口 【致命】

- 后端所有 `/chat/*` 接口由 `JwtAuthGuard` 全局守卫保护（[common.module.ts](file:///c:/Users/HS/Desktop/pioneering/backend/src/api-v1/common/common.module.ts#L18-L21)），需要 `Authorization: Bearer <token>` 头
- 后端已提供小程序专用登录接口 `POST /auth/wechat/miniprogram`（[auth.controller.ts](file:///c:/Users/HS/Desktop/pioneering/backend/src/api-v1/auth/auth.controller.ts#L16-L19)）
- 小程序的 `request.ts` 已经有从 Storage 取 token 并附加到请求头的逻辑（[request.ts](file:///c:/Users/HS/Desktop/pioneering/miniprogram/src/services/request.ts#L42-L47)）
- 但是小程序**没有调用登录接口获取 token 的代码**，也没有登录页面
- `sse.ts` 中的 Taro.request 调用**没有传递 Authorization 头**（[sse.ts](file:///c:/Users/HS/Desktop/pioneering/miniprogram/src/services/sse.ts#L86-L95)）

**影响**：关闭 Mock 后，所有真实 API 调用将因 401 被拒绝。

**修复建议**：
1. 小程序端添加微信登录流程：`wx.login()` → 获取 `code` → `POST /auth/wechat/miniprogram` → 获取 `token` + `refreshToken` → 存入 Storage
2. `sse.ts` 的 `Taro.request` 中添加 `Authorization: Bearer ${token}` 请求头
3. 实现 token 过期自动刷新机制（`POST /auth/refresh`）

### 问题 3：会话管理完全本地化 【高】

小程序使用 Zustand 本地 Store 管理会话，不与后端同步：

| 方面 | 后端 | 小程序 |
|------|------|--------|
| 存储位置 | PostgreSQL (`chat_sessions` 表) | Zustand Store（内存，仅 Session 级别） |
| ID 格式 | `sess_` + 随机字符串 | `session_${Date.now()}` |
| 数据结构 | `id, userId, title, model, systemPrompt, messageCount, ...` | `id, title, preview, updatedAt` |
| 消息关联 | `sessionId` 外键 | `messagesMap[sessionId]` |

**影响**：
- 小程序创建的会话不会持久化到后端，刷新/关闭后丢失
- 启动小程序不会从后端加载历史会话列表
- `sessionId` 格式不一致，后端可能拒绝格式不匹配的 ID

**修复建议**：
1. 小程序启动时调用 `GET /chat/sessions` 加载用户的历史会话
2. 发送消息前调用 `POST /chat/sessions` 创建会话，使用后端返回的 `sessionId`
3. 进入历史会话时调用 `GET /chat/sessions/:sessionId/messages` 加载历史消息
4. 统一 `SessionItem` 数据结构为后端返回格式

### 问题 4：响应格式不匹配 【高】

后端使用 NestJS 默认 JSON 序列化，直接返回数据对象：

```json
// 后端 GET /user/profile 的响应
{ "id": "user_xxx", "username": "wx_xxx", "nickname": "微信用户", ... }
```

小程序 `request.ts` 期望标准包装格式：

```typescript
// request.ts 期望的格式
export interface ApiResponse<T = unknown> {
  code: number;
  data: T;
  message: string;
}
// 解析逻辑：data.data → 即 ApiResponse.data
```

后端返回的原始对象会被赋给 `response.data`（Taro 请求的 `data` 字段），`request.ts` 尝试取 `(response.data as ApiResponse).data`，得到 `undefined`。

同时 `request.ts` 检查 `data.code !== 0 && data.code !== 200`，后端未返回 `code` 字段，`data.code` 为 `undefined`，不等于 `0` 也不等于 `200`，会抛异常。

**影响**：所有非 Mock 请求全部失败。

**修复建议**：
- **方案 A（推荐）**：后端添加全局响应拦截器，包装为 `{ code: 200, data: ..., message: 'success' }`
- **方案 B**：小程序 `request.ts` 适配后端裸返回格式

### 问题 5：SSE 请求参数不匹配 【中】

#### 5.1 `deepThink` / `netSearch` 参数

小程序 `SSEParams` 包含 `deepThink` 和 `netSearch` 字段：

```typescript
// 小程序类型
export interface SSEParams {
  sessionId: string;
  content: string;
  messageId: string;
  deepThink?: boolean;
  netSearch?: boolean;
}
```

但后端 `ChatCompletionDto` 没有这两个字段，发送后会被 `ValidationPipe` 的 `whitelist: true` 过滤掉（不过 `forbidNonWhitelisted: false` 所以不会报错）。

#### 5.2 `messageId` 参数

小程序 `SSEParams` 有 `messageId`，后端没有对应字段。如果后端需要提前创建占位消息 ID，需要新增此字段。

#### 5.3 发送 payload 对比

```typescript
// 小程序 sse.ts 发送的数据
{ sessionId, message: content, stream: true }

// 后端 ChatCompletionDto 期望
{ sessionId?, message, model?, systemPrompt?, temperature?, maxTokens?, stream?, parentMessageId? }
```

字段名 `message` ↔ `message` 一致 ✅，但缺少 `deepThink`, `netSearch`, `messageId`。

**修复建议**：
1. 后端 `ChatCompletionDto` 新增可选字段 `deepThink?: boolean`, `netSearch?: boolean`, `messageId?: string`
2. 或在 `shared/types/chat.ts` 中统一定义请求参数

### 问题 6：停止生成接口参数缺失 【中】

```typescript
// 小程序 api.ts
stopMessage(sessionId: string) {
  return request.post('/chat/completions/stop', { sessionId });
}
```

```typescript
// 后端 StopGenerationDto
class StopGenerationDto {
  sessionId: string;   // @IsString @IsNotEmpty
  messageId: string;   // @IsString @IsNotEmpty  ← 小程序没传！
}
```

后端 `StopGenerationDto` 中 `messageId` 是必填字段，小程序只传了 `sessionId`。且后端 `stopGeneration` 方法使用 `messageId` 查找 `activeStreams`（[chat.service.ts](file:///c:/Users/HS/Desktop/pioneering/backend/src/api-v1/chat/chat.service.ts#L538-L542)）。

**影响**：`POST /chat/completions/stop` 将因参数校验失败返回 400。

**修复建议**：
1. 小程序 `stopMessage` 增加 `messageId` 参数
2. 调用方传入当前 AI 消息的 ID

---

### 问题 7：重新生成接口参数不匹配 【低】

```typescript
// 小程序 api.ts
regenerate(messageId: string) {
  return request.post(`/chat/messages/${messageId}/regenerate`);
}
```

后端 `POST /chat/messages/:messageId/regenerate` 的 `messageId` 应该是**被重新生成的 AI 消息的父消息（用户消息）的 ID**，即 `parentMessageId`。小程序传的 `messageId` 是 AI 消息的 ID，但后端 `regenerate` 方法中使用 `findUnique({ where: { id: parentMessageId } })` 查找（[chat.service.ts](file:///c:/Users/HS/Desktop/pioneering/backend/src/api-v1/chat/chat.service.ts#L556-L568)）。

**影响**：如果传 AI 消息 ID 而非用户消息 ID，将找不到记录返回 404。

**修复建议**：小程序调用方传入对应**用户消息**的 ID。

## 四、数据结构差异对照

| 字段名 | 后端 (Prisma) | 小程序 | 是否对齐 |
|--------|:---:|:---:|:---:|
| 消息 ID | `id` (如 `msg_xxx`) | `id` (如 `msg_${Date.now()}`) | 格式不同 |

| 思考内容 | 无独立字段（含在 content） | `thinkingContent?: string` | 缺失 |
| 状态 | 无（通过存在性判断） | `status: MessageStatus` | 缺失 |
| 时间戳 | `createdAt` / `updatedAt` (DateTime) | `timestamp: number` | 类型不同 |
| 会话 ID | `id: "sess_xxx"` | `sessionId: "session_${Date.now()}"` | 格式不同 |
| 回复格式 | `{ id, sessionId, model, choices, usage, ... }` | `{ message: { id, content, type } }` | 完全不同 |

## 五、Mock 层分析

小程序当前通过两个开关完全绕过真实接口：

1. **[request.ts](file:///c:/Users/HS/Desktop/pioneering/miniprogram/src/services/request.ts#L6)**: `USE_MOCK = true`
   - 只 mock 了 `/chat/completions` 非流式接口

2. **[useSSE.ts](file:///c:/Users/HS/Desktop/pioneering/miniprogram/src/hooks/useSSE.ts#L7)**: `USE_MOCK = true`
   - 本地模拟流式输出（`generateMockStream`）
   - 支持 simulation thinking + answer
   - 完全绕过 `sse.ts` 中的真实请求

Mock 的 `generateMockStream` 输出 `{ type: 'thinking', data }` 和 `{ type: 'content', data }`，与后端真实 SSE 的 `{ type: 'answer' }` 不匹配——但因为是 Mock 所以没问题，一换真就出问题。
