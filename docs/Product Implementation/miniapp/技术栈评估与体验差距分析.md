## 二、对标大厂水准的亮点 ✅

### 2.1 设计 Token 体系
`app.scss` 中定义了完整的设计变量体系，使用语义化命名（`$color-primary`、`$color-text-secondary` 等），这与大厂的 Design Token 实践方向一致。

### 2.2 动画细节到位
多处实现了细腻的微交互动效：

| 动效 | 实现位置 | 技术细节 |
|------|----------|----------|
| 流式光标闪烁 | `MessageBubble.scss` | `cubic-bezier(0.4, 0, 0.6, 1)` |
| 打字三点弹跳 | `MessageBubble.scss` | `animation-delay` 错位实现 |
| 底部弹窗展开 | `ModeSheet.scss` | `cubic-bezier(0.32, 0.72, 0, 1)` |
| 模式切换滑块 | `EmptyState.scss` | CSS 变量 + `translateX` |
| 分段控件 | `ModeSheet.scss` | 绝对定位滑块 + `transform` |
| 历史页下拉刷新 | `SidebarDrawer` | 符合微信原生交互范式 |

### 2.3 Markdown 渲染链路
- 自研轻量 Markdown→HTML 解析器（`utils/markdown.ts`）
- 专门为小程序 `<RichText>` 组件优化
- 符号转义处理正确（`escapeHtml` 优先于 markdown 转换）
- 详尽的 `.ai-reply` 子元素样式覆盖

### 2.4 长按菜单交互
`MessageBubble` 实现了长按 → 触发震动反馈（`wx.vibrateShort`）→ 弹出复制/取消菜单的完整链路。

### 2.5 组件化架构
- IAC 聊天页拆分为 5 个子组件
- 公共组件抽象（KnowledgeCard、UserAvatar）
- Hooks 分离（useStreamingResponse）
- 服务层分离（services/api.ts）

## 三、与大厂的差距详析 ⚠️

### 3.1 列表性能 — 无虚拟滚动

**严重程度**：🔴 高  
**影响范围**：`case-library` 卡片列表、`SidebarDrawer` 历史列表

`case-library/index.tsx` 中的卡片列表采用全量渲染 + 前端分页（`slice(0, displayedCount)`），数据量大时 DOM 节点持续增长。`SidebarDrawer` 的历史会话列表同样使用 `ScrollView` 全量渲染，数百条历史记录时会造成严重卡顿。

大厂小程序在此场景**必然使用虚拟滚动**（Taro VirtualList 或自研虚拟化容器）。

### 3.2 无骨架屏 / 图片懒加载 / 预加载

**严重程度**：🔴 高  
**影响范围**：所有页面首屏加载

所有页面均无骨架屏（Skeleton Screen），首屏加载时呈现白屏或空状态。KnowledgeCard 的 `<Image>` 组件未设置 `lazyLoad` 属性。大厂产品在此方面必有骨架屏或至少 loading 占位。

### 3.3 异常态覆盖不完整

**严重程度**：🔴 高  
**影响范围**：全局

| 场景 | 当前状态 | 大厂要求 |
|------|:--:|:--:|
| 搜索无结果空态 | ❌ 缺失 | ✅ 必须有 |
| 数据加载失败 | ❌ 缺失（profile 页） | ✅ 必须有 |
| 全局网络断连提示 | ❌ 缺失 | ✅ 必须有 |
| 请求超时重试 | ❌ 缺失（仅 401 处理） | ✅ 必须有 |
| IAC 聊天页空态 | ✅ 有 | ✅ |
| IAC 聊天页网络提示 | ✅ 有 | ✅ |

### 3.4 SidebarDrawer 动画 BUG

**严重程度**：🟡 中  
**影响范围**：侧边栏抽屉

`SidebarDrawer.tsx` 中 `if (!visible) return null` 直接卸载 DOM，导致 `sidebar-panel--open` 的 CSS transition 入场动画**无法触发**。组件挂载时 DOM 刚创建，`--open` 类名直接应用在同帧，浏览器不会产生过渡。

正确方式应参照 ModeSheet，使用 `animating` 状态 + `useEffect` + `requestAnimationFrame` 实现动画延迟挂载。

### 3.5 样式 Token 落地不彻底

**严重程度**：🟡 中  
**影响范围**：全局样式一致性

- `case-library/index.scss` 引入了 tokens，但同时硬编码 `#1A1A1A`、`#666666`、`#999999`、`#CCCCCC`
- 混用 `px` 和 `rpx`（如 `margin-top: 24px`，应统一为 rpx）
- `KnowledgeCard` 组件内颜色完全硬编码
- `UserAvatar` 组件内颜色硬编码

大厂项目通过 ESLint 规则强制使用 token 变量，杜绝硬编码。

### 3.6 TypeScript 类型不严谨

**严重程度**：🟡 中  
**影响范围**：类型安全

多处使用 `any` 类型，关键位置如下：

| 文件 | 位置 | 问题 |
|------|------|------|
| `ChatInput.tsx` | `chatAreaRef = useRef<any>` | 应标注具体类型 |
| `iac/index.tsx` | `onChatScroll = (e: any)` | 应使用 Taro 滚动事件类型 |
| `services/api.ts` | `data?: any` | 应使用泛型约束 |
| `useStreamingResponse` | `React.Dispatch<...>` | 应使用更合适的类型 |

`tsconfig.json` 中 `strict: false`、`noImplicitAny: false`，大厂项目通常启用 strict。

### 3.7 代码重复

**严重程度**：🟡 中  
**影响范围**：可维护性

`training/incubation/index.tsx` 中实现了与 IAC 页面几乎相同的流式响应逻辑、输入栏逻辑、扩展面板逻辑。应抽取通用 ChatContainer 组件消除重复。

### 3.8 零自动化测试

**严重程度**：🟡 中  
**影响范围**：质量保障

全项目无任何测试文件。大厂产品通常有：
- 单元测试（Jest / Vitest）
- E2E 测试（miniprogram-automator）
- 视觉回归测试（Percy / Chromatic）

### 3.9 无可观测性设施

**严重程度**：🟢 低（但对商业化产品为高）  
**影响范围**：运营决策

代码中无埋点（曝光/点击/页面停留时长）、无错误监控（Sentry 或自研）、无性能监控。大厂产品对用户行为和系统健康度的实时感知是标配。

### 3.10 无无障碍（Accessibility）支持

**严重程度**：🟢 低（国内普遍薄弱）  
**影响范围**：特定用户群

无 `aria-label`、无焦点管理、无读屏兼容。微信、支付宝在部分核心页面已覆盖基础无障碍适配。

## 五、结论

当前代码的**交互设计品味**和**组件化意识**已经具备对标大厂产品的基因基础，Taro + React + Zustand + Sass 的技术栈组合**完全能支撑商业化级别体验**。

真正的差距不在于技术栈本身，而在于**工程化深度**和**边界场景覆盖率**。补齐这些短板后，用户端体验可达到大厂水准线。
