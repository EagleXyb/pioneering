## 四、关键差异对比

| 维度 | 普通模式 | 专业模式 |
|------|---------|---------|
| **API 前缀** | `/chat/` | `/agent/` |
| **后端处理函数** | `stream_chat_completion()` | `stream_agent_completion()` |
| **SSE 事件类型** | `thinking_delta`/`answer_delta`/`status`/`__metadata__` | `thinking`/`tool_call`/`tool_result`/`text_stream`/`done`/`error`/`__agent_metadata__` |
| **前端解析器** | `useStreamParser.applyStreamEvent()` (事件总线 + step 构建) | 内联 `applyAgentEvent()` (轻量，直接 setMessages) |
| **SSE 解析模块** | `useStreamParser.ts` (200+ 行) | `useAgentChat.ts` 内联 (~100 行) |
| **事件总线** | 使用 `agentEventBus` (emit 各类事件) | 不使用 (`run:started`/`run:finished` 仅标记) |
| **UI 布局** | 左栏 + 中间栏 (两栏) | 左栏 + 中间栏 + 右栏 (三栏) |
| **ExecutionCard** | 隐藏 | 显示 |
| **AgentStepsPanel** | 隐藏 | 显示 |
| **Session 创建** | `POST /chat/sessions` | `POST /agent/sessions` (含 agentMode) |
| **消息加载** | `GET /chat/sessions/{id}/messages` → `MessageResponse` | `GET /agent/sessions/{id}/messages` → `AgentMessageResponse` (含 contentBlocks) |
| **数据库持久化** | ChatMessage (content + metadata) | ChatMessage (content + content_blocks) + AgentToolExecution |

## 五、`stream_chat_completion` vs `stream_agent_completion` 核心差异

两者都在 `agent_bridge.py` 中，都调用同一个 `Coordinator.stream_request()`，但事件转换层不同：

| 维度 | `stream_chat_completion` (普通模式) | `stream_agent_completion` (专业模式) |
|------|-----------------------------------|-----------------------------------|
| **事件转换函数** | `_coordinator_frame_to_frontend_event()` | 内联在 `stream_agent_completion` 中 |
| **thinking 事件** | `thinking_delta` + `thinking_done` | `thinking` (一次性 block) |
| **文本事件** | `answer_delta` (增量) | `text_stream` (增量) |
| **工具事件** | `tool_call_start`/`tool_call_end`/`tool_result_end` | `tool_call`/`tool_result` (一次性 block) |
| **完成事件** | `answer_done` | `done` (空对象 `{}`) |
| **metadata 格式** | `__metadata__` (payload 内嵌) | `__agent_metadata__` (contentBlocks 扁平) |
| **contentBlocks** | 不支持 | 构建完整 content_blocks 数组 |
| **tool_executions** | 不支持 | 提取工具执行明细 |
| **token 统计** | 不支持 | promptTokens + completionTokens |
| **延迟统计** | 不支持 | latencyMs |

## 七、重构方案 — Chat / Agent / Task 三模式代码分离

> 日期: 2026-06-13
> 目标: 将当前 `pages/agent/` 中耦合的三种模式（普通/专业/任务）拆分为独立模块，各自维护迭代互不干扰

### 7.1 现状问题

| 问题 | 说明 |
|------|------|
| **业务耦合严重** | `useAgentChat.ts`（443行）同时处理普通Chat和Agent两种模式的发送逻辑，通过 `if/else chatMode` 分支切换 |
| **API层混杂** | `agentApi.ts` 同时包含 Chat API（`createChatRequest`）和 Agent API（`createAgentRequest`），以及两套会话管理 |
| **类型系统不区分** | `ChatMessage` 被两种模式共用，但 Agent 模式的消息结构（`contentBlocks`）与 Chat 模式（`thinking_content`/`answer_content`）差异很大 |
| **流解析器不统一** | Chat 模式用 `useStreamParser`（解析 `StreamEvent`），Agent 模式在 `useAgentChat` 内部内联了一个 `applyAgentEvent` 闭包 |
| **组件职责模糊** | `ChatMessage.tsx` 通过 `chatMode` prop 决定是否渲染 `ExecutionCard`；`ChatInput.tsx` 同时包含两种模式的配置项 |
| **事件总线仅Agent使用** | `useAgentEventBus` + `useAgentRun` 只在 Agent 模式下有意义，但放在共享 hooks 目录 |

### 7.5 状态管理

```
workspace/index.tsx
  ├── activeMode: 'normal' | 'professional' | 'task'
  ├── useSessionManager()          ← 共享，管理三种模式的会话
  │   ├── sessions                  ← 侧边栏展示
  │   ├── currentSessionId
  │   └── loadSession / createNewSession / removeSession ...
  │
  ├── 切换模式时：
  │   1. 保存当前模块的 messages（可选，或丢弃）
  │   2. 切换 activeMode
  │   3. 子模块重新初始化
  │
  └── 向子模块传递 props：
      ├── mode                      ← 告知子模块当前模式
      ├── sessionId                 ← 当前会话 ID
      ├── onSessionChange           ← 子模块创建/切换会话时通知外壳
      └── onMessagesChange          ← 子模块消息变化时通知外壳（可选）

chat/index.tsx (ChatView)
  ├── useChat()                    ← 独立管理 messages / isGenerating
  ├── useChatStreamParser()         ← Chat SSE 解析
  └── 内部状态：inputValue, selectedModel, deepThinking, webSearch

agent-professional/index.tsx (AgentProfessionalView)
  ├── useAgentChat()               ← 独立管理 messages / isGenerating

  ├── useAgentRun()                 ← Run 状态
  ├── useAgentEventBus()            ← 事件总线
  └── 内部状态：inputValue
```

### 7.12 关键约束

- **agent-professional 交互和样式保持不变**：仅搬迁，不改功能/UI

- **样式各自维护**：每个模块有自己的 `styles/` 目录
- **agent-task 当前占位**：只建目录和占位组件，后续独立开发
