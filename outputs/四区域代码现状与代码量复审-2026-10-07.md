## 六、缺陷清单

严重度定义沿用前几轮：P1 = 功能不可用或安全暴露；P2 = 明确功能缺陷但有绕行；P3 = 工程健壮性/性能/一致性；P4 = 债务与杂物。

### B1（P1，安全/功能）HITL 恢复全链路钉死在默认 react 图，plan_execute 会话暂停后无法正确续写

`packages/modu-agent` 的图形态是**建图期**决定的：`plan_execute` 会话在 send 时经 `create_agent({configurable:{plan_execute_enabled:true, domain:'task_planner'}})` 挂上 `planner` / `step_dispatch` 节点，而 `get_runner()` 缓存的是无覆盖的默认 react 图。恢复侧全部走后者，共五处：

- `apps/backend-ts/src/core/agent-bridge.ts:249` — `streamAgentResume` 固定 `await get_runner()`
- `apps/backend-ts/src/routes/agent.ts:630`、`:671` — `/agent/state/:threadId` 与 `/agent/abort`
- `apps/backend-ts/src/core/agent-scheduler.ts:46`、`:83` — TTL 清扫与单会话检查

后果：task 模式一次敏感工具审批暂停后，`resume_stream` 会在缺少 `planner/step_dispatch` 节点的图上执行 `Command({resume})`；而 `/agent/resume` 请求体（`AgentResumeRequestSchema`）本身也不携带 `agentMode`，`verifySessionOwner` 之后直接进 SSE，没有任何一处能纠正图选择。数据库里其实已经有 `Session.agentMode` 且本轮 T3.5 刚把它下发给前端，修复材料是齐的。这与 `apps/desktop` V2.7 记录的 P1（`executeResume/getHitlState/abortPending` 用错图）是同一类缺陷，desktop 侧用「进程内按 mode 建图缓存」缓解，backend-ts 尚未跟进。

说明：静态证据链完整（图形态建图期决定 + 五个调用点 + 请求契约缺字段），未做动态复现——复现需 LLM API Key，本机 `get_runner()` 直接抛 `OpenAI or Azure OpenAI API key or Token Provider not found`。

建议：`streamAgentResume` 增加 `agentMode` 入参，`routes/agent.ts` 从 session 记录读取后传入；`agent-bridge` 内部按 `(mode, domain)` 维度缓存图实例（对齐 `reset_runner_cache` 的失效语义），state/abort/scheduler 三处同样按会话 mode 取图。

### B2（P1，安全）`/web/preview` HTML 净化可绕过，且接受 `?token=`，构成后端同源 XSS

`apps/backend-ts/src/routes/web.ts` 的 `sanitizeHtml` 用八条正则做净化。事件属性剥离是 `\son[a-z]+…`，**要求属性名前有一个空白字符**，而 HTML 里 `/` 同样是合法属性分隔符。实测 payload：

```
<svg/onload=alert(1)>                 → 原样存活
<img/src="x"/onerror="alert(1)">      → 原样存活
<div><scri<script>pt>alert(1)</scri</script>pt></div> → 净化后复活为 <script>
```

此外 `<(object|embed|form|link)>` 那条对 `link` 特意义务保留（`tag === 'link' ? m : ''`），与文件头注释「移除脚本/事件属性/插件元素」不符；`<meta http-equiv="refresh">`、`<style>` 外联、`href="data:text/html,…" 均不在处理范围。

真实暴露路径是**顶层导航**而非应用内嵌。前端 `SourcesPanel.tsx:119-216` 走的是 `fetch + srcDoc + sandbox="allow-popups allow-popups-to-escape-sandbox"`（无 `allow-scripts`、无 `allow-same-origin`），这条路是安全的。但该端点自身返回 `Content-Type: text/html`，只设了 `Content-Security-Policy: frame-ancestors …`，没有 `sandbox`、没有 `script-src`；而 `vite.config.ts` 的 `/api → localhost:8088` 代理（带 `rewrite`）让 `http://localhost:5173/api/web/preview?…` 与 SPA **同源**，生产环境若走同源反代同样成立。鉴权只需一个合法 JWT，攻击者用**自己账号的 token** 拼进 URL 即可通过 401 校验，受害者点击后 payload 在应用源执行，而 token 存在 `localStorage`（`api/client.ts:10`），可直接读取窃取 → 账号接管。

第二条独立问题：`tokenFromReq` 支持 `?token=`，而净化注入的 `<base href>` 指向被预览的第三方站点，浏览器对页面内自动加载的资源会带上 Referer，把完整 URL 连同 token 发给目标站点。前端目前只用 Authorization 头，所以 `?token=` 实际无人消费，属于「危险且无用的能力」。

建议：换用真正的 HTML 解析器 + 标签/属性白名单（`sanitize-html` 或 `isomorphic-dompurify`），而非正则；移除 `?token=` 分支或改为一次性短时效预览票据；顶层响应补 `Content-Security-Policy: sandbox; script-src 'none'` 与 `X-Content-Type-Options: nosniff`；顺带清掉 `link` 的语义反例。当前该端点完全没有测试覆盖，修复时应一并补 payload 回归用例。
