## 一、P0 · 今天必做（发布阻断）

### P0-1 修 parseAguiStream 的 abort 出口，消掉唯一红灯

- 证据：`src/lib/parseAguiStream.ts:140-176`（while 循环内不查 `signal`、不 `reader.cancel()`）、`:203`（只在流关闭后判 aborted）；红灯 `src/modes/chat/hooks/useAguiChat.test.tsx:285`
- **实现要点（注意：只在循环顶部加检查不够）**：仅加 `if (signal?.aborted)` 仍要等下一次 `read()` resolve 才能退出，本用例 2 个 chunk × 50ms ≈ 100ms 关闭，与断言时机（70+30ms）依旧撞车，测试还是脆的。正确做法是让 abort **立即**打断挂起的 read：

```ts
const reader = response.body?.getReader();
if (!reader) throw new Error('无法读取响应流（response.body 为空）');
const onAbort = () => { void reader.cancel(); };   // cancel 令挂起的 read() 以 done:true 兑现
signal?.addEventListener('abort', onAbort, { once: true });
try {
  while (true) {
    if (signal?.aborted) break;                     // 双保险
    const { done, value } = await reader.read();
    ...
  }
} finally {
  signal?.removeEventListener('abort', onAbort);
}
```

- 同步改测试：把 `await new Promise(r => setTimeout(r, 70))` 这类猜时序的 sleep 换成 `waitFor(() => expect(...).toBe('streaming'))` 再 abort，否则仍会偶发红
- 规模：0.5 h
- 验收：`cd apps/web && npx vitest run` → 92/92，且连跑 5 次无偶发

### P0-2 接管后端真实 messageId，让反馈/重新生成不再必然 404

- 证据链（已逐环核实）：后端 `apps/backend-ts/src/core/llm.ts:80` 在 `TEXT_MESSAGE_START` 里带 `messageId: assistantMsgId` → 解析器已预留通道 `parseAguiStream.ts:101 onTextStart` → 但 `useAguiChat.ts:161-198` 注册的 handlers **没有 onTextStart** → 消息 id 恒为 `:95` 造的 `a_${Date.now()}` → `ChatMessageItem.tsx:94` 反馈、`ChatMode.tsx:238` 重生成打到 `chat.ts:885 / :913` 的 `findFirst({where:{id}})` → 必 404
- 后果：冒烟清单 ① 的"反馈 good/bad 提交成功""重新生成"两项**结构性不可过**（除非切走再切回，换成历史里的真实 id）
- **实现要点**：`assistantId` 是 `const` 且被 `patchAssistant/syncAssistant` 闭包捕获，需改成可变 `let realId` 并在 `onTextStart` 里覆写 + 同步改已入列消息的 id：

```ts
let realId = assistantId;                      // 占位，收到 TEXT_MESSAGE_START 后替换
const onTextStart = (event: AguiEvent) => {
  const rid = typeof event.messageId === 'string' ? event.messageId : '';
  if (!rid || rid === realId) return;
  const prevId = realId;
  realId = rid;
  setMessagesState((prev) => prev.map((m) => (m.id === prevId ? { ...m, id: rid } : m)));
};
```

  并把 `patchAssistant(assistantId, …)` 全部改传 `realId`（闭包内引用，注意 `onRunError/onRunFinished` 也要用最新值）。
- 已知残留竞态（可接受，写进注释即可）：后端 `RUN_FINISHED`（`chat.ts:805`）先于 assistant 行落库（`:808-840`），理论上用户在终态毫秒级内点反馈仍可能 404；人类反应时间远大于该窗口，且反馈本身是乐观更新 + 失败回滚。另一条边界：内容为空时（流被中断且无输出）后端 `if (fullContent || fullReasoning)` 不落库，该条消息的反馈/重生成仍无对应行。
- 备选方案（1 行，但体验差）：流终态后调 `reloadHistory()`——会整包替换消息、闪烁且丢 `stop` 态标记。不推荐。
- 规模：1.5 h（含给 `useAguiChat.test.tsx` 补一例"TEXT_MESSAGE_START 后 id 应为后端 id"的断言）
- 验收：`/chat` 新会话发一条 → 结束后立刻点赞 → Network 200、按钮高亮；点重新生成 → 200 且重新流式
