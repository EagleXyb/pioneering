## 一、总览结论

apps/web 是一个**文档驱动、核心层质量高、但半途状态明显**的 React 应用：

- **架构分层清晰且执行到位**：api（7 文件）→ store（6 个 Zustand）→ hooks → modes（chat/pro/task 三模式）→ layout/pages/components。类型收敛（types/tdesign.ts）、Token 设计（tokens.css）、a11y 意识（aria-*/role/键盘）普遍良好。
- **三模式成熟度严重不均**：task（Plan-and-Execute）最完善——独立 store/hook/组件/持久化恢复/测试；chat 居中——依托 TDesign useChat 全托管；**pro 是半成品**——无历史加载、切换会话不清屏、无 Markdown 渲染、无 IME 保护、无消息操作栏。
- **P0：构建链已坏**。`tsc -b` 28 个类型错误（两个 MoreMenu 组件），且 web 的 package-lock.json（6-21）落后于 package.json（7-20）——lucide-react/@radix-ui 等新依赖从未进 lock，`npm ci` 不可用，依赖解析悬在根 node_modules 的偶然状态上。
- docs/ 下 4 份设计文档质量很高，但部分结论已过时（后端 501 已修复），本次复审做了失效核查（见第八节）。

## 二、组织结构与模块划分

```
apps/web/src/
├── api/          # HTTP 层：client(统一封装/401刷新) + 按域拆分 session/message/plan/auth-api/system + 类型 types + 转换器 converter(+test)
├── store/        # Zustand ×6：conversationStore(会话,带persist) / auth(persist) / planExecuteStore / artifactStore / appStore(布局) / themeContext(Context)

├── modes/        # 三模式，各自独立目录（components/hooks/css）
│   ├── chat/     # TDesign useChat(agui) 托管：ChatMode 294行 + List/Item/Welcome/Input
│   ├── pro/      # 手写 SSE：useAgentChat 461行 + AnalysisLayout/List/Input/ProcessPanel
│   └── task/     # 自研最全：usePlanExecuteChat 347行 + PlanPipelineTree/TaskPipeline/TaskMessageList/Input(+MoreMenu)
├── layout/       # Sidebar 856行(最大) / TopNav / TaskTopBar / AppShell.css
├── pages/        # auth×5(Login/Register/AuthLayout/ForgotPassword/auth.module.css) + HelpPage + NotFound

├── config/       # models.ts(三模式默认模型)
├── styles/       # tokens.css(亮暗双主题) + tailwind.css(作用域限定 .tw-scope)
└── types/        # tdesign.ts(集中 re-export 传递依赖) / auth.d.ts / 顶层 types.ts
```

**路由结构**（App.tsx）：`/auth/*` 无壳免守卫 → `/help` 独立全屏受守卫 → `/chat|/pro|/task` 共享 AppLayout（Sidebar+条件 TopNav，三模式均 lazy）→ `*` 404。全部 lazy + Suspense。

**状态与数据流**：`conversationStore` 是会话唯一真理源（乐观创建+回滚、游标分页防重、归档视图、sessionModes 本地映射弥补后端无 mode 字段）；`planExecuteStore` 扁平 `Record<step_id, PlanItem>` + rootIds 驱动时间轴，`source: live|history` 区分实时流与快照恢复；组件层普遍 `useXxxStore((s) => s.field)` 细粒度订阅。

## 三、主要功能与技术实现（三模式对照）

| 维度 | chat | pro | task |
|---|---|---|---|
| 通道 | TDesign `useChat`，`protocol:'agui'`，onRequest 注入 auth | 手写 fetch SSE（useAgentChat） | 手写 fetch SSE（usePlanExecuteChat），带 `agentMode:'plan_execute'` |
| 历史加载 | ✅ 游标分页 + 竞态保护 + 滚动位置恢复 | ❌ 无（切会话不清屏、刷新即丢） | ✅ loadHistory 恢复消息 + plan 时间轴快照 |
| Markdown | TDesign 渲染 + reasoning 折叠 | ❌ 纯文本（\n 拼接） | ✅ 自研 Markdown + 代码块 artifact 预览 |
| IME 保护 | TDesign 内置 | ❌ 无（中文选词回车误发送） | ✅ 完整（含 Safari iOS 500ms 时间戳校验） |
| 停止 | abortChat + 后端 /stop 联动 | abort() 仅客户端 | abort() + Escape 键 |
| 右栏 | 无 | ProcessPanel（thinking/tool 线性步骤） | PlanPipelineTree 时间轴（5 态/折叠/历史禁动画） |
| 附加 | R1 深思考开关、AI 生成标题、反馈/复制/分享 | stateMap 步骤流 | 折叠快照回传持久化、ArtifactPanel 互斥 |

**task 模式闭环（近期主战场）**：STATE_DELTA(plan) 全量建树 → STATE_DELTA(execute) 增量更新 → RUN_FINISHED 后异步回传折叠快照到 `chat_messages.metadata`；切会话时 `GET /agent/messages/:id/plan` 装配终态（hydrateFromHistory），渲染层按 `data-source="history"` 禁用 running 脉冲。后端 plan_steps 表持久化与该端点已核实存在（agent.ts:668）。

**输入组件实现分化**：ChatInput=TDesign ChatSender；AnalysisInput=106 行简化手写（无 IME/无草稿）；TaskInput+useTaskInput=最完整（sessionStorage 草稿防抖 500ms/会话隔离、autosize 恢复祖先滚动、enterToSend 偏好读取）。

## 四、依赖关系与调用逻辑

核心调用链（task 为例）：

```
TaskMode (useEffect[activeId])
  ├─ resetArtifact / loadHistory(sessionId)
  │     └─ getMessages → convertMessages → setMessages
  │     └─ metadata.plan_phase? → getMessagePlan → hydrateFromHistory
  ├─ TaskMessageList ← messages/status；滚动+useScrollToMessage 反向联动 artifactStore
  ├─ TaskInput → useTaskInput(草稿/IME/autosize) → sendMessage → usePlanExecuteChat
  │     └─ fetch /api/agent/completions (SSE) → applyPlanDelta/setPhase → planExecuteStore
  │     └─ RUN_FINISHED → persistCollapsedSnapshot → patchCollapsedSteps
  └─ TaskPipeline(=ArtifactPanel 互斥) → PlanPipelineTree ← planExecuteStore
```

**跨模式共享面**：三模式各自目录下的 `useChatSync.ts`（预览/标题两阶段同步，见第五节）；`TaskResizer` 被 pro 复用（import ../task/components）；`extractCodeBlocks/Markdown/artifactStore` 由 task 独享；`useAuth/auth store/client.ts` 全局共享。

**后端契约**：vite proxy `/api → localhost:8088`（env.ts:29 注释自认弃用 6000 是因 Chromium 不安全端口黑名单）。chat 走 `/chat/*`，pro/task 走 `/agent/completions`（SSE）。`/agent/sessions/:id/messages` 等端点前端仍未消费。

## 七、可维护性与扩展性评估

**优点（值得保持）**：
- 注释文化极好：几乎每个文件头部有设计意图/参考文档/兼容性说明，关键修复标注编号（P0-2、P2-1…）与 docs 互链。
- 核心层（client.ts 的 401 刷新并发去重、conversationStore 的乐观更新+并发去重+游标防重、themeContext 的双属性主题同步、useTaskInput 的 IME/草稿/autosize）是高质量的、可直接复用的。
- types/tdesign.ts 把未声明传递依赖的 deep import 收敛到单点，升级可控。
- 测试虽少但质量高（extractCodeBlocks 16 例、store 4 文件、TaskMessageList 9 例）。

**扩展性风险**：
1. **三模式无共享底座**：会话同步（R1）、输入框（R5）、SSE 解析（R4）各自拷贝。每加一个模式 = 复制 3 份；每修一个 bug（如标题串改防护）要同步 3 处——已经发生（staleMessagesRef 这类精细防护在三份拷贝间同步是靠运气）。
2. **pro 模式是技术债集中地**：若确定保留 pro，最小路径是复用 task 的骨架（usePlanExecuteChat 模式：loadHistory + store + Markdown 列表）；若不保留，应尽早移除入口避免用户踩空。
3. **大文件**：Sidebar 856 行（SidebarItem/AccountPopover/Sidebar 三职责）、SettingsDialog 626 行（7 个分区内联）可拆但非紧迫。
4. **门禁缺失**是当前最大结构性风险：tsc 28 错能长期存在、hooks 违规无人拦，说明本地无 pre-commit、无 CI。desktop 已建立"修复+单测"节奏，web 缺同等约束。

## 十、结语

apps/web 的核心链路（认证/会话/聊天/任务编排）真实可用且代码质量高于平均水平，task 模式与后端 plan_execute 已形成完整闭环。当前最紧迫的不是功能，而是**把已经坏的构建门禁修好、把 lock 补上**——这两件事半天内可完成，却是后续一切迭代的前提。三模式的收敛（共享底座）与 pro 模式的补全/移除决策，是中期最重要的架构议题。
