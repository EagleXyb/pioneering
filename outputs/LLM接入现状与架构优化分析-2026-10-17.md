## 一、结论摘要

1. 全项目**只有 DeepSeek 真正在跑**（`deepseek-v4-flash` 默认、`deepseek-v4-pro` 深度思考），其余模型仅存在于注册表或前端静态目录。
2. 模型调用**全部走 OpenAI 兼容协议**，没有接入任何厂商专属 SDK；两种形态并存 —— 后端原生 `fetch` 直连（chat 通道）与 LangChain `ChatOpenAI`（agent 通道）。
3. 前端**不直连模型**，只通过 `/api` 与 SSE 与后端交互。
4. 存在三类显著错配：模型目录 ≠ 真实可用；Agent 通道忽略模型选择；默认模型名在三处取值不一致。
5. 主要优化方向：收敛为单一 LLM Gateway、模型能力由后端下发、分级超时与心跳、统一上下文预算、补齐幂等与可观测。

## 三、连接方式与配置

### 3.1 三种连接形态

**（1）`apps/backend-ts`：原生 HTTP 直连（无 SDK）**

- 使用 Node 内建 `fetch` 调用 `${LLM_BASE_URL}/chat/completions`，手写 SSE 行解析与 AG-UI 事件编码。
- 配置入口：`apps/backend-ts/.env` → `apps/backend-ts/src/config/env.ts`（Zod 校验为类型安全 `env` 对象）。
- `apps/backend-ts/package.json` 中的 `undici` 依赖实际未被 import，运行时用的是 Node 内建 fetch。

**（2）`packages/modu-agent`：第三方库 `@langchain/openai`**

- 唯一构造入口 `packages/modu-agent/src/graph/adapters/llm-adapter.ts`，创建 `ChatOpenAI`（`streaming: true`），底层由 LangChain 调 OpenAI Node SDK，仍走 OpenAI 兼容协议；GLM/DeepSeek/Qwen 通过自定义 `baseURL` 复用同一实现。
- 两处关键网络处理：
  - 用 Node 内建 fetch 覆盖 SDK 默认 fetch，规避 SSE `Premature close`；
  - 旁路嗅探 `reasoning_content` 增量（LangChain 会丢弃该字段），供前端「深度思考」段渲染。
- Provider 规格与默认值：`packages/modu-agent/src/graph/adapters/llm-provider-registry.ts`；环境变量清单：`packages/modu-agent/src/config/env.ts`。

**（3）`apps/web`：不直连模型**

- 仅 `fetch` + `ReadableStream` 解析 SSE；`package.json` 无任何 AI SDK。

### 3.2 连接参数解析优先级（modu-agent）

1. 显式参数（`configurable.model` / `provider`）
2. provider 专属 env（如 `MODU_DEEPSEEK_API_KEY` / `_BASE_URL` / `_MODEL`）
3. 别名 env（如 `MODU_OPENAI_*`）
4. 通用 `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_DEFAULT_MODEL`
5. provider 内置默认值

### 3.3 运行时行为参数

| 参数 | 取值 | 来源 |
|---|---|---|
| `llm.default_provider` | `deepseek` | `DEFAULT_CONFIG`（`MODU_LLM_PROVIDER` 未设置） |
| `llm.temperature` | `0.7` | `DEFAULT_CONFIG` |
| `llm.max_tokens` | `8192` | `packages/modu-agent/config.yaml` 覆盖框架默认 512 |
| `llm.router.enabled` | `false` | `DEFAULT_CONFIG` |
| `feedback.quality_monitor_mode` | `rule` | `DEFAULT_CONFIG`（不构造 Judge LLM） |
| 直连通道超时 | `120_000 ms` | 硬编码于 `core/llm.ts` |

> `config.yaml` 通过包内相对路径定位（`findConfigYaml()` 以 `__dirname` 上溯两级），与进程启动目录无关，因此上述覆盖稳定生效。

## 四、按模型分列：用途、集成方式、关键文件

### 4.1 DeepSeek `deepseek-v4-flash`（在用，默认）

- **用途**：chat 对话与标题生成、Agent（pro/task）主推理、联网搜索关键词提炼。
- **集成方式**：双路径 —— 后端原生 fetch 直连；modu-agent 经 `ChatOpenAI`。
- **配置**：`apps/backend-ts/.env` 的 `LLM_DEFAULT_MODEL`；`packages/modu-agent/config.yaml` 的 `llm.max_tokens`；`runtime-config.ts` 的默认温度/路由。
- **关键文件**：
  - 直连：`apps/backend-ts/src/core/llm.ts`、`apps/backend-ts/src/core/web-search.ts`、`apps/backend-ts/src/routes/chat.ts`
  - Agent：`apps/backend-ts/src/core/agent-bridge.ts`、`packages/modu-agent/src/graph/factory.ts`、`packages/modu-agent/src/graph/adapters/llm-adapter.ts`、`packages/modu-agent/src/graph/adapters/llm-provider-registry.ts`、`packages/modu-agent/src/graph/nodes.ts`
- **流程概述**：`/chat/completions` → 组装消息（含历史与联网结果）→ `llmService` 直发 DeepSeek → SSE 增量转 AG-UI；Agent 路径 → `create_agent`/`get_runner` → `build_chat_model` → `ChatOpenAI` 绑定工具后由 ReAct / Plan-Execute 节点 `invoke`。

### 4.2 DeepSeek `deepseek-v4-pro`（在用，deepThink）

- **用途**：chat 模式「深度思考」开关触发的推理模型。
- **集成方式**：后端原生 fetch 直连（仅此一条路径，Agent 通道不支持）。
- **配置**：模型 ID 硬编码在路由中，非环境变量。
- **关键文件**：`apps/backend-ts/src/routes/chat.ts`、`apps/backend-ts/src/schemas/chat.ts`、`apps/backend-ts/src/routes/system.ts`
- **流程概述**：请求体 `deepThink=true` → 路由将 `model` 覆盖为 `deepseek-v4-pro` → 同一 `streamAgui` 发送 → 前端将 `reasoning_content` 渲染为思考段。

### 4.3 GLM / GPT / Qwen（已编码，未启用）

- **用途**：provider 注册表提供的可替换实现，供宿主通过配置或注册接口切换；当前无密钥、未选 provider，不参与实际调用。
- **集成方式**：统一 `ChatOpenAI` + 各自 `baseURL`：
  - GLM：`https://open.bigmodel.cn/api/paas/v4`
  - OpenAI：`https://api.openai.com/v1`
  - Qwen：`https://dashscope.aliyuncs.com/compatible-mode/v1`
- **配置**：`MODU_GLM_*`、`OPENAI_API_KEY` / `MODU_OPENAI_*`、`MODU_QWEN_*`、`MODU_LLM_PROVIDER`。
- **关键文件**：`packages/modu-agent/src/graph/adapters/llm-provider-registry.ts`、`packages/modu-agent/src/graph/adapters/llm-adapter.ts`、`packages/modu-agent/src/config/runtime-config.ts`、`packages/modu-agent/src/reasoning/llm/router.ts`
- **流程概述**：`llm.default_provider` 或 `configurable.llm_provider` 指定 → 注册表取工厂 → 解析对应 env → 构造 `ChatOpenAI`；未知 provider 会回退 `glm`。

### 4.4 仅目录展示的模型（无真实接入）

- `glm-5.3`、`glm-5.3-flash`、`minimax-m3`、`gpt-4o`、`gpt-4o-mini` 仅存在于 `apps/backend-ts/src/routes/system.ts` 的静态清单；前端经 `apps/web/src/api/system.ts` → `apps/web/src/hooks/useModelOptions.ts` → `apps/web/src/components/ModelSelect/` 展示。
- 选中后其 ID 会作为 `model` 字段发往**同一个** `LLM_BASE_URL`，没有按供应商切换端点，因此除 DeepSeek 外实际不可用。

### 4.5 非对话类模型能力

- **向量嵌入**：`packages/modu-agent/src/memory/chroma.ts` 使用 SHA-256 hash 伪嵌入（SentenceTransformer / ONNX 在 TS 侧不可用），未调用嵌入模型。
- **ASR**：`packages/modu-agent/src/perception/audio/asr-processor.ts` 中 Whisper / SpeechRecognition 为 TODO 占位。
- **检索**：`apps/backend-ts/src/core/web-search.ts`、`packages/modu-agent/src/tools/search.ts` 走 Tavily → DuckDuckGo → Bing HTML，不涉及 LLM（除关键词提炼）。

## 五、跨目录调用链路

### 链路 A：chat 模式（非 Agent，直连模型）

```text
apps/web/src/modes/chat/components/ChatInput.tsx   （模型选择）
  → apps/web/src/modes/chat/hooks/useAguiChat.ts
  → POST /api/chat/completions
  → apps/web/vite.config.ts 代理 → localhost:8088
  → apps/backend-ts/src/routes/chat.ts
      （配额校验 → DB 历史 → 可选联网搜索）
  → apps/backend-ts/src/core/llm.ts
  → DeepSeek /chat/completions
  → AG-UI SSE
  → apps/web/src/lib/parseAguiStream.ts → 渲染
  → 用量经 apps/backend-ts/src/core/quota.ts 落库
```

### 链路 B：pro / task 模式（Agent，经 modu-agent）

```text
apps/web/src/modes/pro/hooks/useAgentChat.ts        （react_agent）
apps/web/src/modes/task/hooks/usePlanExecuteChat.ts （plan_execute）
  → apps/web/src/api/agent.ts
  → POST /api/agent/completions
  → apps/backend-ts/src/routes/agent.ts
  → apps/backend-ts/src/core/agent-bridge.ts
  → @pioneering/modu-agent: create_agent / get_runner + stream_response
  → packages/modu-agent/src/graph/plan-execute/planner.ts
    packages/modu-agent/src/graph/nodes.ts
  → build_chat_model → ChatOpenAI → DeepSeek
  → LangGraph 事件 → packages/modu-agent/src/orchestration/communication/agui-adapter.ts
  → AG-UI SSE → apps/web/src/lib/parseAguiStream.ts → 渲染
```

### 链路 C：辅助调用

- **会话标题**：`apps/backend-ts/src/routes/chat.ts` 内用默认模型低温度（0.3）、`max_tokens=100` 生成。
- **联网搜索**：前端开关 → 后端 `core/web-search.ts` 先用默认模型提炼关键词（`max_tokens=400`），再抓取搜索引擎结果注入 system 消息。

### 链路 D：HITL 恢复

前端 `POST /api/agent/resume` → `apps/backend-ts/src/core/agent-bridge.ts` → `resume_stream` + LangGraph `Command({resume})` → 继续同一 checkpoint 的模型调用。

## 六、优化建议（P0 / P1 / P2）

### P0 — 正确性与用户可直接感知的问题

**1. 模型目录与实际接入不符**

- 问题：`/system/models` 返回 7 个模型，但后端把 `model` 原样发给同一个 DeepSeek 端点；选中非 DeepSeek 模型必然失败。
- 建议：删减为真实可用模型，或在元数据中增加 `base_url` / `key_ref`，按模型路由到对应供应商。
- 位置：`apps/backend-ts/src/routes/system.ts`、`apps/backend-ts/src/routes/chat.ts`、`apps/web/src/hooks/useModelOptions.ts`

**2. Agent 通道的模型选择是「假控件」**

- 问题：`/agent/completions` 固定传 `model: null`，`session.model` 不参与推理；pro/task 的 `ModelSelect` 无效。
- 建议：透传 `model` 到 `configurable.model`，或移除控件避免误导。
- 位置：`apps/backend-ts/src/routes/agent.ts`、`apps/backend-ts/src/core/agent-bridge.ts`、`apps/web/src/modes/pro/components/AnalysisInput.tsx`

**3. chat 流式硬编码 120 秒总超时**

- 问题：`AbortSignal.timeout(120_000)` 覆盖整个响应体读取，长回答 / 深度思考超过 2 分钟会被直接掐断。
- 建议：改为空闲超时（两次 chunk 间隔计时）或配置化，与 `llm.request_timeout_ms` 统一口径。
- 位置：`apps/backend-ts/src/core/llm.ts`

**4. 默认模型名三处不一致**

- 问题：`env.ts` 默认 `deepseek-chat`，modu-agent 注册表与前端目录为 `deepseek-v4-flash`；缺 `.env` 时会请求一个目录中不存在的模型。
- 建议：收敛为单一常量，或统一从 provider 注册表取默认值。
- 位置：`apps/backend-ts/src/config/env.ts`、`packages/modu-agent/src/graph/adapters/llm-provider-registry.ts`、`apps/web/src/config/models.ts`

**5. `deepseek-v4-pro` 硬编码在路由**

- 问题：`deepThink` 直接写死模型名，换模型需改代码。
- 建议：抽成 `llm.reasoning_model` 配置项。
- 位置：`apps/backend-ts/src/routes/chat.ts`

### P1 — 架构一致性（可靠性与成本）

**6. LLM 调用双轨并行**

- 问题：chat 走手写 fetch + 自研 SSE 解析，agent 走 LangChain；重试、超时、usage 采集、`reasoning_content` 处理、错误语义均不同；直连路径无 metrics/tracing。
- 建议：抽出统一 `llm-client`（或让 chat 复用 modu-agent 的 `build_chat_model`），至少统一超时、重试与 usage 解析，并补 SSE 契约测试。
- 位置：`apps/backend-ts/src/core/llm.ts`、`packages/modu-agent/src/graph/adapters/llm-adapter.ts`、`packages/modu-agent/src/graph/adapters/retry.ts`

**7. 两条通道上下文策略不一致**

- 问题：chat 固定带最近 20 条；agent 用 token 预算（8000 tokens / 保留 6 条）。前者长会话易溢出，后者已实现却未复用。
- 建议：chat 统一改用 `loadSessionHistoryByBudget`。
- 位置：`apps/backend-ts/src/routes/chat.ts`、`apps/backend-ts/src/core/context-budget.ts`

**8. 带 systemPrompt 的请求每次重建整张图**

- 问题：`hasBuildOverrides` 为真时走 `create_agent()`，会重跑内置工具注册、MCP 工具发现、checkpointer 装配；仅无覆盖时命中 `get_runner()` 缓存。
- 建议：按 `system_prompt + model + plan_execute` 组合做图缓存（LRU）。
- 位置：`apps/backend-ts/src/core/agent-bridge.ts`、`packages/modu-agent/src/graph/factory.ts`

**9. 联网搜索多一次串行 LLM 调用**

- 问题：`netSearch` 请求先调模型提炼关键词（`max_tokens=400`），再发主请求，首字延迟翻倍且无缓存。
- 建议：并发（先发原 query，命中差再改写）、短 TTL 缓存，或规则化改写。
- 位置：`apps/backend-ts/src/core/web-search.ts`

**10. 未知 provider 静默回退 `glm`**

- 问题：`UNKNOWN_PROVIDER_FALLBACK = 'glm'`，在无 GLM key 的环境中表现为一次 401，错误信息与真实原因无关。
- 建议：fail-fast 并明确报出非法 provider id。
- 位置：`packages/modu-agent/src/graph/adapters/llm-adapter.ts`

**11. `max_tokens` 配置双源、router 死分支**

- 问题：框架默认 512、YAML 覆盖 8192，散落在 `DEFAULT_CONFIG` / YAML / env 三层；`llm.router.enabled=false` 但路由表构造代码仍在。
- 建议：单一事实源，并在 `/debug/config` 输出「生效值 + 来源」；router 关闭时彻底跳过构造。
- 位置：`packages/modu-agent/src/config/runtime-config.ts`、`packages/modu-agent/config.yaml`、`packages/modu-agent/src/graph/factory.ts`

### P2 — 工程与体验

**12. 前端硬编码 `/api`**

- `apps/web/src/api/client.ts` 写死 `/api`，`.env` 的 `VITE_API_BASE_URL` 完全未使用；生产只能靠同源反代，无法通过配置切换后端。
- 位置：`apps/web/src/api/client.ts`、`apps/web/.env`、`apps/web/vite.config.ts`

**13. `max_tokens` 字段语义混用**

- 模型目录里的 `max_tokens: 128000` 被前端当作「上下文窗口」展示，而请求体同名参数是「补全上限」。
- 建议：改名 `context_window`。
- 位置：`apps/backend-ts/src/routes/system.ts`、`apps/web/src/components/ModelSelect/modelFacts.ts`

**14. chat SSE 无心跳**

- agent 通道有 heartbeat，chat 通道没有，长回答经 Nginx / 网关时容易被判定空闲断开。
- 位置：`apps/backend-ts/src/routes/chat.ts`、`apps/backend-ts/src/routes/agent.ts`

**15. 向量检索质量**

- Chroma 使用 SHA-256 hash 伪嵌入，语义检索基本无效（`setEmbeddingFunction` 已预留但无人注入）。
- 建议：接入真实 embedding 服务，或改用 pgvector + 远程 embedding。
- 位置：`packages/modu-agent/src/memory/chroma.ts`

**16. 遗留物清理**

- `AiConfig` 表无人读写；`undici` 依赖未使用；`ChatSession.model` 的 DB 默认值仍是 `gpt-4o-mini`。
- 位置：`apps/backend-ts/prisma/schema.prisma`、`apps/backend-ts/package.json`

**17. 计费口径**

- `system.ts` 的 `pricing` 仅用于前端展示倍率，`quota.ts` 仅记 token、不按价格计费，两者可能长期漂移。
- 位置：`apps/backend-ts/src/routes/system.ts`、`apps/backend-ts/src/core/quota.ts`

> 安全补充：`apps/backend-ts/.env` 与 `apps/web/.env` 均已被 `.gitignore` 忽略且未纳入版本控制（已用 `git check-ignore` / `git ls-files` 核实），密钥风险仅限本机明文。若需彻底治理，可改为启动时从系统钥匙串或密钥服务注入。

## 七、成熟产品怎么做

### 7.1 分层架构

```text
Web / App
  ↓  只说「模型别名 + 能力要求」，不认识厂商
BFF / API Gateway        鉴权、限流、配额、审计、SSE 编排
  ↓
LLM Gateway              模型目录、路由、失败转移、重试、成本核算、可观测
  ↓
Provider Adapters        OpenAI / Anthropic / 通义 / 智谱 …
```

要点：

- **模型目录是服务端配置**（DB / 配置中心），包含 `alias`、真实版本号、上下文窗口、最大输出、能力标签、单价、限流、下线日期。
- **别名与版本分离**：客户端只认 `fast` / `smart` / `reasoning`，后端映射到具体版本，升级模型不发版。
- **能力声明驱动 UI**：前端按 `capabilities` 决定是否显示「深度思考」「上传图片」「工具调用」，而非按模型名写分支。
- **密钥只在网关**：存 KMS / Vault，按环境隔离并轮换；出网加白名单，只允许厂商域名。
- **失败转移是常态**：主备 provider、熔断、指数退避 + 抖动，按错误类型决定重试 / 切换 / 直接失败。

### 7.2 一次请求的完整生命周期

1. 启动拉取能力：`GET /capabilities` 返回模型列表、可用状态、价格、限流、能力标签；不可用项置灰并给原因。
2. 前端按模式过滤（如 pro 只显示支持工具的模型），提交 `model_alias` 而非原始 ID。
3. 请求带幂等键：`Idempotency-Key` + `request_id`，防弱网重发造成重复计费与重复落库。
4. 服务端准入：鉴权 → 租户隔离 → 分层限流 → 配额**预扣** → 内容审核。
5. 上下文组装：统一 token 预算裁剪；系统提示词与工具描述来自版本化 prompt registry。
6. 路由与调用：按 alias 选 provider，设置**分级超时**（连接 / 首 token / 空闲 / 总时长），流式只对空闲计时。
7. 流式下发：SSE 事件带 `id` 与序号、服务端心跳、支持 `Last-Event-ID` 断线续传；客户端 abort 向上游传播。
8. 落库与结算：先建消息占位（pending），流结束更新为 complete / failed / aborted；按实际 usage 结算配额；写审计与指标。
9. 可观测：记录 `trace_id / provider / model_version / ttft / latency / tokens / finish_reason`，对截断率、401 率、首 token P95、单会话成本告警。

### 7.3 安全性清单

| 面向 | 成熟做法 |
|---|---|
| 密钥 | 服务端集中托管（KMS/Vault）、环境隔离、定期轮换、日志与错误信息脱敏、出网白名单 |
| 鉴权 | 短期 access token + refresh 轮换（含重用检测）、会话归属校验、多租户隔离（缓存 key 也带 tenant） |
| 输入 | 长度 / 文件类型 / 大小限制、上传扫描、URL 抓取防 SSRF、prompt injection 检测 |
| 输出 | PII / 密钥 / 内网 IP 脱敏、Markdown 白名单渲染防 XSS、外链 `rel=noopener`、错误信息不透传上游原始响应体 |
| 工具调用 | 白名单 + 最小权限 + 沙箱 + 人工审批（HITL）+ 全量审计；工具返回内容视为不可信输入 |
| 滥用 | 分层限流（IP / 用户 / 租户 / 模型）、并发上限与背压、成本熔断、异常用量告警 |
| 数据 | 留存期限、删除权、是否用于训练的明确承诺、审计日志防篡改 |

### 7.4 用户体验清单

- **首字延迟优先**：任何「为了更好」而增加的串行模型调用都要砍掉或并行化。
- **过程可见**：思考、工具调用、正文分块渲染且可折叠；长任务显示阶段与进度。
- **随时可控**：停止生成（真正中止上游）、重新生成、编辑重发、切换模型时提示影响。
- **失败可恢复**：保留已生成内容 + 重试按钮；区分 429 / 401 / 超时 / 内容拦截并给出不同 CTA。
- **透明**：显示实际生效的模型版本；自动降级时用系统消息明示，不「偷偷换模型」。
- **一致性**：多端与刷新后会话状态可恢复；草稿本地保存。
- **性能**：Markdown 增量渲染节流、长列表虚拟化、图片懒加载与代理。

## 九、实施改造方案（Web + Agent）

> 目标：把"模型选择、调用、容错、计费、观测"从散落的业务代码收进统一网关；前端只表达意图，Agent 只负责编排。
> 原则：**先收敛入口，再升级协议，最后做体验**；每一步可灰度、可回滚，不改变现有鉴权与 HITL 语义。
> 本文为方案设计，未改动任何源码。

### 9.1 目标架构

```text
apps/web
  ├─ useCapabilities        模型目录 / 能力标签 / 可用态（后端下发）
  ├─ sseClient              事件 id、心跳、续传、abort
  └─ 会话状态机             pending → streaming → paused / complete / failed / aborted

apps/backend-ts  (BFF + Gateway)
  ├─ routes/                chat / agent / capabilities / admin
  ├─ llm-gateway            统一出入口
  │    ├─ registry          别名 → 版本 + 能力矩阵 + 价格 + 限流
  │    ├─ policy            分级超时 / 重试 / 熔断 / 限流 / 配额预扣
  │    ├─ adapters          openai-compatible（首期）/ anthropic（预留）
  │    ├─ stream            AG-UI + 事件 id + 心跳 + 续传
  │    └─ usage             ttft / tokens / cost / finish_reason
  └─ core/agent-bridge      向 modu-agent 注入 provider factory

packages/modu-agent
  ├─ graph / tools / memory / HITL   纯编排，不持有密钥、不解析 env
  └─ LLM 构造                        改为消费注入的 factory（复用现有 registerLLMProvider）
```

**包归属建议**：新建 `packages/llm-gateway`（workspace）。理由：`apps/desktop` 也直接使用 modu-agent，网关放共享包才能三端复用；若只做短周期，可先落在 `apps/backend-ts/src/core/llm-gateway/`，接口保持一致，后续平移。

### 9.2 核心契约

#### 9.2.1 模型目录（服务端单一事实源）

| 字段 | 说明 |
|---|---|
| `alias` | 客户端唯一可见标识：`fast` / `smart` / `reasoning` / `vision` |
| `model_id` | 真实模型 ID（如 `deepseek-v4-flash`），仅服务端使用 |
| `provider` | `deepseek` / `openai` / `zhipu` / `dashscope` |
| `capabilities` | `tools` / `vision` / `reasoning` / `json_mode` / `long_context` |
| `context_window` / `max_output` | 与旧 `max_tokens` 语义解耦 |
| `pricing` | 输入/输出单价，用于成本核算 |
| `limits` | RPM / TPM / 并发 / 单次最大输入 |
| `status` | `active` / `degraded` / `sunset` + 原因 |
| `version` | 模型版本号，写入每次调用记录 |

#### 9.2.2 新增 `GET /capabilities`

返回可用模型列表 + 每项 `alias / display_name / capabilities / context_window / status / disable_reason`；前端**不再硬编码**任何模型名。

#### 9.2.3 请求契约

- `POST /chat/completions`、`POST /agent/completions` 统一收 `model_alias`，服务端解析；旧 `model` 字段保留为兼容别名（映射表内已登记）。
- 新增 `Idempotency-Key` 头；同键重复请求返回同一结果，不重复计费。
- 请求体拒绝未知字段，避免前端透传 provider 私有参数。

#### 9.2.4 SSE 协议升级

| 项 | 现状 | 目标 |
|---|---|---|
| 事件编号 | 无 | `id: <seq>`，单调递增 |
| 心跳 | agent 有，chat 无 | 统一 15s `: ping` |
| 续传 | 无 | `Last-Event-ID` → 从事件表回放 |
| 终止事件 | RUN_FINISHED / RUN_ERROR | 增加 `RUN_ABORTED` / `RUN_PAUSED` 语义化 |
| 错误透出 | 上游 body 截断 500 字符 | 统一错误码 + 脱敏文案 |

#### 9.2.5 统一错误码

`INVALID_MODEL` / `AUTH_EXPIRED` / `FORBIDDEN` / `PAYLOAD_TOO_LARGE` / `CONTENT_BLOCKED` / `RATE_LIMITED` / `QUOTA_EXCEEDED` / `UPSTREAM_TIMEOUT` / `UPSTREAM_ERROR` / `CANCELED`

前端按码给不同 CTA：稍后重试 / 重新登录 / 换模型 / 缩短输入 / 联系管理员。

| 表 | 变更 | 用途 |
|---|---|---|
| `ModelCatalog`（新增） | alias / provider / model_id / capabilities / limits / pricing / status | 模型目录单一事实源 |

### 9.5 灰度与回滚

| 阶段 | 灰度维度 | 观测指标 | 回滚动作 |
|---|---|---|---|
| 网关收口 | 按 userId hash 5% → 50% → 100% | 错误率、延迟、事件序列一致性 | 关 `llm_gateway_enabled` |
| SSE v2 | 按客户端版本 | 断线率、续传成功率 | 关 `sse_v2_enabled`，前端降级旧解析 |
| Agent 模型透传 | 按租户 | 构建耗时、成本 | 恢复 `model: null` |
| 配额预扣 | 全量前先影子计费 | 预扣/结算偏差 | 回退为纯事后记账 |

**硬性要求**：每个 flag 都有独立开关、独立指标、独立回滚路径；回滚不依赖发版。

| 后端（1 人） | 网关、registry、路由改造 | 超时/重试/幂等/SSE | 配额、限流、成本 |

| Agent（1 人） | factory 注入、env 解析移除 | 图缓存、上下文预算 | 护栏、评测 |
| 测试（0.5 人） | 契约测试 | 断线/中止/幂等用例 | 回归集与 eval gate |

总计约 **25～30 人日**；三人并行可压到 **3 周**。

### 9.7 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 网关成为单点 | 全站不可用 | 无状态多实例 + 熔断降级到备用 provider + 只读缓存 |
| 模型目录热更新引发不一致 | 前后端别名错配 | 版本号随目录下发，前端缓存带版本，变更走灰度 |
| SSE 续传依赖事件表 | 存储膨胀 | 事件表按 run 保留 7 天，超期返回 410 让前端重拉 |
| 图缓存与动态 prompt 冲突 | 回答错乱 | 缓存 key 纳入 prompt 哈希；配置变更主动失效 |
| 配额预扣导致误拒 | 体验受损 | 按上限估算预扣 + 结算差额回补；提供人工提额 |
| 护栏默认开启影响输出 | 内容被误脱敏 | 先影子模式（只记录不拦截），观察漏拦/误拦率后再拦截 |

### 9.8 改造范围界定

**不做**：不改 JWT/刷新逻辑；不改 HITL 状态机语义；不改 LangGraph 图结构与路由规则；不改现有表结构与字段含义（仅新增）。

**必须做**：模型目录单一事实源；三条链路共用网关；SSE 协议升级；幂等与配额；护栏与限流。

### 11.1 与第九、十章的关系

### 11.2 v2.2 带来的三处根本变化

1. **执行位置挂在 Task 上**（§4.1）：`task.deviceId + lease` 是唯一路由真相，`ChatSession.runtime` 降级为"上次使用的设备类型"。同一个账号可能同时拥有多台本地电脑与云电脑。
2. **云电脑是一台真实执行体**（§4.4、§4.3）：要跑文件操作、文档生成、浏览器任务，意味着 Agent 内核必须能在 Linux VM 里运行，Electron 不再是端侧的唯一宿主。
3. **事件与连接解耦**（§4.6、§4.11）：`seq` 由服务端分配，断连只退订不 abort，支持 `Last-Event-ID` 重放与换机续跑。

### 11.3 上一版失效的三个假设

| 第九章的假设 | v2.2 的现实 | 结果 |
|---|---|---|
| 执行位置是编译期的「云 / 边」二选一 | 运行期按任务所属设备决定 | 不能再按宿主打包两套网关 |
| 「边」= Electron 桌面 | 边包含桌面、其他本地电脑、云电脑 VM | 端侧装配不能依赖 Electron |
| 网关负责把流推给客户端 | 传输与编号归任务事件服务 | 网关只产出标准化增量 |

### 11.4 终态目录树

```text
pioneering/
├─ apps/
│  ├─ web/                        控制面客户端（云端任务）
│  ├─ mobile/                     控制面客户端（任务 / 审批 / 远控）
│  ├─ backend-ts/
│  │   ├─ src/tasks/              设备注册、租约、任务状态机、task_events(seq)
│  │   ├─ src/llm-proxy/          统一 LLM 代理（设备与 web 共用；平台 key、配额、审计）
│  │   └─ src/catalog/            云端模型目录（定价、限流、状态）
│  └─ desktop/
│      └─ src/main/
│          ├─ agent-process.ts    utilityProcess 入口（薄壳）
│          └─ llm/                profile 选择 + 钥匙串 + 本地探测
│
├─ packages/
│  ├─ agent-protocol/             AG-UI / HITL / 任务事件（含 protocol_version）
│  ├─ agent-client/               控制面 SDK：createTask / subscribe(afterSeq) / approve / stop / reassign
│  ├─ agent-kernel/               modu-agent 内核：graph / tools / memory / HITL，零厂商依赖
│  ├─ agent-host/                 ★新增：执行宿主（租约、事件、停顿、接管、profile、模型缓存）
│  ├─ llm-contracts/              模型描述 / 别名 / 能力 / 错误码 / 用量 / 代理协议
│  ├─ llm-core/                   alias 解析、profile 路由、能力兼容、超时重试、用量
│  ├─ llm-adapters/               openai-compatible / anthropic / ollama / llama-cpp
│  └─ llm-testkit/                契约与适配器一致性测试
```

**关键简化**：云电脑不写第三套装配。它以 `managed-proxy` profile 运行同一个 `agent-host`，与桌面共用全部代码路径。

### 11.5 执行宿主 `agent-host`

```text
agent-host/src/
├─ run/          任务生命周期、lease / fencing、stop、step 边界停顿
├─ events/       事件 sink（本地表 / 上报云端）、与服务端 seq 对齐
├─ profiles/     local-byok / managed-proxy / mixed
├─ models/       ChatModelFactory 实现 + 缓存（taskId + profile + alias + keyFingerprint）
└─ tools/        设备能力注入（授权目录、MCP、软件）
```

职责边界：

- **不含 Electron**：桌面用 utilityProcess 包一层，云电脑直接作为 Node 服务运行；
- **不含传输**：只产出事件，由 sink 决定落本地表还是上报云端；
- **不含业务状态机**：任务状态归 `apps/backend-ts/src/tasks`（本地离线任务由本地 DAO 兜底）。

### 11.6 三种 AccessProfile

| Profile | 密钥 | 模型来源 | 适用 |
|---|---|---|---|
| `local-byok` | 系统钥匙串 | 本地探测 + 直连厂商 | 桌面、有 GPU 的设备 |
| `managed-proxy` | 无（持 JWT / 设备令牌） | 云端目录 | 云电脑、web、mobile、无 key 的设备 |
| `mixed` | 钥匙串优先 | 本地优先、代理兜底 | 桌面在线且追求低延迟 |

选择规则：**任务创建时确定 `billing_mode`，设备执行时确定 `profile`**。两者独立，避免"本地执行却无法计费"或"离线却依赖平台 key"。

### 11.7 必须补的四个契约

| 契约 | 现状（v2.2） | 建议 |
|---|---|---|
| 设备模型能力 | `Device.capabilities` 仅含 `fs.local / app.control / net.intranet / office / gpu / browser.persist` | 补 `llm.local`、`llm.models[]`、`llm.max_params`、`llm.context_window`，否则能力预检对模型维度失效 |
| 任务模型意图与溯源 | `Task` 只有 `deviceId / checkpointRef / artifacts` | 增加 `Task.modelAlias`；`task_events` 每条记录 `resolved_model_id / provider / profile` |
| 计费与密钥来源 | 仅 §4.12 文字提及 `billing_mode` | 落到 `Task.billing_mode` 与 `UsageLedger.key_source / device_id`，作为代理与 BYOK 两条路径的计费依据 |
| 离线与平台 key | §4.10 承诺断网可跑，§4.12 要求平台托管 key | 明确：离线任务只能走 `local-byok` 或本地模型；`billing_mode=platform` 且离线时显式提示，不静默失败 |

### 11.8 与云边阶段 B–F 的对应

| 阶段 | LLM 接入侧动作 | 原因 |
|---|---|---|
| B（数据模型 + 进程隔离） | 抽 `llm-contracts`；内核改为注入 `ChatModelFactory`；`agent-host` 骨架与事件 sink | 唯一不可逆的一步，模型上下文必须一起进 per-run 结构 |
| C（任务解耦 + 事件日志） | `llm-core` 只产出标准化增量，交给 task_events；usage 带 `taskId / seq` | 否则重放缺片段、成本无法归属到任务 |
| D（云电脑） | `managed-proxy` profile + `llm-proxy` 服务；云 VM 跑 `agent-host` | 避免云电脑另写一套接入 |
| E（移动端 + 远控） | `agent-client` 增控制面 API；mobile 不打包 provider | 遥控器不需要模型接入 |
| F（换机） | `modelAlias` 随任务迁移、per-step 溯源、能力兼容预检 | 换机的语义正确性依赖该层 |

**顺序要点**：`agent-host` 必须与阶段 B 同批落地。若先做 B 再把 `agent-runtime.ts` 塞进 utilityProcess，云电脑阶段会再拆一次，等于返工两遍。

### 11.9 从当前口径迁移到终态的桥接（避免返工）

| 当前（第九、十章） | 终态（本章） | 迁移方式 |
|---|---|---|
| `packages/llm-gateway` 单包 | `llm-proxy` + `agent-host/profiles` | 先保留包内 `contracts / core / adapters` 三个目录，迁移时只搬装配层 |
| `agent-runtime`（modu-agent） | `agent-kernel` | 先加 `agent-kernel` 作为新入口并 re-export，旧入口继续可用 |
| 网关生成 SSE 事件 id | `task_events.seq` | 先保留 `id` 字段并双写，后续切换编号来源，前端不改协议 |
| `agent-client` 的 `sendMessage` | `createTask / subscribe(afterSeq)` | 先加新方法，旧方法标记 deprecated，一个版本后移除 |
| web 的 `sseClient` | 同一客户端 | 直接复用，仅把事件源从 HTTP 改为可插拔 |

### 11.10 两个需要提前规避的隐患

1. **进程级单例与任务级凭据冲突**
   `runtime-config.ts` 的 `_config`、`factory.ts` 的 `_sharedMemoryCheckpointer`、`runner.ts` 的 `_runnerCache` 都是进程级。多任务并发时，A 任务 BYOK、B 任务代理会互相串台。
   约定：配置、模型实例、缓存 key 全部 per-run；禁止再用 `reset_runner_cache()` 这类全局重置。

2. **换机后的模型连续性**
   换机在 step 边界发生，checkpoint 可迁移，但模型可能从 `deepseek-v4-flash` 变为本地小模型。
   建议：换机预检增加「能力等价性」硬门槛（`tools / json_mode / context_window`），不满足时提示用户而非自动降级；同时记录 per-step 模型，便于回放与评测。

### 11.11 切换判据

满足以下条件后，LLM 接入按本章收敛：

- 阶段 B 的 `devices / tasks / task_events` 表已上线，`task.deviceId` 成为唯一路由真相；
- `agent-host` 在桌面 utilityProcess 与云电脑 VM 两处跑通同一套代码；
- 设备模型能力与 `billing_mode` 已进入数据模型；
- 事件 seq 与 `Last-Event-ID` 重放通过验收。

在此之前，继续按第九章、第十章执行，不做结构性调整。
