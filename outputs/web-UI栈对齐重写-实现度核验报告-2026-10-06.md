## 三、新发现问题（按严重度）

### P1-1 · abort 语义只挂在"循环结束后"，vitest 因此红灯

`lib/parseAguiStream.ts:140-176` 的读取循环内**从不检查 signal，也不 `reader.cancel()`**，只在 `:203` 流自然关闭后才判 `signal?.aborted`。测试桩 `useAguiChat.test.tsx:18-35` 的 `sseResponse` 是自建 `ReadableStream`（与被 mock 的 fetch 一起，完全不受 AbortSignal 影响），2 个 chunk × 50ms ≈ 100ms 关闭，而断言发生在 70+30ms —— 时序撞车，`status` 仍为 `streaming`，`:285` 断言失败。

生产环境靠"浏览器 abort 会让 body reader 以 AbortError 拒绝"这条平台耦合侥幸走通（落到 `useAguiChat.ts:227` 的 catch 分支），实现自身没有中止出口。**修法（3 行，同时修好测试与语义）**：在 while 循环顶部加

```ts
if (signal?.aborted) { await reader.cancel(); return { reason: 'aborted', eventCount, eventTypes: [...eventTypes] }; }
```

收益：点"停止"后立即停止消费后续事件（而非等流关闭），测试从"靠 sleep 猜时序"变为确定通过。

### P1-2 · 刚生成的回答，反馈与重新生成必然失败

后端 `core/llm.ts:80` 明确在 `TEXT_MESSAGE_START` 事件里下发了**真实 assistant messageId**，`parseAguiStream` 也预留了 `onTextStart` 通道（`:101`）。但 `useAguiChat.ts:161-198` 注册的 handlers 里**没有 onTextStart**，消息 id 自始至终是本地造的 `a_${Date.now()}`（`:95`）。后果链：

- `ChatMessageItem.tsx:94` `feedbackMessage(message.id, ...)` → `POST /chat/messages/a_1759.../feedback` → 后端 `chat.ts:885` 按 id `findFirst` 落空 → 404 → toast"反馈失败，请重试"
- `ChatMode.tsx:238` `regenerateMessage(message.id)` → `chat.ts:913` 同样按 id 查库 → `NotFoundError('消息不存在')`

即：**新会话里第一条回答的点赞/点踩/重新生成一定失败**，除非切走再切回（走历史加载换成真实 id）。这正是冒烟清单 ① 中"反馈（good/bad）状态提交成功"与"重新生成"两项无法通过的原因。同仓库 task 模式已有正确范式——`usePlanExecuteChat.ts:54` 注释直言"后端持久化后才有真实 messageId"，并在流结束后拉历史补齐。

**修法（二选一，均 ≤6 行）**：注册 `onTextStart`，用 `event.messageId` 覆写 `assistantId` 并同步 patch 已入列消息的 id；或 chat 流 `finished` 后调一次 `reloadHistory()`。

（说明：重写前的 TDesign 版本同样用 `message.id` 做反馈，`git show HEAD:ChatMessageItem.tsx:61` 一致，故这是**既有契约缺口**而非本轮回归；但现在 web 已自持解析器，成本降到几行，且它是"阶段 4 退出标准"的硬阻断。）

### P2-2 · 流式渲染每个 token 全量重解析 Markdown

`ChatMessageList.tsx:100-104` 用 `messages.length + lastContentLen + status` 驱动自动滚动，每个 delta 都产生新消息数组；`Markdown` 虽 `memo`，但 `content` 字符串每个 delta 都在变 → 每个 token 触发一次 `ReactMarkdown` 全量解析 + `rehype-highlight` + `rehype-sanitize`，长回答整体 O(n²)。这与 memory 里 desktop 的"逐 token IPC 无批处理"是同一类问题。建议：delta 节流（rAF 或 60ms 合并）或流式中先渲染纯文本、终态再走 Markdown。
