## 一、功能完整性

### ①【P1】plan_execute 会话的 HITL resume 使用错误的图实例（静态证据链实证）

**证据**：
- `src/main/agent-runtime.ts:273-276`——send 时 `plan_execute` 走 `create_agent({ configurable: { plan_execute_enabled: true } })`（**新建图，不入缓存**）；
- `src/main/agent-runtime.ts:314`——`executeResume` 固定 `await get_runner()`（默认 ReAct 缓存图）；`getHitlState:437`、`abortPending:414` 同样用 `get_runner()`；
- `packages/modu-agent/src/graph/factory.ts:1009-1010`——planner/step_dispatch/step_finalize 节点**仅在建图期**由 `configurable.plan_execute_enabled` 决定是否挂载；
- 代码自身注释（agent-runtime.ts:267-272）承认「若只在运行时传，路由会指向不存在的 planner 节点而报错」。

**影响**：plan_execute 会话中一旦触发工具审批/澄清中断（RUN_PAUSED），resume 在缺少对应节点的图上重放含 `step_dispatch` pending 任务的 thread checkpoint → 无效目标/报错，计划模式 + HITL 组合整体不可用；`abortPending` 同理会以错误图结构执行 `resume_sync(approved=false)`。注释声称的「checkpointer 模块级单例跨图共享」只解决 checkpoint 数据可达，不解决图结构不匹配。**该路径 V2.7 的 26 项修复未覆盖**（测试仅覆盖 send 建图期覆盖，见 `agent-runtime.test.ts`）。注：静态证据链完整，未动态复现（需真实 LLM key 跑通 interrupt→resume）。

### ②【P1】图片附件止步 UI，模型侧链路断（代码注释自认）

**证据**：`shared/types.ts:107-131` `SendMessageRequest` 无 images 字段；`agent-runtime.ts:161-171` `validateSendRequest` 白名单静默丢弃任何图片字段；`lib/input/image-attachments.ts:6` 注释「后端暂未实现视觉通道，但附件在 UI 层完整可用」；`image-attachments.ts:29` 纯图发送用字面量 `'[User attached images without additional text.]'`。

**影响**：用户贴图发送后，Agent 收到的是一个方括号占位字符串而非图片，回复内容会暴露该占位符；无图片消息失败提示（发送成功语义与实际不符）。IPC 模式的 `buildIpcHistory`（chatStore.ts:93-100）也只压缩 role/content，多轮中的图片信息彻底丢失。属已知未实现，但从缺陷视角它是**当前最显著的功能断点**，且占位符外泄到模型输入影响回复质量。

### ⑤【P2】三个「有壳无核」的产品闭环

- **plan_confirm 方案确认门**：`shared/types.ts:308-311` 注释明示「后端图节点暂未发射该事件，属于协议预留」；UI 卡与 `getHitlState` 的 artifacts 透传（agent-runtime.ts:465）全部就绪，仅缺内核生产者节点；`InputArea.tsx:196-201` 的 mock 载荷 dev-only。影响：文档生成后「是否基于方案继续执行」的产品闭环不可达。
- **自动化定时任务**：`AutomationPage.tsx:50-51` 注释「真实定时调度（触发 Agent run）待后端/主进程调度器接入」；运行记录 Tab 恒定空态（550-554 行）。UI 已如实标注，主进程无 scheduler 模块。
- **插件市场**：`PluginsPage.tsx:119-344` 静态目录，安装态仅写 electron-store（T13），不产生任何运行时效果（不注册工具/不改 Agent 行为）。页面有琥珀角标如实声明。

### ⑯【P3】会话归档能力已铺设但未交付

**证据**：`local-store.ts` schema 含 `is_archived` 列、`listSessions` 支持 `archived` 参数、`ipc-channels.ts` 的 `LocalSessionListRequest` 透传；但 `ConversationList.tsx`/`SessionActionsDropdown.tsx` 无任何归档/取消归档入口（grep 无命中），渲染层 `chatService.getSessions(1, 50)` 恒取未归档。影响：`deleteSession` 走物理删除（本地）或 `chatService.deleteSession(sessionId, true)`（云端），用户没有软归档路径——底层列是死重。

### ⑳【P4】regenerateMessage 丢失发送选项

**证据**：`chatStore.ts:1563-1565` 重新生成仅回传 `images`，不传 model/selectedFiles/skill；模型走当前 defaultModel 而非原消息所用模型。影响：多模型场景下「重新回答」换了模型，结果不可复现。

## 二、边界条件处理

**做得好的**（不重复展开）：send/resume 入参白名单校验（agent-runtime.ts:148-193）、文件路径 4096 字符/空字节/`..`/软链逐级解析（ipc-handlers.ts:160-238）、10MB 读写上限 + `Buffer.byteLength` 单位修正、`sanitizeValue` 防原型链污染 + B6 净化失败拒绝写入、拖拽坐标 `Number.isFinite` 校验、DRAFT_ASSET 的 id/MIME/dataURL 三重校验、字符上限 10000 前端拦截。

### ⑰【P4】validateSendRequest 对 history 无尺寸界

**证据**：`agent-runtime.ts:153-160` 校验 history 每项的 role/content 为 string，但**不限数组长度、不限单项 content 长度**（顶层 message 有 100k 上限，history 没有）。影响：被攻陷的渲染端或 bug 场景可传无界 history 进内核（token 成本/内存）。前提有 `isTrustedSender` 把关，属纵深不足而非直接漏洞。

### ㉑【P4】反馈与本地落库均为 fire-and-forget

**证据**：`chatStore.ts:816-824, 1386-1391`——`appendMessages/sendFeedback` 失败仅 `console.warn`，无重试、无用户可见提示。影响：DB 异常时 UI 与 local-chat.db 不一致（消息「发送成功」但未持久化，重启后消失）；点赞点踩乐观更新失败会回滚 UI（1392-1398）但**不回滚后端**，两边可能长期不一致。

### ⑲【P4】HitlToolConfirmPanel 组件态跨项残留

**证据**：`InputArea.tsx:306-330` 注释宣称「组件随审批项条件挂载/卸载，展开/改参状态天然按项隔离」，但 `hitlStore.dequeue()`（hitlStore.ts:149-157）可在 currentItem 从 A 直接切到同为 tool_confirm 的 B 时不发生 null 中间态 → 组件不卸载，`argEdits/expanded/editMode` 的 useState 初始化器不重跑。影响：B 的卡片可能带上 A 的展开态；若 tool_call id 恰好碰撞（同会话连续两次 interrupt 复用 id 的内核行为），**提交的是上一项的陈旧改参 JSON**。隔离应改用 `key={hitl 标识}` 显式声明，而非依赖卸载时序巧合。

## 三、性能与效率

### ⑬【P3】逐 token 的 AGENT_EVENT IPC，无批处理

**证据**：`agent-runtime.ts:199-212`——每个 AG-UI 事件（含每个 TEXT delta）单独 `webContents.send(envelope)`；渲染端 `ipc-transport.ts` 逐条 structured clone 反序列化。stream-handler 的 rAF flush 只优化了 React 渲染侧，**IPC 消息量本身未合并**。影响：高频流式（>100 token/s）时主进程→渲染端每秒上百次跨进程消息 + JSON 序列化，挤占主进程事件循环（同进程还跑着 Agent 图执行）。缓解方向：主进程侧按帧合并事件或改 MessagePort 流。

### ⑫【P3】electron-store STORE_SET 同步整档写

**证据**：`ipc-handlers.ts:562-574` 直接 `appStore.set`（electron-store 默认同步全文件重写）；消费方含 400ms 防抖的文本草稿（use-input-draft-persistence）、插件安装态、自动化任务、API 设置。图片已外置（T9）消除大头，但草稿/设置键值增长后每次 set 重写全 JSON。影响：当前数据量下无感，随使用时长主进程出现周期性同步写放大（远期风险，提前记录）。

### ⑭【P3】历史消息 Trace 树全量重建

**证据**：`chatStore.ts:384-398` `chatMessageToMessage` 对每条历史消息跑 `buildTraceFromContentBlocks`（contentBlocks 是 JSON 字符串整档解析）；长会话 200 条含完整工具轨迹时一次 `loadMessages` 的解析成本集中在主线程。rAF 不覆盖此路径（一次性 setState）。影响：切换重会话时首帧卡顿（百 ms 级，随消息体积线性增长）。

## 四、代码健壮性与容错性

### ③【P2】idle 超时不联动 transport 取消——超时路径的孤儿 run

**证据**：`stream-handler.ts:151-157`——60s 无数据触发 `handleError` → `chatStore.onError`（chatStore.ts:916-936）finalize 消息并经 `emptyStreaming` **把 abortController 置 null**，全程不调 `controller.abort()` 也不调 `transport.stop()`。影响（IPC）：主进程 `executeSend` 循环继续到图自然结束，孤儿 run 持续消耗 token/CPU，UI 却已显示错误并「空闲」；用户再发送也不触发抢占清理（abortController 已 null，chatStore.ts:706 的抢占分支不命中）。HTTP 模式同理：fetch reader 持续读到网络流结束，数据靠 `isStale()` 丢弃。这是 T1 修复（抢占路径补 stop）遗漏的同型第二路径。修复：onError 终态统一 `abortController?.abort()` + 按 runtime `transport.stop`。

### ⑦【P3】ipc-transport 订阅泄漏（进程被强杀/窗口销毁边界）

**证据**：`ipc-transport.ts:98-106`——run 仅在「终态事件到达」或「本地 abort」时 `finishRun`（退订 + 出 activeRuns）。若主进程异常退出（未发出 RUN_ERROR），渲染端 `activeRuns` 条目与 AGENT_EVENT 监听器泄漏至页面重载。低概率，但 `window.api.agent` 通道无主进程存活探测。

### ⑨【P3】LocalChatStore 粘性失败

**证据**：`local-store.ts:451-466`——`_openError` 一旦置位，`getLocalChatStore` 永久返回 null。影响：瞬时磁盘/权限异常（外置盘拔出、备份工具锁文件）后，本地模式整个生命周期不可用且不提示原因，仅日志一条；「降级不崩溃」达成，但缺恢复路径与用户可见状态（UI 上 local 按钮仅按 `window.api.localChat` 存在性判定可用性）。

### ⑩【P3】删除会话不清理草稿与外置图片资产

**证据**：`chatStore.ts:1402-1447` `deleteSession` 删消息/会话/内存映射，但无 `removeInputDraft` 调用（全仓调用点仅 /clear 与发送后清除，grep 实证）；`draft-assets/<id>` 文件仅由草稿删除链路清理 → 被删会话若有含图草稿，electron-store 键 + userData/draft-assets 二进制文件永久残留。影响：磁盘单调增长的孤儿文件 + 存储键泄漏（安全面：被删会话的截图内容仍落盘可寻）。

### ⑪【P3】KeyStore 删除与 .env 加载模型失同步

**证据**：`key-store.ts:141-149` `delete()` 直接 `delete process.env[name]`；`agent-runtime.ts:121-139` `ensureAgentEnv` 的 `envLoaded` 为一次性布尔。影响：若该键同时存在于 desktop/.env，UI 删除后当前进程运行期间 LLM 键彻底消失（.env 值不会重新注入），表现为「删除密钥后所有请求 401，重启又好了」的迷惑行为；反向（改配置期望回退 .env）同样需重启。

### ⑮【P3】local 会话 model 列硬编码误导

**证据**：`local-store.ts:56, 223`——建会话默认 `model='gpt-4o-mini'`（对齐云端 schema 的字面量），与本地实际使用的 `LLM_DEFAULT_MODEL` 无任何关联；`toSessionDto` 把它回传渲染端。影响：会话元数据说谎，未来若 UI 展示「会话所用模型」会直接错误；本地 IPC 路径本就忽略 model 字段（agent-runtime validate 白名单），该列是误导性死数据。

## 五、可维护性与可扩展性

- `chatStore.ts` 1567 行承载会话 CRUD、流式编排、HITL 状态机、本地/云端分流、标题生成策略五种职责；`sendMessage` 与 `resumeHitl` 各自维护一套近 90 行同构的 onFlush/onDone/onError/onHumanInputRequest/onRunPaused/onHitlAborted 回调（chatStore.ts:846-968 vs 1162-1248），新增一类流事件需同步改两处，历史上多处 bug（HITL 中止漏落库等）正是这类双写漂移。

## 六、安全性

**做得好的**：sandbox:true + contextIsolation + 不暴露 ipcRenderer（H1/H5）、isTrustedSender 严格主机匹配（S1/S6 修复含 `localhost.evil.com` 用例）、文件路径白名单 + realpath 软链防逃逸（S4 父链解析）、`frame-src 'none'` + CSP connect-src 限回环、产物预览 `sandbox="allow-scripts"` 不给 same-origin（ArtifactRender.tsx:136，实证无洞）、MODEL_SECRET 明文不回传 + 掩码、通知/剪贴板/外链协议白名单、非隔离 preload 抛错拒暴露。

### ④【P2】无 will-navigate 守卫——同窗口导航不受限

**证据**：`src/main/index.ts` 全文仅 `setWindowOpenHandler`（拦截新窗口，S3 修复），**没有** `webContents.on('will-navigate')` 拦截（grep 实证全仓无命中）。影响：若渲染层被注入内容（XSS 或恶意产物 HTML 经某种途径逃逸），可在同一窗口触发 `location.href` 跳往任意 https 站点——preload 的 `window.api` 仍会被注入到该外部页面（contextBridge 按 webPreferences 生效），虽然 `isTrustedSender` 会让所有 IPC 被拒（外部 URL 不匹配白名单），但**钓鱼/伪造 UI 面完全敞开**，且 `window.api.store/agent` 的存在本身泄露应用结构。修复成本低：`will-navigate` 拦截非本地 URL → `setWindowOpenHandler` 同款处理。

### ⑲′【P3】CSP 头注入作用于所有响应

**证据**：`index.ts:54-63`——`onHeadersReceived` 无 URL 过滤，给**每一个**经 defaultSession 的响应追加 RENDERER_CSP。影响一：若未来渲染层加载真实远程资源（CDN 图片/iframe 应用），其响应被强加 `frame-src 'none'` 等策略造成诡异加载失败（当前架构不加载远程资源，属未来踩坑点）；影响二：向第三方域名回传「此环境注入了什么策略」的信息（轻微）。属正确性瑕疵而非漏洞。

### ⑳′【P4】数据删除承诺与实际不符（隐私面）

本地会话删除是**物理级联删除**（local-store.ts:272-285，注释自认「无归档恢复诉求简化为硬删」），配合⑩的草稿/资产残留，呈现「立即彻底删不掉 + 想恢复又没有回收站」的矛盾组合。对文档型桌面应用（用户可能期望误删可恢复），这是产品语义缺陷而非代码漏洞。

## 七、兼容性与依赖

**做得好的**：HashRouter（file:// 兼容）、CSP/网络检测层 127.0.0.1 归一化 + 旧端口迁移（Windows IPv6 解析）、窗口配置表按平台分支（window-config.ts）、`match-accelerator` 平台注入修正（T16，macOS ⌃/⌘ 测试全绿）、`better-sqlite3` 缺失→DAO 降级不崩溃、`safeStorage` 不可用→敏感键拒写并明示、`crypto.randomUUID` 有降级、`@pioneering/modu-agent` file: 本地包锁定同源演进。

### ㉑′【P3】Linux 环境的功能性缺口

`key-store.ts:129-131` + `ipc-handlers.ts:982-984`——safeStorage 依赖桌面密钥服务（libsecret/Keychain/DPAPI）；Linux 无密钥服务时本地模式 LLM 密钥**完全无法配置**（拒写），仅剩 .env 路径（打包态无此文件）→ Linux 用户本地模式事实上不可用。错误文案准确，但产品上缺一个逃生舱说明/降级通道（如首次运行检测并提示安装 libsecret）。

### ㉒′【P4】内核行为对桌面端为黑盒单点

desktop 对 modu-agent 的调用面（12 个导出符号，agent-runtime.ts:35-48）中 `get_runner()` 的缓存语义、`checkpointer 模块级单例` 等关键假设只写在注释里，没有契约测试兜底——①的 resume 图实例问题是该类假设漂移的已兑现案例；内核升级（file: 依赖随 monorepo 前进）时桌面端无版本握手/特性探测机制。

## 结论与修复优先级建议

1. **先修 ①**（plan_execute resume 图实例）：executeResume/abortPending/getHitlState 增加「按会话记录 send 时所用图句柄」或在 resume 时按 `session.agentMode==='plan_execute'` 重建带 plan 节点的图；补一条「plan_execute + 审批 interrupt + resume」的集成回归测试。
2. **再修 ③**（超时取消联动）：onError 终态补 `abortController?.abort()` + `transport.stop`，与 T1 抢占路径对齐——两处共用一个 `terminateRun(sid)` 小函数即可，顺带消除样板。
3. **④ 与 ②**：will-navigate 一行守卫（低成本 P2）；图片通道需要 SendMessageRequest→validateSendRequest→内核 image_processor 全链排期，属功能项非修复项，建议明确列入里程碑。
4. ⑩（删除会话清草稿+资产）与 ⑪（密钥删除 .env 失同步）为小改动高一致性收益；⑬⑭⑮ 为性能/重构储备，可排期。
