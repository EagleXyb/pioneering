# apps/desktop 修复任务清单（按优先级）

- 来源：《desktop-ui功能分析报告-2026-10-05.md》（含同日复审勘误附录 A），逐条回源确认，行号以工作树 HEAD `fb2bdaa` 为准（分支 V2.6；原基线 `d133c2c` + AccountMenu 未提交改版已过期，`21b90e5` 已提交）。
- 优先级定义：P1 = 功能错误或真实资源损耗；P2 = 误导用户 / 安全隐患 / 架构债；P3 = 死路交互与半成品（伤可信度但不伤功能）；P4 = 有意占位（仅需文案或排期标注）。
- 「改动面」标注是否跨包：仅 desktop 可自闭环，或需联动 packages/modu-agent / apps/backend-ts 契约。

## 本次优化（2026-10-05 第二轮）引入的两个降级维度

对照报告复审后，本次重排额外引入两个此前缺失的判据，用于纠正「修了但用户用不上」和「不阻断任何门禁却被误当紧急」的错配：

1. **可触发性**：修复后是否存在真实用户路径能触达该缺陷？无路径者降级并绑定到上游生产者任务，避免出现「修好了但永远不生效」的任务。
2. **门禁阻断性**：该失败是否阻断 `npm run build`？实测 `build` = `typecheck && electron-vite build`（**不含 test**），且仓库无 `.github/workflows`，故 5 例测试失败不阻断任何流水线——测试债据此锚定 P3，而非凭「有失败用例」直觉升级。

**优先级变更摘要**（详见文末附录 B）：

| 任务 | 原级 | 新级 | 依据 |
|---|---|---|---|
| T9 草稿图片 base64 同步整档落盘 | P2 | **P1** | 20MB base64 × JSON 往返 × 同步落盘，符合 P1「真实资源损耗」定义 |
| T2 本地 getHitlState 不透传 artifacts | P1 | **P3** | 无可触发性：plan_confirm 全链路无生产者（报告 §4-A-2），修好也无用户路径 |
| T10 agentMode=plan_execute 入口 | P2/第二批 | **P2/第一批** | 原标注的内核阻塞已被 `graph.ts:669-685` 的 T0-2 修复解除 |
| T4 图片全链路 | P1 单条 | **拆为 T4a/T4b** | T4a 仅 desktop 可闭环且能消除误导，应先做；T4b 跨包独立立项 |
| T3 TaskMonitor 硬编码 | P1 | P1（保留） | 与报告 §4-C-15 的 P2 分歧，本清单按「默认标签页即虚假信息 + 修复成本 1 行」从严判定 |

## P1 —— 先修（正确性与资源成本）

### T1. IPC 抢占发送产生孤儿 run（烧 token）
- 现状：流式中发送新消息走 `chatStore.ts:677-699`，只 `abortController.abort()`（渲染端退订），不调 `transport.stop()`；主进程 `executeSend` 继续跑到自然结束。停止按钮路径已修（`chatStore.ts:984-993`），两处语义不一致。
- 方案：抢占分支对齐停止按钮——对 Agent 通道（`useAgent` 时）追加 `void getTransportForRuntime(targetSession?.runtime).stop(sid).catch(()=>{})`；普通聊天沿用 `chatService.stopGeneration`。
- 文件：`stores/chatStore.ts`。改动面：仅 desktop。
- 验收：本地 IPC 模式流式中直接发新消息，主进程日志出现 `stopRun aborted=true`，旧 run 事件提前终止（不再有旧 runId 的后续 AGENT_EVENT）。

### T3. TaskMonitor「待办」硬编码示例数据
- 现状：`TaskMonitor.tsx:44-49` DEFAULT_TODO_ITEMS 为 4 条与任何会话无关的"已完成"历史示例（含 2026-08-16 AI 新闻任务），右栏默认打开即展示（`rightPanelStore` 默认标签 = monitor）。
- 方案分两步：① 立即——默认值改为空数组走「暂无待办项」空态（`TaskMonitor.tsx:341-343` 已有空态分支）；② 数据接线——消费已有 `plan-step` TraceNode（STATE_DELTA 已在 stream-handler 落地，`stream-handler.ts:550-586`），把当前会话 plan-step 节点映射为待办项（标题=description、完成态=status），历史会话取最后一条 assistant 消息的 traceNodes。
- 文件：`right-panel/TaskMonitor.tsx`。改动面：仅 desktop（数据源已存在）。
- 验收：普通会话右栏不再出现无关待办；plan_execute 轨迹下待办与步骤状态同步。
- 附注：② 的价值依赖 T10 打通 plan_execute 入口，否则普通会话永远产不出 plan-step 节点。故 T10 优先级已相应上调。

### T4a. 图片附件「按钮」入口无响应（用户可见的功能错误）
- 现状：`image-attachments.ts:17` 注释声称附件支持「粘贴 / 拖拽 / 按钮添加」，实测 `addImages` **只有 2 个调用点**（粘贴 `InputArea.tsx:651`、拖拽 `:685`）。「+」面板 → 上传文件走 `handleAttachFile`（`:632-643`），打开通用文件对话框后**只插入 `@{path}` token**（`:624-629`），不生成缩略图附件——用户点「上传文件」选一张图，界面无任何反馈。另：拖拽路径仅按 `f.type.startsWith('image/')` 过滤（`:682`），未像粘贴那样限定 png/jpeg/gif/webp（对比 `image-attachments.ts:61`）。
- 方案：① 二选一并保持一致——要么让按钮路径对图片调用 `addImages`，要么从 UI 移除图片上传暗示；② 拖拽复用粘贴的类型白名单（`image-attachments.ts:61` 的 `ACCEPTED_IMAGE_TYPES.includes`）；③ 同步修正 `image-attachments.ts:17` 文件头注释。
- 文件：`components/chat/input/InputArea.tsx`、`lib/input/image-attachments.ts`。改动面：仅 desktop。
- 验收：三个入口行为一致或入口明确移除；选中 png/jpg/gif/webp 均走附件路径，其他类型走 token 路径。
- 注：本任务是 T4 全链路的前置止血，**不依赖任何跨包排期**，应先于 T4b 完成。

### T9. 草稿图片 base64 同步整档写 electron-store（真实资源损耗）
- 现状：草稿（含 ≤20MB 图 base64）经 `STORE_SET` 写主进程，主进程 JSON 往返 + 同步整档落盘；`use-input-draft-persistence.ts:43` 仅 400ms 去抖、**无体积阈值**，高频编辑会阻塞主进程。
- 方案：图片附件落 `userData/draft-assets/<id>`（复用 `FILE_WRITE`，`shared/ipc-channels.ts:44`），草稿仅存引用；草稿写节流加大，并对 value 体积超阈值时跳过图片字段。
- 文件：`hooks/use-input-draft-persistence.ts`、`lib/input/input-drafts.ts`、（配套）`ipc-handlers.ts`。改动面：仅 desktop。
- 验收：附 20MB 图连续输入时主进程无同步写阻塞；草稿恢复仍能还原缩略图。

### T17. 「+」面板图片入口与附件能力不一致（同 T4a 根因，另侧）
- 现状：HITL 精简态（`mode='hitl'`）下 `+` 面板仅剩附件项（`InputArea.tsx:535-538`），而该面板唯一动作 `handleAttachFile` 不产出图片附件（同 T4a）——即 HITL 态下图片**完全无法附加**。
- 方案：随 T4a 一并修复；若选择「移除图片上传暗示」，则 HITL 态需给出明确文案而非静默无效。
- 文件：`components/chat/input/InputArea.tsx`。改动面：仅 desktop。

## P2 —— 尽快修（误导 / 安全 / 架构债）

### T5. 「检查更新」假结果
- 现状：`AboutSection.tsx:144-153` 用 `Math.random() > 0.2` 决定"已是最新/出错"，用户会得到虚假反馈；主进程 `APP_CHECK_UPDATE` 仅回传版本号（`ipc-handlers.ts:290-294`），无自动更新器。
- 方案：接入真实 updater 前，按钮点击直接展示"当前版本 vX，暂无自动更新通道"（或调用 `appApi.checkUpdate()` 回显版本），删除随机逻辑。
- 文件：`settings/sections/AboutSection.tsx`。改动面：仅 desktop。

### T6. 模型选择三处断裂 + apiKey 明文
- 现状：输入框下拉硬编码 `MODEL_OPTIONS`（`InputArea.tsx:212-220`）与设置页 `modelConfigs/defaultModel`（localStorage persist，apiKey 明文）零连通；本地 IPC 模式 model 被 `validateSendRequest` 丢弃；'Auto' 原样发给云端。
- **补强（复审发现）**：两侧不只是"两套数据"，而是**内容互斥**——Kimi K3、Auto、glm-5-turbo、minimax-m2.7 各仅存在于一侧，用户在设置页启用的模型在下拉里可能根本选不到。这使问题比原描述更严重。
- 方案：① ModelSelect 改为读 `useAppStore.modelConfigs`（enabled 项 + defaultModel），保留"配置模型"跳设置入口；② apiKey/apiBase 迁入既有 safeStorage 受管键通道（SECURE_KEY_SET 已含图缓存失效），localStorage 不再存敏感值；③ 本地模式如需按会话换模型，内核侧要求 model 进入 config hash 或提供运行时覆盖——短期可先在 UI 标注"本地模式模型以设置页密钥配置的 LLM_DEFAULT_MODEL 为准"。
- 文件：`InputArea.tsx`、`ModelSection.tsx`、`useAppStore.ts`、（可选）`agent-runtime.ts`。改动面：desktop 为主。

### T7. SecuritySection 装饰开关

- 文件：`SecuritySection.tsx`。改动面：仅 desktop。

### T8. chatStore ↔ hitlStore 循环 import
- 现状：**已复核实存**——`chatStore.ts:40` 顶层 `import { useHitlStore } from './hitlStore'`，`hitlStore.ts:23` 顶层 `import { useChatStore } from './chatStore'`，模块级互相引用，靠运行时时序侥幸。任一侧模块初始化顺序变化即可能拿到 undefined。

### T10. agentMode=plan_execute 无 UI 入口（阻塞已解除，可立即排期）
- 现状：chatStore→主进程→内核透传链完整（`chatStore.ts:932` → `types.ts:130` → `agent-runtime.ts:273-283`），但 `createSession` 三处均只写 `react_agent`（`chatStore.ts:507,531,545`），desktop 无任何交互能置为 plan_execute。

- 验收：切到计划模式后本地/云端均进入 planner→step_dispatch 链路，不出现 unknown destination。

### T18. SidebarNav `placeholder` 标记与实际实现矛盾（未来误改风险）

- 方案：删除这四个 `placeholder` 标记，或改为从页面组件自身导出的能力标志（单一真源）。
- 文件：`components/sidebar/SidebarNav.tsx`。改动面：仅 desktop。
- 验收：导航无过时的占位声明；占位状态与各页实际渲染一致。
